## Overview/Goal

Turn the raw metrics of S-A..S-D into something a maintainer or an orchestrator can act on without a composite score (D4): each metric shows its raw value beside two separate judgments, its trend coloured green / yellow / red **vs baseline** (a value measured from existing data and recorded before any future number is seen, D8) and its **target attainment** against a declared target (D17), trends are visible on the CLI and on a dashboard page (D7), and a metric can feed a gate only after a human audit has shown it reliable (D6).

Staged requirements R-48, R-49, R-50, R-51 (and R-29's answered definition). Baseline: leaves `baseline-set-a-metric-s-threshold`, `baseline-read-the-evaluation-metrics` and `baseline-start-a-session` (BR-1413) (proposed rules below); BR-1005 stays true (no metric feeds a decision in this initiative). Depends on S-A..S-D.

## Scope

- `lore metrics baseline [--apply]` (BR-1405): without `--apply` prints the baselines it would store; with `--apply` appends, for each ok metric with no baseline, an epoch-1 row to the corpus store — metric, epoch, value over the 30 days ending at the recording, window, sample size, recorded_by, time — each row and its audit entry in one store transaction, unique per (metric, epoch); of two concurrent first recordings one succeeds and the other exits 4. Re-running never changes a row. The race is tested through the barrier seam (E-D16).
- `lore metrics baseline --rebaseline <metric> --reason <text>` (BR-1416): the only way to move a baseline; appends the next epoch (30 days ending then) with its reason and audit entry in one transaction; earlier epochs stay stored and the latest is current; without `--reason` exit 2; metric not ok or never baselined: exit 4; two concurrent rebaselines of one metric: one succeeds, the other exits 4.
- No update or delete (BR-1418): no command updates or deletes a baseline row, so delete-then-re-record is impossible; `.lore/config.yaml` holds no baselines (the D12 band values stay where they are); a direct store edit is caught by the audit trail's chain verification. The earlier digest / `unaudited` mechanism is dropped: it guarded a settings-file copy that no longer exists.
- Trend colour (BR-1406, BR-1405, revised S3 round 2, eng 8): each baseline is stored with its 95% interval; the relative change from it, in the metric's declared bad direction, gets a 95% interval combining the current and the baseline interval (MOVER ratio, Donner and Zou), rounded to 9 decimals, a bound exactly on a 10% or 25% edge counting as past it; red or yellow when the whole interval lies past 25% or 10%, green when the whole interval is short of 10%, otherwise `within_noise`. When the baseline's own interval reaches 0 a ratio is undefined, so the difference interval (Newcombe from Wilson for shares, MOVER difference otherwise) is judged: red when wholly beyond 0 in the bad direction, green when wholly on the good side, otherwise `within_noise`; a value staying at a zero baseline is within noise, not green.
- Two judgments per metric (D17, BR-1454): the raw value, `trend_vs_baseline` (the colour above, always labelled "vs baseline" in text, JSON and dashboard) and `target_attainment` (`met` | `not_met` | `within_noise` | `no_target`), never merged into one field. `no_target` and `within_noise` are never styled as a good result; a metric whose target is not met is never shown as fine, whatever its trend.
- Target attainment (BR-1453, BR-1460): met when the whole 95% interval is on the target's good side (a bound equal to the target counts as met), not_met when the whole interval is on the bad side, else within_noise; no stored target → `no_target`; insufficient or no_data → no judgment. A metric that is itself a 95% bound (the kappa lower bound) is compared directly, with no further interval, so attainment and gate eligibility (BR-1407) read it the same way (eng 9). Fewer than 20 facts in a metric or a trend bucket: no colour and no target judgment, never green (R-48, BR-1460).
- Targets (BR-1452, revised S3 round 2, design 9): `lore metrics target [--apply]` stores an epoch-1 row (metric, epoch, value, good direction, source, recorded_by, time, reason) with its audit entry in one transaction, unique per (metric, epoch), only for a declared target whose source cites external evidence, a live baseline rule, or an owner decision recorded from a person's terminal (the S4 approval of a proposed row is recorded that way); a proposed target with no owner decision is refused (exit 4), stored nowhere, and its metric shows `no_target`. `lore metrics target --retarget <metric> --value <v> --source <citation or decision> --reason <text>` appends the next epoch (exit 2 without reason; exit 4 for a metric without a declared target or a source that is neither); no update or delete; same barrier seam as baselines. Targets live in the store, never in `.lore/config.yaml`.
- Trend: `lore metrics --trend day|week [--since <iso>] [--until <iso>]` (`--since`/`--until` are S-A's window flags) gives each metric's envelope per bucket, computed on read. The HTTP read surface exposes the same JSON; the dashboard page `/p/<project>/metrics` (and `/metrics` in single-project mode) shows one section per question with each metric's per-bucket values, colour, sample size and status, from that JSON.
- Gate eligibility (BR-1407): `lore metrics eligibility <metric>` exits 0 only for a question-A metric backed by audited judgments with at least 30 audited items and the 95% lower bound of κ ≥ 0.6; every other request exits 4 naming what is missing. No other metric can become eligible in v1. No gate is wired to a metric in this initiative.
- Session start (BR-1413): `lore bootstrap` prints one line per metric red or yellow vs baseline or whose target is not met, with its value, baseline, target and action line (`action_line`, defined in S-A A-D13: a fixed sentence authored with the metric's definition by the slice that builds it); the compact injection is unchanged.

### Targets

Source "external" cites evidence and is stored by `lore metrics target --apply`; "proposed — owner decides at S4" is a pending owner decision, not stored truth: it is stored only once the owner's decision is recorded (BR-1452), and until then the metric shows no target. DORA values: 2024 performance clusters (octopus.com/blog/2024-devops-performance-clusters, evidence tier B4 in `knowledge-evaluation-systems-for-ai-native-development`, fetched 2026-10-26: Elite lead time < 1 day, change fail 5%, recovery < 1 hour; High 1 day-1 week, 20%, < 1 day); dora.dev defines the metrics but publishes no numbers. A landing is far smaller than a DORA deployment, so the High cluster is used where the Elite value would be met or missed by unit size alone.

## Out of scope

- Wiring a specific metric into an autonomy decision or plan close: a pre-registered branch in the plan opens a new spec when the first metric becomes eligible.
- Push alerts (trap row 18); rankings by person (trap row 20); any combined score (trap row 21).

## Design Decisions

| # | Decision | Chosen | Rejected and why |
|---|---|---|---|
| E-D1 | Where baselines live (review rev5-5) | Append-only rows in the corpus store (metric, epoch, value, window, sample size, recorded_by, time, reason), each written with its audit entry in one transaction, unique per (metric, epoch); band values stay where they are | Project config written by a command with a separate audit entry (two stores whose writes can part, a file compare-and-swap, and a hand-delete path that re-opens write-once); a corpus document (no machine-read contract) |
| E-D2 | X and Y | 10% yellow, 25% red, fixed in the rule text so changing them is a spec change (pre-registration) | Per-metric X/Y (invites tuning after seeing data); σ-based bands (needs a long stable history this corpus does not have) |
| E-D3 | Zero baseline (revised S3 round 2, eng 8) | When the baseline's interval reaches 0, judge the difference interval (Newcombe/MOVER difference): red when wholly beyond 0 in the bad direction, green when wholly on the good side, else within_noise | A ratio against 0 (undefined); the round-1 value-interval exception that called a value staying at 0 green (a zero baseline is itself uncertain); letting the edge rule apply at 0 |
| E-D4 | Trend storage | Computed on read per bucket | Snapshot rows (a writer under concurrency; turns reads into writes) |
| E-D5 | Dashboard data | The same JSON as the CLI via the HTTP read | A dashboard-side computation (two implementations that can disagree) |
| E-D6 | Noise (S3 eng 5; round 2 eng 8) | Colour only when the 95% interval of the relative change, combining the current interval (Wilson for shares, bootstrap otherwise) with the stored baseline interval by MOVER ratio, lies wholly past the band edge, else within_noise | Point-value bands (n=20 shares flip colour on noise); an interval on the current value only with the baseline treated as exact (round 1: 0.23 against 0.20 with baseline interval 0.17-0.23 read yellow); a bootstrap over the baseline's facts (the attempt ledger is gone after 30 days, so the baseline's facts cannot be re-read) |
| E-D7 | Fixed targets (revised by D17, 2026-10-26) | Targets are kept as a mechanism: the note-share argument (S-B B-D15) removed one metric that cannot miss, not the mechanism. A baseline taken from known-bad data makes green mean "no worse than at the start", which reads as "good"; a target judges the value itself. The note share still gets no target | No targets, baseline as the only reference (the earlier v1 choice: hides a metric that stays bad); targets replacing baselines (loses the change signal and the pre-registered bands) |
| E-D17 | How trend and target are shown (D17) | Two separate judgments plus the raw value; trend always labelled "vs baseline"; `no_target` and `within_noise` neutral, never green; bootstrap also lists not-met targets (BR-1413, BR-1453, BR-1454) | One combined colour (worst of both: hides which judgment fired); attainment shown only in JSON (the text and dashboard would still read green as good); a metric without target shown as met |
| E-D18 | Where target values come from (round 2, design 9) | External evidence cited where it exists (DORA 2024 clusters, Landis and Koch, BR-1410); otherwise proposed here, marked "proposed — owner decides at S4", and stored only once an owner decision is recorded from a person's terminal | Storing proposed targets as audited truth (round 1: an AI-proposed value would colour metrics as if decided); targets chosen by the implementer; targets only where evidence exists |
| E-D19 | Where targets are stored | Append-only store rows with audit entry, epoch per change, like baselines (BR-1452); the declared values live in the metric registry with each definition and are recorded by `lore metrics target --apply` | Project config (hand-editable without audit); reading the registry value directly (a change would rewrite the reference with no epoch or audit) |
| E-D20 | Attainment edge | A bound equal to the target counts as met (targets are written as ≤ / ≥) | Strict inequality (a value exactly on target would fail its own target) |
| E-D21 | Metrics that are themselves confidence bounds (round 2, eng 9) | Judged directly against their target and baseline, with no interval of their own (BR-1460) | An interval around a bound (double-counts noise: a kappa lower bound of 0.61 is gate-eligible under BR-1407 yet would not read met) |
| E-D22 | Small samples (round 2, eng 10; R-48) | Below 20 facts in a metric or trend bucket: no colour and no target judgment (BR-1460) | Colouring buckets from their own interval only (a 5-fact day bucket could read green) |
| E-D23 | κ target value (S3 round 3) | 0.6, the BR-1407 eligibility floor, proposed for the owner at S4 | 0.61 from Landis and Koch (a κ bound of 0.60 would be gate-eligible yet not meet its target: two thresholds for one quantity) |
| E-D24 | Target sources the store admits (S3 round 3) | External evidence, a live baseline rule (audit completion, BR-1410), or a recorded owner decision (BR-1452) | Calling an internal rule external (mislabels the evidence); requiring an owner decision for a value an approved rule already fixes (a second decision for a decided number) |
| E-D8 | Concurrent baseline writes (S3 eng 10, review rev5-5) | The store's unique (metric, epoch) inside one transaction: the loser exits 4, nothing half-written | Compare-and-swap on a settings file plus a separate audit write (ordering gap between the two) |
| E-D9 | Gate scope (S3 DA2, eng 4; D10) | Only question-A metrics backed by audited items, gated on the κ lower bound ≥ 0.6; a machine-only reliability proof for other metrics is out of v1 | Any audited metric on κ point value (n=30 κ ±0.25) |
| E-D10 | Agent action on red (S3 EU1; revised D17) | The session-start snapshot (`lore bootstrap`) prints one line per metric red or yellow vs baseline or whose target is not met (BR-1413); the compact injection stays seat-only | Injecting metric lines into the compact session-start form (it carries only the seat's own claims by rule); wiring red into a gate (D6); printing only red and yellow trend lines (a metric at its baseline but below target would never be shown) |
| E-D11 | Recorded baselines on this repo (S3 plan 6) | AC-TS-6: every ok metric has an audited baseline with its stored window, every other states a reason, no question lacks registered metrics, totals printed; recording blocked by the telemetry and test-run fixes | Requiring 11 baselines (H may be permanently no_data) |
| E-D12 | Re-recording baselines (review rev2-5) | Write-once; replacing needs `--rebaseline <metric> --reason`, keeps the old value, audited, new epoch shown (BR-1416) | Re-running `--apply` overwrites (a red metric could be turned green by re-recording: post-hoc tuning) |
| E-D13 | Baseline window (review rev2-5) | The 30 days ending at the recording, stored with the baseline | All history (drifts with corpus age); the caller's chosen window (two implementers record different references) |
| E-D14 | Exact edge (review rev2-5) | After 9-decimal rounding a bound on the edge counts as past it, matching "worse by at least 10%" (D8) | Short of the edge (a value exactly 10% worse would never turn yellow) |
| E-D15 | Hand-edit detection (review rev3-5..rev5-5) | Dropped: baselines are store rows no command updates or deletes, and a direct store change is caught by the existing audit chain verification (BR-1418) | A per-baseline digest with an `unaudited` state (it guarded a config-file copy that no longer exists, and could not catch delete-then-re-record) |
| E-D16 | How recording, rebaseline and target races are tested (review rev3-5; rewritten S3 round 3 for the store-row design) | A test seam `LORE_TEST_BASELINE_BARRIER` pauses each process after it has read the current epochs from the store and before its insert transaction, until a barrier file appears, so two writers provably overlap; the store's unique (metric, epoch) inside one transaction then lets exactly one win and the other exit 4 (E-D8). Used by baselines, rebaselines and targets alike; the sequential ordering is asserted separately | Two processes started together with an outcome that depends on timing (a correct implementation can fail the test); asserting only the sequential case (the unique-constraint path would never be exercised); a pause point before the store read (both would read before either writes only by chance) |

Falsifier literals implementers must keep: `YELLOW_PCT = 10` and `RED_PCT = 25` in `packages/lore/src/service/metrics/thresholds.ts`; `factsInBucket(` in `packages/lore/src/service/metrics/trend.ts`; `"no data"` in `packages/dashboard/src/components/metrics/MetricCell.tsx`; `KAPPA_LOWER_BOUND_MIN = 0.6` in `packages/lore/src/service/metrics/eligibility.ts` (the only AC-TS-3 falsifier literal); `SHOWN_AT_START_IF_TARGET = ["not_met"]` in `packages/lore/src/service/metrics/thresholds.ts` (AC-TS-7 empties it); `INSERT INTO metric_targets` in `packages/lore/src/service/metrics/target-store.ts` (AC-TS-9); `"not_met"` in `packages/lore/src/service/metrics/attainment.ts` (AC-TS-10); `INSERT INTO metric_baselines` (AC-TS-1) and `epoch: current.epoch + 1` (AC-TS-8) in `packages/lore/src/service/metrics/baseline-store.ts`.
