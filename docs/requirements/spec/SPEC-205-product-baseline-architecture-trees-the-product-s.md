## Product Baseline & Architecture Trees (the product's current form)

**Status of this section**: PRD UPDATE, owner-approved 2026-10-07 after a 5-stakeholder review (scores 6,6,6,6,5; consensus fixes applied: BL-13 evidence-computed rule truth, BL-14 citation fidelity, slicing, hardened metrics, BL-1 downgraded to fresh-only). Upstream chain for this round: owner decisions (`adr-the-product-is-a-baseline-tree-specs-are-implementations`, decisions 1–12) + Validation Ledger (`knowledge-baseline-product-shape-validation-ledger-a1-spec-to`, experiments A1–A5). No benchmark teardown or OST was run for this round; the reference method is `everything-workspace/skills/business-baseline` (DDD modelling layer + BDD specification layer) and the reference architecture layout is `everything-workspace/architecture/`. Requirements carry `source` and `validation`; nothing is marked validated that the Ledger does not show as validated.

### Problem

"What does lore do in domain X, and under which rules?" has no single, addressable answer today:

- 165 of 166 live specs hang directly off the root PRD; none sits under a domain. Specs are per-requirement documents: the rules of one domain are spread across many of them, and old ones are not updated when later ones change behaviour.
- The root PRD (v77) has become an append-only requirement log (Goals G1–G16 by phase/version, 18 `R-##` entries) rather than a description of the product as it is.
- The corpus answers questions confidently and wrongly when an older doc disagrees with the code. Measured (A3): a reader using only `lore search/get` scored 8/10 on ten code-verified boundary questions, with **2 confident-wrong answers** (relied on a stale SPEC-002 parent table; read a schema and missed a lint) while self-reporting "no contradictions". This is North Star property 1 ("the corpus must not lie") failing in practice.
- The same AC id is claimed by more than one live spec (observed: `AC-ACS-1..8` in two specs), so an AC id is not an address (North Star property 3).

Primary users: AI agents working in lore-governed projects (they read rules before producing, and are the first to be misled by a stale corpus), and the human owner who adjudicates. Secondary: every consuming project, which inherits the same problem the moment its corpus grows past one round.

### Product shape (what changes)

1. **Two current-state trees, nothing else defines the product.**
   - **Baseline tree** (business): root → branches (bounded contexts; boundary where a term changes meaning) → leaves (one business point each: single verb, user-meaningful result, Command → Constraint → Domain Event). Leaves hold rules. Mutable, current-state only; history lives in versions and change records, never in the text.
   - **Architecture tree** (technical), laid out as `everything-workspace/architecture/`: current-state (system overview, module cards, dependencies, data flow, deployment), target-state (target, boundaries, migration roadmap), standards (rules new code must follow; four parts: Current Reality / Target Rule / Current Exceptions / Migration), ADRs, and an architecture-debt registry (id, scope, issue, severity, target, owner, status).
2. **Specs are implementations, related many-to-many.** A spec has no single tree parent. Every acceptance criterion cites ≥ 1 live rule — a baseline leaf rule or an architecture standard rule. "Which specs implement this leaf / standard" and "which rules have no implementing AC" are computed from citations.
3. **The PRD keeps strategy only** (why, for whom, non-goals, positioning). It stops being the tree root and stops carrying requirement inventories; its `R-##` entries become leaf rules and its outline entries become branches.

Lore's own baseline branches (owner-approved 2026-10-07): corpus · review · baseline · specification · execution · session · hygiene · autonomy · issue-loop · distribution · sync · context. Not branches: dashboard (a surface), provenance changelog (history), output-contract (its rules distribute into leaves), gates (each gate is a `guaranteed` rule in the leaf it constrains), read-only queries (cross-cutting notes on their branch).

### Non-goals (with the evidence that set them)

| What | Why |
|---|---|
| Gherkin `.feature` files in the tree | Acceptance is lore's AC-as-code with runner attestation, which already proves a command ran; rules carry inline boundary examples instead |
| A single tree parent per spec | Refuted three times: A1 (50.6% / 60.4% vs 70%), A4 (66.5% tree agreement vs 85%), A5 (computed home 80% vs 85%) |
| Placement of a spec decided by agent judgment | Refuted (A4: 66.5% inter-agent agreement; plainly wrong placements observed) |
| Change-set `impact` field (additive / action-required / breaking) | Not selected for v1 (ADR 7); revisit if BL-10 output proves insufficient |
| Bulk generation of a whole baseline in one pass | Reference method: bulk extraction rots; lore's own migration (BL-7) is excavated branch by branch from code, not generated from the existing prose |

### Decisions the design spec must make (engineering review)

Data model: what replaces a spec's `parent_id` (schema requires it for spec / task / phase today, auto-resolved to the root PRD); whether rules are structured data (like ACs and phases in `extra`) or parsed from markdown — BL-9/10/11/13 need structured; rule-id scope (global vs per-branch) and where it is stored; where an AC's citation lives (a new AC field) and what adding it does to already-approved specs (`ac set` demotes); how duplicate AC ids (`AC-ACS-*`) are resolved. Single-root consumer inventory: grep-derived list of every site that assumes one PRD root (the engineering review counted 20+ files, e.g. corpus-service, prd-outline-service, session-service, gate-predicates, tree, status), each with a target.

Kill / revisit criteria: (1) pilot (BL-7): if owner adjudication exceeds 30% of the pilot branch's ACs, stop and redesign the migration before scaling — the 30% line is a starting assumption (A5 suggests ~31% rule-level disagreement retroactively), to be re-set from pilot data, not defended; (2) if a branch's probe accuracy falls below the corpus-only baseline at the 4-week re-probe, the format is not earning its cost for that branch; (3) if citation fidelity (BL-14) is below 70% after the gate arms, the gate is producing ceremony — return it to report-only.

### Risks and assumptions

| Risk / assumption | Confidence | Mitigation |
|---|---|---|
| Rules go stale like specs did | HIGH that this is the central risk (all 5 reviewers) | BL-13 computes each rule's truth from attested evidence and code drift; the 4-week re-probe metric measures it. A2/A3 measured a *fresh* baseline only |
| Citation becomes ceremony (agents cite a plausible id to pass the gate) | HIGH | BL-14 fidelity sampling + catch-all flag + exemption cap; kill criterion (3) |
| A half-migrated corpus runs two truths | MEDIUM | slicing (see Delivery slices) keeps the gate report-only until the pilot passes |
| Rule-level AC mapping needs heavy owner adjudication | MEDIUM (A5: 69%) | BL-7 pilot with a kill line before scaling |
| Two concurrent sessions allocate the same rule id or edit one leaf | MEDIUM | BL-3 concurrency-safe allocation; leaf edits use the existing version CAS |
| Consumers with large existing corpora cannot adopt | MEDIUM | BL-8 adoption mode (report, not refuse) |
| Lore's technical vocabulary makes the business/implementation line arbitrary | HIGH that it is hard (A2: 8 cases) | BL-11 explicit lore-specific rule, deterministic check |

### Cross-cutting concerns

Privacy: no new personal data; rule and debt entries may name an owner (a role or actor id already stored in the corpus). Ethics / dark patterns: not applicable (no end-user persuasion surface). Accessibility: any new dashboard view (BL-9) meets the dashboard's existing WCAG AA target and keyboard operation. Inclusivity: rule text and ubiquitous-language tables may be written in the team's language (the reference method writes rules in Chinese); ids stay ASCII.
