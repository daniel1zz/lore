# Baseline current values are bound to their source, rendered from the value in effect, and migrated in one approved batch (resolves #409)

## Overview/Goal

A baseline node never states a setting-dependent value as text. It binds each value to its source (a project setting, or a value the product itself governs), and every reader sees the value in effect.

Today 91 baseline documents (72 approved, 19 draft; measured 2026-10-26 with `sqlite3 -readonly`) carry a hand-written "Current values" table with a "Read at" date. The root's conventions ask for exactly that: "Facts that may change with a project's settings are recorded under Current values in the leaf, with the date they were read". Nothing in `packages/*/src` or the tests reads or verifies these tables. `baseline-measure-corpus-usage` states telemetry recording is "on", while `createApp` (packages/lore/src/app.ts:1862, `createTelemetry(config?.telemetry)`) writes no telemetry unless `.lore/config.yaml` opts in (#409).

**Mechanism.** Current values are prose copies of configuration and code, with no binding to their source and no comparison.

**End state.**
- `extra.current_values` holds bindings only: `{ name, who_may_change, source: { governed: <id> } }`, naming an entry of the product's governed-value registry.
- `lore get`, the mirror export and the v9 judge (derived part) render each row with the value in effect, computed by the same function the product uses at its decision point.
- A baseline body containing a "Current values" section is refused at write (exit 4).
- A binding whose source no longer exists fails `--check-baseline` (exit 3).
- The 91 tables are migrated once, inside the ONE change batch shared with #416 (user decision D18). Each node's entry removes its table and carries its bindings as the entry's structured patch. Until a person approves the batch, readers see the written tables and no binding exists, so two values are never shown. On approval, tables and bindings change together. From then on the values are generated by the system and need no approval. The throwaway migration script prints every row whose written value differs from the value in effect, so the reviewer sees each found defect (like #409's) inside the diff set.

Issue: GitHub #409, owned by this spec and bound through its plan. The evaluation spec S-A narrows its own telemetry task to rule text and behaviour, and that task no longer resolves #409. Uses the change batch of `spec-a-baseline-parent-s-children-list-is-rendered-from-the` (#416) and the v9 derived-part mechanism of `spec-each-document-type-declares-which-structured-fields-the` (#414).

## Scope

**In:**
- the governed-value registry in `@lore/core`;
- the runtime decision sites the initial registry covers (telemetry recording first);
- `lore baseline value add|rm` (bindings for values added later; each binding goes through the node's normal per-item review);
- rendering on `lore get`, export and judge;
- the write refusal;
- the integrity finding;
- the 91 tables and the root's conventions sentence, migrated through the shared change batch by a throwaway script (no migration verb ships).

**Out:**
- The 13 non-baseline documents with a "Current values" heading. They are records (9 of the 13 are archived) whose text is history, not a statement of the product.
- Hand-correcting any table: the batch does it, reviewed once.

## Design

### Sources

There is one source kind, a governed id: an id in `GOVERNED_VALUES` (`packages/core/src/governed-values.ts`, pure, browser-safe). Each entry is `{ id, describe, read(config) }`, and the product's own decision site calls the same `read`. Example: `telemetry.recording` is `config.telemetry !== undefined && config.telemetry.enabled !== false ? "on" : "off"`, and `createApp` decides between `JsonlTelemetry` and `NoOpTelemetry` by calling `GOVERNED_VALUES["telemetry.recording"].read(config)`. A setting is a governed entry wrapping the product's own effective-value resolver (for example `trace.retention_days` reads through `resolveTraceRetentionDays`, which applies the section-absent default), and a constant (a file name, a limit) is an entry exporting the constant the code uses. So the decision, the setting resolution and the rendered value are one definition.

### Writing

- `lore baseline value add <node> --name <n> --who <role> --governed <id>` writes one binding through the baseline pending-revision path (one item).
- `lore baseline value rm <node> --name <n>` removes one.
- Unknown id: exit 4, nothing written.
- A create or revision of a baseline node whose body has a heading line `Current values` (levels 2-4, any case) is refused with exit 4, naming `lore baseline value add`. Other document types are not affected.

### Reading

`renderCurrentValues(node, effectiveConfig)` (in `packages/lore/src/service/baseline-generated-parts.ts`, the module shared with #416's children list) is a pure function producing `| Value | In effect | Who may change it | Source |` under `Current values (in effect now)`. It appears on `lore get` text and `--json` (`rendered_current_values`), in the mirror export (as of export time, stated in the heading), and as a v9 derived bundle part.

### Integrity

`--check-baseline` adds the finding `current-value-unbound` for a binding whose id no longer exists (exit 3, BR-447's exit path).

### Migration (throwaway, one batch, user decision D18)

1. `scripts/migrations/baseline-generated-parts.ts`, the one throwaway script shared with #416, holds the whole transform (no migration code ships). It reads every live baseline body. For each "Current values" table it maps each row to a governed id or a `drop: <reason>` using a mapping inside the script. It exits 1 naming any row it cannot account for, and writes nothing in that case.
2. It writes ONE `changes.json`. Per node there is one entry: the body without the table (and without a children list, for parents), plus `patch.current_values` with the bindings. The root's conventions sentence is rewritten to "bound to its source and shown with the value in effect". It prints each row whose written value differs from the value in effect.
3. The task runs `lore batch stage --file changes.json` (#416). Staging and approval both validate every binding in every patch against `GOVERNED_VALUES`; an unknown id refuses the whole batch with exit 4 and nothing is written. A person reviews the one diff set and approves it once. The approval applies every node atomically.
4. Before staging, the task runs the script's own one-time self-checks on a fixture corpus, recorded as evidence on the migration task and deleted with the script. They are not product criteria:
   - one node carrying both a 2-row table and, as a parent, a children table yields ONE entry with both removed and 2 bindings in its patch;
   - while that batch is staged but not approved, the node shows its written table and holds 0 bindings; after approval it shows the generated values and no table.
5. The script and its self-check are deleted by the same task after approval. The permanent end-state oracles are shipped behaviour only: `lore status --check-baseline` (every binding resolves, AC-CV-4) and the write refusal (AC-CV-3), which keeps tables from returning.

### Public interface (falsifier literals, verbatim, once each)

- `baseline-generated-parts.ts`:
  - `value: readBoundValue(binding.source, effectiveConfig)`
  - `const CURRENT_VALUES_HEADING = /^#{2,4}\s+Current values\s*$/im;`
  - `if ((node.extra.current_values ?? []).length === 0) return null;` (end-state meaning: a node with no bindings has no Current values section; an absent field and an empty list render the same)
- `corpus-service.ts`: `if (hasCurrentValuesHeading(nextContent)) return refuseCurrentValuesProse(`.
- `baseline-status.ts`: `if (!isKnownBinding(binding.source)) findings.push(`.
- `export-docs-service.ts`: `const currentValuesSection = renderCurrentValues(doc, effectiveConfig);`.
- `app.ts`: `GOVERNED_VALUES["telemetry.recording"].read(config)`, replacing `createTelemetry(config?.telemetry)` at :1862.
- `change-batch-service.ts`: `applyPatch(node, entry.patch)` (bindings land in the same write as the body), and before any write `if (!isGovernedValueId(binding.source.governed)) return refuseBatch(`: approving a batch whose patch names an unknown governed id is refused (exit 4) and nothing of the batch is applied (BR-1432).

## Design Decisions

Decided with Sequential Thinking (2026-10-26).

| # | Choice | Chosen | Rejected (why) |
|---|---|---|---|
| D1 | What is stored | The binding only; the value is computed at read time | Value plus binding, with a mismatch check: a second copy that is wrong between write and check. Prose plus an AI staleness probe: non-deterministic, and finds drift only after the fact |
| D2 | Source kinds | One kind: a governed registry entry whose `read` is the product's own resolver or decision function | Raw setting keys read with schema defaults: `telemetry.enabled` defaults to `true` while the product writes nothing when the section is absent, so the binding would reproduce #409's lie, and `trace.retention_days` needs `resolveTraceRetentionDays` for the same reason |
| D3 | Keeping prose tables out | Refusal at write (exit 4) | A status scanner reporting prose tables after the fact: a guard on the old design. The write path is where the format is decided |
| D4 | Migration (D18) | Everything migration-specific is throwaway: transform, mapping, run and self-check live in one script deleted after the one approved batch; the permanent oracles are `--check-baseline` and the write refusal | A shipped pure transform with a permanent test (S3 draft): one-time code kept forever, tested only because it ships. Shipped inventory/import verbs (S2 draft): the same, plus about 91 approvals |
| D5 | Where the new rules live | New leaf `baseline-bind-a-current-value-to-its-source` | Modifying BR-447: held by #416's change set (one change set per rule at a time); and binding values is its own verb |
| D6 | What a node renders | Values render only from bindings; a node with no bindings has no Current values section. The pre-approval 'no two values' check is a one-time check on the migration task | A permanent 'no two values during a pending batch' criterion (S4 draft AC-CV-7): it tests a migration-only state, and its fixture needs a body the write refusal forbids |
| D7 | Bindings arriving in a batch | Validated against GOVERNED_VALUES at stage and again at approve; one unknown id refuses the whole batch (exit 4) | Validate only in `lore baseline value add`: a mapping mistake in the migration would store unknown ids, found only later as current-value-unbound |

## Acceptance Criteria

Stored with `lore ac add`; repeated here for readers of the body.

- **AC-CV-1** (BR-1430): a leaf bound to the governed ids `trace.retention_days` and `telemetry.recording` renders the values in effect on `lore get` (text and `--json`): 90 / off with no trace section and no telemetry section; 30 / on after the config sets `trace.retention_days: 30` and `telemetry.enabled: true`. The leaf is not edited in between. Test: `packages/lore/tests/integration/cli/baseline-current-values-render.test.ts`.
- **AC-CV-2** (BR-1430): wiring. `createApp` picks `JsonlTelemetry` exactly when `GOVERNED_VALUES["telemetry.recording"].read(config)` is "on"; a stubbed entry flips the choice. Test: `packages/lore/tests/unit/app/telemetry-governed-value.test.ts`.
- **AC-CV-3** (BR-1431): creating or revising a baseline node whose body has `### Current values` exits 4 naming `lore baseline value add`, and nothing is written. A spec with the same heading is accepted. Test: `packages/lore/tests/integration/cli/baseline-current-values-refusal.test.ts`.
- **AC-CV-4** (BR-1432, BR-447): `lore baseline value add --governed no.such.id` exits 4. A binding whose governed id is removed from the registry makes `lore status --check-baseline` exit 3 with `current-value-unbound`. Test: `packages/lore/tests/integration/status/check-baseline-current-values.test.ts`.
- **AC-CV-5** (BR-1430, BR-960): the mirror export and the v9 judge prompt of a bound leaf show the rendered values. Test: `packages/lore/tests/integration/baseline-current-values-everywhere.test.ts`.
- **AC-CV-6** (BR-1432): `lore batch stage` of a batch whose patch binds an unknown governed id exits 4, naming the node and id, and no batch is created. A batch that became invalid after staging (its registry entry removed) is refused at `lore approve` with exit 4, and no node changes. Test: `packages/lore/tests/integration/cli/change-batch-current-values-validation.bun.test.ts`.
