## 20. Upstream Issue Feedback Loop (consumer-reported defects → corpus)

**Vision (owner, 2026-07-24)**: extend the dogfooding loop beyond this repo — every consuming project's AI agent becomes a defect sensor for Lore itself. Today the "found a lore defect → fix it" loop exists only inside this repository; a consuming project's agent that hits a gate false-deny, a wrong error message, or a crash has no channel back. Distinct from §14 (autonomous feedback on corpus *document lifecycle*) and SPEC-012 telemetry (passive, local-only JSONL): here the **discoverer is the consuming agent itself**, which authors a structured report at the moment of failure with full context in hand; Lore supplies only the channel, the trigger discipline, and the landing workflow. No signal mining, no raw-data exfiltration. **Honest v1 population**: same-machine transport means v1 serves the owner's own multi-project setup (the §17 P1 install base); the metric clock and the cross-machine channel are staged accordingly.

- **F1 Report command** — `lore report-issue` files a structured defect report **directly into a configured upstream corpus**, landing as a **draft ad-hoc task** (SPEC-069 channel: planless, auto-parented to the upstream root PRD, `status: draft` — never pre-approved). Config is an object, both keys required: `feedback.upstream.corpus_path` (**path to the upstream repo root** — the directory shape `lore init` produces, matching `findLoreDbPath`'s contract) + `feedback.upstream.root_prd` (expected root-PRD slug or id — a corpus-identity pin so a stale/copy-pasted path can never misdirect writes into an unrelated corpus; mismatch → `VALIDATION_ERROR` naming both the expected and found root). Structured payload in `extra.issue_report`: `reporter_project`, `reporter_actor` (SPEC-071 actor resolution), `lore_version`, `repro_command`, `expected`, `actual`, `reported_at`. Report body (title + description) is agent-authored prose. Unconfigured → `VALIDATION_ERROR` (exit 4) naming the exact config keys with a literal example — fail loud, no local fallback, no outbox; configuring the upstream IS the consent act (opt-in by construction). **Safety rails (all fail-loud, R-5)**: (a) *no side-effect migration* — filing a report MUST NOT mutate the upstream corpus schema; the upstream `lore.db` schema version (`PRAGMA user_version`) is prechecked BEFORE any store construction that could auto-migrate; mismatch with the reporting binary's expected version → `VALIDATION_ERROR` naming both versions, no write attempted (`lore_version` is thereby an active precondition, not just a passive report field); (b) *SQLite-only upstream in v1* — an upstream with `sync.enabled: true` is rejected with a named error (the consumer holds no valid credential for someone else's Turso replica; cross-machine transport is the P2 home for this); (c) *enforced rate cap* — max 10 open (draft, non-rejected) reports per `reporter_project` in the upstream corpus; exceeded → `VALIDATION_ERROR` listing the existing open reports (advisory dedup surfaces candidates; the cap bounds reviewer blast radius — the 2026-07-07 pollution-incident lesson, now a designed rail rather than an accident report).
- **F2 Trigger surfaces (staged, §14 R1/R2 precedent)** — *Committed v1*: (a) the CLI command itself; (b) MCP tool `lore_report_issue` for MCP-only consumers (explicit `by` required, SPEC-025 convention). *Promoted to committed by owner decision 2026-07-24 (original first-true-positive data-gate overridden — owner wants promotion pressure from day one; the quantified kill criterion below stays armed as the counterweight, its clock now starting at landing)*: (c) *error-path embedding* — gate-deny feeding packs (SPEC-049) and CLI internal-error output append a one-line hint, worded to demand re-verification ("if after re-checking your own input you still judge this a lore defect → `lore report-issue …`"), rendered only when an upstream is configured, and scoped to crash/internal-error + gate-deny classes — never routine usage errors (bad flags), to avoid handing agents a blame-shift escape hatch; (d) *vendored discipline* — the `lore setup` asset tree (§17 P0/P1) gains a standing stanza "suspected lore defect → re-verify, then report upstream" (asset-SSOT conformance oracle keeps repo and installed copies in lockstep). Gating rationale: (c)/(d) broadcast promotion pressure to every install and are costly to recall; they ship on evidence, not hope.
- **F3 Landing workflow** — the report enters the upstream **pending review queue** as a draft ad-hoc task; triage owner = the upstream corpus owner, on the existing `lore pending` maintenance rhythm (no new queue, no hard SLA — the success metric below honestly depends on this rhythm). Approve → visible in `lore ready --adhoc`, enters the claim/evidence/release fix loop. Reject → rejection reason recorded (standard SPEC-005 path). **Advisory dedup**: at write time an FTS5 search over the upstream corpus attaches `possible_duplicates` (top-3 doc ids) to `extra.issue_report` — advisory only, never blocks (SPEC-053 precedent: advisory never decision-driving). **§14 provenance pin**: report-originated tasks carry their foreign origin in `extra.issue_report` and are permanently excluded from §14 auto-stage judgment (assist ceiling) regardless of calibration data — a foreign-authored draft never self-approves.
- **F4 Closure (receipt + outcome learning)** — a successful report appends `{upstream_doc_id, title, at}` to a consumer-side append-only receipt log (`.lore/issue-receipts.jsonl`); `lore report-issue --list` prints the filed history **joined live with each report's current upstream status and, for rejections, the recorded reason** (same-machine read via the same safety-railed path — closure is two-directional: the agent that reports in session N learns in session N+5 that its report was noise, before re-filing the same false positive). SessionStart/bootstrap surfacing is explicitly REJECTED (owner decision 2026-07-24: no new injection into session start); the human-facing visibility surface is the dashboard Issues page (F5).
- **F5 Dashboard Issues surface (owner-committed 2026-07-24)** — triage happens entirely in the dashboard (§13.5 projection family): a nav entry with a count badge of OPEN incoming reports (draft tasks carrying `extra.issue_report`), a dedicated Issues page (list: title / reporter_project / reported_at / possible_duplicates count; detail view rendering the full structured payload), and in-place approve / reject-with-reason via the SPEC-022 cookie-gated write surface — approve makes the report visible in `lore ready --adhoc` (the readyAdhoc review-gate carve-out), reject records the reason the consumer's `report-issue --list` will echo. A compact incoming-reports card also appears on the dashboard home (living-PRD page). No new write semantics: the page composes existing pending-review + approve/reject routes plus one new read projection (open incoming reports).

**Privacy/consent boundary**: the report body is agent-authored, human-reviewable text — nothing is auto-captured beyond `lore_version` + the explicitly passed `repro_command`; no corpus content, no environment dump. The consuming project's corpus is never read by the upstream.

**Test discipline (binding on the landing spec)**: cross-corpus tests construct **twin throwaway corpora** (`mkdtemp` + `lore init` × 2: consumer with `feedback.upstream.*` set, upstream seeded with a root PRD) and run under `bun test` (`.bun.test.ts` — both sides touch `SQLiteStore`); the no-upstream-configured output of every existing error surface must be byte-identical to the pre-§20 baseline (regression pin).

**Success metrics**: clock starts at the first consuming project configuring `feedback.upstream.*` (not at feature landing — adoption is exogenous to the mechanism); from that point: ≥1 true defect reported AND fixed through the loop (report → approved → evidence → released) within 1 month; review-rejected ratio per `reporter_project` tracked at each `lore assess` touching report-originated tasks; 0 silent failures across the unconfigured/misconfigured/version-skew/rate-cap paths (all oracle-tested exits).

**Kill criterion (§8 family, quantified)**: F2(c)/(d) hints — if within 2 months of their landing the loop records 0 additional true positives AND ≥5 review-rejected reports, the hints/stanza are withdrawn (asset-tree removal), reverting to bare command + MCP tool. If 6 months after landing no consuming project has configured an upstream at all, §20 is re-opened with a revert-and-ADR trigger (same evidence standard as §18).

**Non-goals**: no cross-machine transport in v1 (HTTP push + remote status query + credentialed sync-upstream = P2, gated on actual multi-machine demand); no auto-approved tasks (draft + human review, always); no hard content dedup (advisory only; the rate cap bounds volume, not similarity); no general inter-project message bus (defect reports only); no automatic issue creation from telemetry (SPEC-012 stays passive/local); no upstream schema auto-migration, ever (R-5 invariant).
