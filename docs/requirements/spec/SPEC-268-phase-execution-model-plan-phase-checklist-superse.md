## 18. Phase Execution Model (plan → phase → checklist; supersedes fine-grained task pre-decomposition)

**Vision (owner, 2026-07-19)**: the execution unit becomes the *phase* — a cohesive, session-sized, independently verifiable slice — replacing speculative fine-grained task pre-decomposition. Empirical driver: the last 7 implementation plans (SPEC-047/049/050/051/053/054/055) all degenerated to exactly 1 task per plan — the task layer's *planning* granularity stopped earning its keep, while its *mechanical* layer (claim lease, file anchors, evidence trail) remains load-bearing. The restructure moves the mechanics up one level and dissolves the speculative granularity into a fluid, model-owned in-phase layer. **Rival hypothesis recorded (not yet falsified)**: the 1-task degeneration may reflect small, well-scoped specs rather than a failed task layer — in which case phases will degenerate to 1-per-plan identically. The model therefore self-diagnoses: phases-per-plan distribution is tracked at each `lore assess`; clustering at 1 across 7 consecutive post-migration plans re-opens this section with a revert-and-ADR trigger (the same evidence standard applied to the layer it replaces). Industry-shape evidence (tier-tagged, 2026-07-19; a *structurally partial* analogy — the fluid-layer/contract-layer split matches, the trust allocation does not, since all three retain a durable per-unit artifact where Lore's `track` is deliberately non-authoritative): Kiro spec-driven tasks reference EARS acceptance criteria rather than restating them; GitHub PRs pair informational description checkboxes with oracle-bound required status checks; Scrum separates fluid sprint tasks from the fixed Definition of Done.

- **P1 Phase absorbs the task mechanics** — `claim` lease, `file_anchors` (+ the anchor-overlap gate, checkpoint renamed task-claim → phase-claim, predicates reused unchanged), and append-only `verification_evidence` move from task to phase. *Zod schema shapes* carry over unchanged (SPEC-025/042 semantics, one level up); the *service surface* does NOT — this is a coordinated multi-service rename, honestly scoped here: `TaskWorkflowService.resolveTask` (type-literal check), `CorpusService.getPlanBundle` (the `tasks` field + its consumers `AIProviderService.assessPlan` and `VerifyRunnerService.resolveTargetTask`), anchor-grammar split (`rejectHashInTaskAnchors`), CLI/MCP badges and tools, `lore tree` rendering, and the `workflow.gates."task-claim"` config key (renamed with a read-side alias for existing corpora, deprecation logged loud). The owning spec's design pass enumerates the full consumer list before task authoring.
- **P2 Three in-phase components, hard/soft split by trust source**:
  - `ac_scope: string[]` — the phase's contract projection: the subset of the parent spec's AC ids this phase is responsible for (SPEC-040 plan-`ac_scope` precedent; membership validated against the spec at write time). Acceptance substance lives ONLY in spec ACs — a checklist item never restates an AC, it references one.
  - `checklist` — local gate items beneath spec granularity, each bound `script` (attested via the SPEC-039 trusted runner; §M2 command-provenance approval + env allowlist inherited unchanged) or `manual` ({by, at} sign-off; editing the statement voids the sign-off). No stored `done` on computable kinds. Dropping an item requires {by, at, reason} and is named loudly at phase close and in `lore assess`.
  - `track` — informational-only work log (id / statement / status / note): stable ids for handoff reference ("continue from T-4"), mid-execution discoveries land in notes. NEVER consulted by completion computation — the price of its total mutation freedom (Self-Verification Paradox: model self-reports are not oracles).
- **P3 Completion is computed, never stored** — `phase done := every ac_scope AC has attested pass evidence ∧ every non-dropped checklist item green`. No stored phase state machine at all (pending/active/done derive from claim + checklist + evidence); the "readiness is computed" invariant extends to completion. Whole-phase cancellation walks the existing `lore invalidate` path, not a new field. Four invariants close the formula's edges: (a) **anti-vacuous** — `ac_scope` empty ∧ every checklist item dropped ⇒ NOT done; it reports a distinct `vacuous` state with a loud badge/exit code, never silent completion; (b) **scope-freeze** — once the first evidence entry lands, `ac_scope` edits are restricted to additive-with-revalidation (removal of an already-evidenced id is refused, naming `lore invalidate` for genuine descoping); (c) **overrun is normal** — a phase whose claim expires mid-checklist (multi-session phase) simply re-claims at next seat entry; checklist/evidence state is on the doc, nothing orphans (the S2 handoff + P4 feed carry continuity); (d) **honest trust label** — `manual` checklist items are self-attested sign-offs, not oracle-verified; every completion surface renders them visually distinct from attested items (computed ≠ uniformly verified, stated rather than implied). Human trust surface: `lore phase status <phase>` (CLI scorecard: N/M attested, checklist state, dropped items named) and the dashboard phase view (§13.5 projection family) are the PM-facing read of the same computation.
- **P4 Layered context injection** — `lore feed phase-start <phase>`: T1 contract layer verbatim (phase goal / track / checklist / anchors + `ac_scope` AC texts + the PRD requirements they cover via SPEC-055 `requirement_refs`), T2 chain layer summarized (plan, sibling-phase states, spec slice, latest handoff), T3 memory layer as pointers only (1-hop linked ADR/knowledge, top-N by link-weight × recency, SPEC-043/044 hygiene-filtered — invalidated excluded, stale badged). Per-section char budgets with recorded truncation (`ai.assess.*` precedent); zero overlap with SessionStart-hook injection (channel-unification lesson, 2026-07-17).
- **P5 Metadata admission rule** (recorded here as the phase schema's constitution, applies corpus-wide): a field enters the typed schema the day a pure function reads it (gate predicate / feed selector / coverage computation / renderer) — never speculatively; until then it lives in `extra` passthrough (the `prdExtraSchema`→SPEC-055 promotion precedent). Phase v1 carries exactly: `kind` (single enum backend|frontend|fullstack|infra|docs — consumed by feed templates + verification profiles), `ac_scope`, `checklist`, `track`, `file_anchors`, plus mechanism-owned `claim`/`verification_evidence`. Explicitly rejected: open tag arrays (`types[]`) — the disciplined equivalent (`labels` + selectors, k8s pattern) is admitted only WITH the §19 hooks system, which is its consumer.
- **P6 Verification profiles (companion, separable)** — per-`spec_kind` oracle-coverage floors (e.g. `design` → ≥1 e2e/browser-bound AC + plan requires UAT; `feature`/`tech` → ≥1 test-bound AC) as a deterministic spec-promote predicate + phase-checklist seeding templates injected at `feed phase-start`; deliberately thin (1-2 hard requirements per profile), richer nuance stays AI-advisory (SPEC-053 channel). Works on the current task model too — lands as its own spec.
- **P7 One-shot migration** — existing task docs merge into phase docs (grouped by `extra.phase` where declared, else one phase per task), `--dry-run` first, append-only version history preserved (zero data loss, G12 — oracle: pre/post reconciliation counts docs + evidence entries + claims and diffs field-by-field). Edge rules stated up front, not discovered mid-run: multiple fresh claims collapsing into one phase-group → newest fresh claim wins the phase `claim`, displaced holders recorded as `track` notes (loud in the migration report); merged `verification_evidence` arrays exceeding the 50-entry cap → cap is per-source-task preserved via an evidence `origin` marker, never truncated; SPEC-023's `extra.legacy_phase` residue is honored as a grouping key fallback; declared plan phases with zero referencing tasks become empty phase docs (declared intent is data, not noise). The sweep is idempotent and resumable — a partial-failure re-run skips already-migrated groups by construction, verified by running the migration twice in the fixture suite.

Non-goals: no stored phase status field; no human-dimension estimation fields (person-days are banned by team constitution); no open tag arrays; intra-phase parallel subagent dispatch stays session-orchestrated (corpus gates govern cross-session concurrency only — one *claiming* session per phase). This is NOT a parallelism regression: plan-level concurrency = multiple phases claimed by different sessions (anchor-gated exactly as tasks were); within a claimed phase, the holding session dispatches parallel subagent worktrees under its own orchestration, unchanged from today's CLAUDE.md discipline — the corpus-visible mutex simply sits at the phase boundary, where the sessions actually are.

Delivery & sequencing: three landing specs through the §13 output contract — phase model (schema + services + gates + feed + migration), seat model (§15 S4: `lore seat` + seat-aware resume), verification profiles (P6). The first two are independent of each other; the third is independent of both. §17 coordination: the task→phase rename touches the vendored `assets/` skill/hook tree (task-claim references) — the phase-model spec lands its asset resync in the SAME change as the rename (assets-ssot conformance oracle keeps the two in lockstep), and the rename does not ship between §17 P1 and P2 cuts mid-adoption without a coordinated asset release. Kill criterion (§8 family): the §18 intro's phases-per-plan re-open trigger AND the §15 S4 seat cost counter-metric each carry a revert-and-ADR path — a failed bet is reversed by the same evidence standard that committed it.

**Closure-loop hardening (landed 2026-07-28, spec-plan-closure-must-be-loud-terminality-divergence-silent)**: the execution model had no closed loop between task-level completion and plan-level state. `lore done` walks a task to archived and never touches its plan; the plan-close checkpoint (and therefore SPEC-069's attestationFloor) fires only on the plan doc's own status transition. A session could archive every task, run `lore assess`, and report closure while the plan sat non-terminal and its gate had never evaluated it — observed live, and a corpus scan then found the same divergence on five unrelated plans, i.e. the loop had never closed for anyone. Three deliberate speech-not-guessing fixes: (i) TreeCheckService gains a `plan-terminality` drift (plan non-terminal while at least one child task exists and ALL are terminal), surfaced by `lore status --check-tree` — already run by hooks/pre-push, so it arms for every consumer without a hook edit — and deliberately NOT auto-fixable, since transitioning a plan inside a repair command would fire a governance gate the operator never invoked; (ii) `lore done` ANNOUNCES when it archives a plan's last non-terminal task, naming the plan and the literal close command, but performs no plan write — plan-close may legitimately deny, and done must not fail for reasons unrelated to its own task; (iii) the approved-to-draft auto-demotion that a content edit triggers is now reported on every surface, because the CLOSE-phase discipline of appending a closure record to an approved plan was itself the silent de-promotion. A fourth fix is not about closure but about honesty at the same gate: absent GateContext fields no longer render as asserted corpus facts (verifyReachability gained an explicit unknown outcome distinct from known-false), after a deny pack told an operator a plan "has no spec-tier ancestor at all" — untrue, and both remedies it offered would have corrupted a correct corpus.
