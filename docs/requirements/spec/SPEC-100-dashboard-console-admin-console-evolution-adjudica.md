## 21. Dashboard Console (admin-console evolution; adjudication workbench first)

**Vision (owner, 2026-07-24)**: the dashboard's positioning broadens from the §13.5 "PRD projection + adjudication surface" into the team's **general admin console** over the corpus — full CRUD affordances and, staged, execution-operation surfaces. **Why now**: the v0.12 §20 round committed the dashboard as THE issue-triage channel (F5) while explicitly deferring broader dashboard planning to its own product round; this is that round, triggered by the owner's 2026-07-24 expansion directive plus the SPEC-074 landing making the dashboard an active daily surface. Owner explicitly overruled the 6-role ideation consensus recommendation of a narrower "adjudication cockpit" (dissent + rationale recorded in `knowledge-ideation-dashboard-capability-expansion-6-role`; 4/6 roles warned of dual-write-surface consistency cost). **Structural bound that makes the console positioning safe**: `GateEnforcer` runs at the service layer, so every dashboard write already passes the same deterministic gates as CLI/MCP — console breadth can never become gate bypass; the residual risk is UX-affordance design, and each new write surface still pays the SPEC-062-class consistency tax, which is why batches are staged and telemetry-gated. Batch ordering is itself an owner decision (D2): the ideation consensus ranked the execution view first; owner chose the adjudication workbench first — recorded, not hidden. §13.5 (Home = resolved living PRD, SPEC-033) is **unchanged** — any home-identity revision (e.g. inbox-first) requires an explicit owner reversal, never a silent redesign. The console serves all human collaborators (3-5 people), not only the owner: every F1 surface is cookie-session-scoped with actor attribution through the existing audit trail, no owner-only affordances.

- **F1 Adjudication workbench (first batch, committed)** — adjudication becomes evidence-grounded on one screen:
  - (a) **Evidence/AC tab on doc detail**: task docs render the `extra.verification_evidence` timeline (result, oracle type, command, attested-vs-self-reported trust label — the SPEC-039 distinction made visual, `output_tail` in a monospace terminal-style panel); spec docs render the structured AC list (SPEC-038) with per-AC coverage state derived from evidence `ac_ref` joins; plan docs surface the plan-wide attestation ratio (SPEC-069 `attestationFloor` input). **Named backend deliverable**: a read-only aggregation surface (service method + HTTP route) for AC-coverage and attestation-ratio — today these are computed only transiently inside gate predicates; no standing query path exists. Read-only projection, no new write semantics. Boundary states are first-class: zero evidence entries and spec-without-ACs render explicit empty states (never blank/crash).
  - (b) **Adjudication context panel**: on any doc carrying pending review, the approve/reject controls render adjacent to (a)'s evidence summary + AC coverage state — zero additional navigation steps between evidence and verdict. A layout spike on the existing DocDetail component tree is the first task of the landing plan (feasibility before commitment — if the same-screen constraint proves unachievable, the fallback of a one-click evidence popover requires owner sign-off as a requirement change to R-8).
  - (c) **Keyboard-first triage**: the pending/triage queue operable with keyboard alone — `j`/`k` selection, `a` approve, `x` reject-with-reason modal, `e` expand blocking questions, `o` open doc detail (Linear-inbox pattern). Keyboard shortcuts are suppressed whenever an editable element (CodeMirror editor, input, textarea) holds focus — keystrokes pass through to the editor, never trigger adjudication. Calibration capture (SPEC-033 §2.1 hoisted hook) fires identically for keyboard and pointer paths.
  - (d) **Judgment drill-down**: `JudgmentBadge` gains an expansion revealing the structured judgment record — decision, confidence, per-dimension qualitative reasons (`reasons[]: {dimension, finding}` — the actual SPEC-034 data shape; there are NO numeric per-dimension scores and none are invented), blocking questions, prompt_version — so the human sees WHY before ruling. Docs with no judgment record (pre-SPEC-034 or never judged) render the existing "unreviewed" state with no drill-down affordance, never an error.
- **F2 Usage telemetry (ships WITH F1 — owner decision D3)**: route-level view events (`route_id`, `doc_type` when applicable, timestamp, session marker) recorded to the existing SPEC-012 local JSONL sink under the existing opt-in config. **Named backend deliverable**: telemetry writes are server-side (the browser has no fs access — Node-free invariant), so F2 includes one cookie-gated ingestion route in the `/api/dashboard/*` family. Sink write failure is logged server-side and never surfaces to the UI as an error (deliberate, documented exception to fail-loud: observability must not break the observed surface). No new sink, no remote export, no doc-content capture. Purpose: replace assumption with measurement (ideation A1) before later batches commit — and, via `route_id`, attribute demand to specific surfaces (F1 vs F3) so the kill criterion can distinguish "workbench unused" from "wrong batch shipped first".
- **F3 Execution read surface (committed second batch; design round required before build)**: `GET /api/ready/:plan` already exists (SPEC-037 D1) — the F3 deliverable is the missing **UI layer** over it plus its gaps: read-only views for claims with TTL countdown, derived sessions, anchor conflicts, evidence timelines, phase progress (§18 `lore phase status` family), with any additional read routes spec-pinned (SPEC-036 shape-drift lesson). Also fixes the stale `packages/dashboard/CLAUDE.md` claim that the ready route doesn't exist. Read-only: execution verbs stay out of this batch.
- **F4 Staged candidates (admission-gated; §18 P5 rule — no consumer, no commitment)**: each candidate carries its admission trigger: (i) production build + single-binary embed — admitted after a spike measures the real `dist/lore` size delta (§17 P3 family); (ii) home-page evolution toward attention-feed/inbox — requires the §13.5 owner reversal; (iii) **execution-verb writes** (claim/release/evidence buttons) — requires BOTH an independent, explicit owner reversal of the "execution verbs stay CLI-only" ideation consensus (a separate decision from D1, same standard as the home-identity reversal) AND F2 telemetry showing ≥3 F3-route sessions/week over 4 consecutive weeks; (iv) calibration/attestation trust panel + read-only share mode — admitted after F1 lands; share mode additionally requires a redaction pass before any external exposure; (v) corpus DAG graph view — admitted on demand evidence from F2 route data. Anything without its trigger fired stays out of every landing spec.

**Privacy/consent boundary**: F2 telemetry is local JSONL under the existing opt-in flag; no route data leaves the machine; no doc content is captured in events.

**Launch oracles (pre-release, CI-verifiable — distinct from the KPIs below)**: (1) component tests prove the full keyboard loop with keyboard-only event dispatch, including the editor-focus suppression case; (2) component tests prove the boundary states — zero evidence, spec without ACs, missing judgment record, telemetry-disabled zero-write, sink-write-failure invisible to UI; (3) Playwright e2e proves an adjudication performed with the evidence panel visible on the same screen writes the same calibration record a CLI adjudication would.

**Post-launch KPIs (operational, NOT CI gates; thresholds provisional — n=1 human baseline, to be recalibrated against the first month of real F2 data)**: (1) audit trail records ≥5 dashboard-surface adjudications (`http_cookie`) with paired calibration captures within 4 weeks of F1 landing; (2) dashboard sessions/day computable from the JSONL sink within 2 weeks of landing.

**Kill criterion (§8 family)**: if 4 consecutive weeks of F2 telemetry after F1 lands show <3 dashboard sessions/week (threshold provisional, same n=1 caveat), F3+ batches freeze pending an owner re-decision — and the freeze review MUST consult per-`route_id` data plus the two known confounds before attributing cause: (a) the two-process dev-launch friction (unresolved in this round; a low session count may measure launch friction, not feature value — the F4(i) spike is the counterpart), (b) which routes were actually visited. The F1 surfaces themselves remain (sunk, small, harmless).

**Non-goals**: no CLI feature parity for its own sake — the console grows only surfaces where a UI has structural leverage (timelines, matrices, drill-downs, graphs); no hosted/multi-tenant dashboard in this round (§17 P2+ home); no SSE/live push until an explicit evidence-visibility latency SLA is decided (polling stays the default); no home-page identity change in this round; no numeric judgment scores invented where the data model has none.
