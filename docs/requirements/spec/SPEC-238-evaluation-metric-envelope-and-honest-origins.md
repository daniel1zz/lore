## Overview/Goal

Every evaluation number lore prints must be unable to lie silently (OST O1, the root need under every other question). Today 94% of the "human" calibration rows are agent approvals (#406), the baseline says telemetry is on while the code records none (#409), and test runs left 81 runs in the repo corpus (#411; measured 2026-10-26, all never ended, none with an attributed write), which the five envelope fields read as ordinary agent runs (plan 1 experiment O1-S2, path B: stop and re-review, `knowledge-experiment-o1-honesty-of-the-evaluation-data`). This spec introduces the `lore metrics` command and the envelope every metric is printed through: sample size, window, newest fact read, origin split, and a status that separates "no data" and "too few" from a real value. It answers nothing on its own; S-B to S-D register metrics into it and S-E colours them.

Staged requirements: R-29 (all 11 questions, answered / explicit no_data), R-30 (origin), R-31 (envelope and status); the #411 and #409 fixes are tasks resolving those issues (R-32, R-33 withdrawn at S3) in `knowledge-evaluation-system-staged-prd-requirements`. Baseline: leaf `baseline-read-the-evaluation-metrics` (proposed rules below), modified rules BR-555, BR-993, BR-1013, a proposed rule on `baseline-attribute-work-to-a-run`.

## Scope

- `lore metrics [--question A..K] [--since <iso>] [--until <iso>] [--json]`: read-only; lists the 11 questions A–K, each with its metrics; text and JSON carry the same values.
- The metric envelope: `{ id, question, value, unit, status: ok|insufficient|no_data, no_data_cause?: source_absent|source_off, reason?, sample_size, window: {from, to}, newest_fact_at, origin_counts: {human, agent, machine_event, unknown}, source, action_line, baseline: {value, window, sample_size, epoch} | null }`; per question `answered | explicit_no_data | unanswered` plus the three totals. A present but empty source is `insufficient` (n = 0), never no_data (BR-1382). `baseline` is read as stored from the baselines S-E records (S-E BR-1405); this read path never writes one (BR-1384).
- Action line: every metric carries `action_line`, one fixed sentence saying what to do when it turns yellow or red, written with the metric's definition (A-D13).
- Origin: stored with every fact at write time from the write's attributed party (BR-1055, all four parties): harness run → agent; HTTP bearer key → agent; human session → human; dashboard login → human; rows the product's own recorders write with no party (outcome sweep, check outcome recording, hook outcome intake) → machine-event. A one-time upgrade step writes the origin of every existing row (the resolved party, else `unknown`; runs the test-run repair matched get `unknown` although their party resolves to agent, BR-1383, BR-1455); metrics read only the stored field (BR-1383).
- `lore calibration --stats` groups additionally split by origin (BR-555 modified), so its agreement rate is never AI-vs-AI pooled with human rows.
- #409: the baseline is corrected to the code's deliberate opt-in (AC-C3, no file side effect by default): BR-993 and BR-1013 now say "when the project has switched telemetry on (off by default)". This spec owns only those two rules' text and the opt-in behaviour AC-EM-5 checks; the Current values rows and where the telemetry setting is governed belong to the #409 governance spec, which resolves #409 (crossdoc 1).
- #411: the root cause of test runs reaching the checkout's own corpus is fixed at the write site located in plan phase 1 (BR-1386, AC-EM-6), so no new test run reaches a real corpus.
- Test-run repair (BR-1455): the same one-time upgrade ENDS each run that meets all three facts (session id of the form `test-session-<epoch ms>-<random suffix>`, never ended, nothing attributed to it in versions or audit) with end reason `test-run-repair`, stores its origin `unknown` and writes one audit entry per run; rows are kept. It re-reads the schema version inside the upgrade's write lock (BEGIN IMMEDIATE) and selects only unended runs, so a repaired row no longer matches and concurrent or repeated upgrades repair each run once. On this repository it ends the 81 leaked runs, so question D's open-run count no longer includes them and its origin split shows them as unknown.

## Out of scope

- The individual metrics of questions A–K: each slice (S-B, S-C, S-D) registers its question's metrics when it lands. Until then the question is listed as `unanswered` with the reason `no metric registered` (A-D12); no placeholder metric and no extra state exist. This slice's criteria exercise the envelope through the registry's test seam with fixture metrics.
- Threshold colours (S-E).
- Guessing a legacy row's origin from a claimed name: the upgrade step stores `unknown` when the party does not resolve.

## Design Decisions

| # | Decision | Chosen | Rejected and why |
|---|---|---|---|
| A-D1 | Where the envelope and command live | In this slice (O1), before any metric | Putting the command in S-E (surface last): every metric AC in S-B..S-D needs an observable read path, and honesty is a property of the envelope, not of the surface |
| A-D2 | How empty is told apart from zero | `status` field plus `value: null` and a `reason` naming the source | `value: null` alone: text output cannot show the difference and a consumer reading `value` treats null as 0 |

| A-D4 | Legacy rows (review rev2-1) | A one-time upgrade step stores origin for every existing row (resolved party, else `unknown`); one stored field, one read path | Classifying legacy rows when read (a permanent second, legacy-only code path); dropping them (silent filtering) |
| A-D5 | #409 direction | Correct the baseline to opt-in | Flip code to default-on: violates AC-C3 (no file side effect without opt-in) and adds a file write to every consumer |
| A-D6 | #411 | Fixed only at the write site the phase-1 experiment locates (BR-1386); if it is not located, plan 1 stops and this spec is re-reviewed. | A-D17 | The 81 test runs already in this corpus (O1-S2 path B; revised in S3 round 2, design 3, eng 7) | The one-time audited upgrade repair ends them (end reason `test-run-repair`) and stores origin `unknown`; four origins only; identification needs all three facts (test-session id form, never ended, no attributed version or audit entry; 81 of 81 meet them, a never-ended UUID-session run does not); version re-read inside the write lock and a selection that excludes repaired rows make it concurrency-safe and idempotent; BR-1386 and AC-EM-6 stop new leaks | A fifth origin `test` (round 1): a legacy bucket only the repair ever writes, the same pattern A-D12 rejected for not_built, and it left the runs open so D's open-run count stayed inflated; a provenance mark written at registration (the test environment variable was unarmed in all 81 leaks, O1-S3); deleting the rows (the count drops with only an audit row as trace); a read-time filter by session id (A-D6); identifying by session id alone (one name-like fact, BR-1055) |
| A-D18 | Origin of the runs the repair ends (S3 round 3) | `unknown`, stated as an explicit exception in BR-1383 and BR-1455: their party resolves to agent (registered as harness runs), but they never acted as an agent party (no version or audit entry) | `agent` as the resolved party (counts 81 test registrations as agent work in D's origin split); a fifth origin (rejected in A-D17) |

| A-D7 | Read path | Metrics are computed on read; the command writes nothing | Snapshot rows written per read (needs a writer under concurrency and turns a read into a write) |
| A-D12 | Questions whose slice has not landed (review rev-1, rev2-1) | Listed as `unanswered` with reason `no metric registered`; BR-1385 defines only answered / explicit no_data / unanswered | A `not_built` state (a transitional state written into the permanent contract); placeholder no_data metrics (misuse no_data) |
| A-D15 | How no_data says why (review rev3-1) | Structured `no_data_cause`: `source_absent` or `source_off`; a present but empty source is `insufficient` with n = 0; the question roll-up reads the cause field | Free-text reason only (the roll-up would parse prose); a third cause `empty` under no_data (empty is a small sample, not a missing source) |
| A-D16 | Where a metric's baseline comes from (review rev3-1) | A read-only `baseline` field showing the stored baseline defined and recorded by S-E (BR-1405, its own command); this spec only reads it | Recording baselines on the read path (a write, contradicting BR-1384); leaving "recorded baseline" undefined in this spec |
| A-D14 | Where this slice's criteria get metrics (review rev2-1) | Fixture metrics through the registry's test seam | Moving AC-EM-1/AC-EM-2 to the slice that registers question A (the envelope would land unverified) |
| A-D13 | What the action line is | `action_line` (named for yellow and red, not only red): one fixed sentence authored with each metric's definition in the metric registry by the slice that builds the metric, reviewed with that slice's spec; computed nothing, stored nowhere in the corpus | Free text stored in config (editable per project, unreviewed); no action line (a red metric would tell an agent nothing to do) |
| A-D8 | Bearer keys and dashboard logins (S3 crossdoc 5) | Bearer key → agent, dashboard login → human; machine-event names its three recorders | Bearer key → unknown (it is a known party under BR-1055; unknown would hide it); "machine-event = any write with no party" (contradicts BR-1055: every write has a party) |
| A-D9 | When a question counts as answered (S3 EU2, crossdoc 6) | answered = ≥1 metric ok with a recorded baseline (S-E's target attainment is shown beside it and does not decide answered); explicit no_data = every metric no_data with a stated cause, source_absent or source_off (BR-1385, AC-EM-4); otherwise unanswered | Counting every empty question as explicit no_data (an empty corpus would score 11/11); requiring a baseline for every metric (unreachable while H has no source) |
| A-D10 | #409 / #411 in the requirement list (S3 PS1) | Withdrawn R-32, R-33; kept as issue-resolving tasks whose oracles are AC-EM-5, AC-EM-6 | Keeping them as product requirements (they are defects, not product behaviour) |
| A-D11 | Proof that reading writes nothing (S3 eng 12) | sha256 of the database and WAL plus the .lore file list, byte-identical | Row counts only (miss WAL checkpoints and cache files) |

## Acceptance Criteria

A pre-registered branch never weakens a criterion: a branch that would need different behaviour is stop-and-re-review (plan 1 Decisions Log).
