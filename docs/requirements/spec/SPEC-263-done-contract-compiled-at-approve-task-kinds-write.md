# Done-contract compiled at approve, task kinds, write sets and start/finish (stage 1)

## Overview/Goal

A task's done-requirements are known when it is approved but surface only at `lore done`. Stage 1 makes `lore approve <task>` compile and store them as the task's **done-contract**; gives every task a kind (`code | check | corpus`); adds the implementer verbs `lore start` and `lore finish`; lets a claim declare the files it will touch (its **write set**); makes `lore done` check the stored contract; and migrates in-flight tasks. Decisions: D28 to D32, `adr-stage-1-the-done-contract-is-compiled-at-approve-with-task` (this spec implements it). Evidence: issue #475. Each behaviour is stated once, in its acceptance criterion; this text gives the reasons, the invariants and the decisions, and cites criteria by id. Landing is unchanged in stage 1: `lore integrate`, then `lore done`.

## Scope

In scope: the stored contract and its compile (AC-DCS1-1 to AC-DCS1-3, AC-DCS1-9); kinds (AC-DCS1-4, AC-DCS1-19 to AC-DCS1-21); the red declaration and the retired surfaces (AC-DCS1-5, AC-DCS1-6); `lore done` and plan close reading the contract (AC-DCS1-7, AC-DCS1-8); the claim write set (AC-DCS1-10 to AC-DCS1-12); `start` (AC-DCS1-13, AC-DCS1-14); `finish` (AC-DCS1-15 to AC-DCS1-18, AC-DCS1-20); migration (AC-DCS1-22, AC-DCS1-23); shipped text (AC-DCS1-24); the two live-corpus proofs of the plan close and the live migration (AC-DCS1-25, AC-DCS1-26).

Out of scope (stage 2, drafted after stage 1 lands; no criteria here): `lore dispatch`, `lore land`, automatic plan close and the removal of close tasks, the execution log, the drift check at start, the shipped standing dispatch rules. Stage 1 keeps close tasks. Locked tasks are never reopened (decision T7 below). The CLI is the only command surface (the MCP server was removed from main by commit 191c6822); the HTTP routes inherit the service-level guards.

## Design

**Contract.** `extra.done_contract` is written by these paths and no other: the compile (approve; the approve of an approved task that has no contract yet, AC-DCS1-5; the migration, AC-DCS1-23) and, afterwards, `lore release`, a run end and `finish`, which only add test oracles to `added_oracles` (AC-DCS1-11, AC-DCS1-15); `lore done` derives the additions again but writes nothing. `lore set` cannot write it (AC-DCS1-4). It holds: `compiled_at_commit` (tip of the base branch at compile), `kind`, `base_branch` (the plan's integration branch, else `main`; it must exist at compile), `oracles`, `install`, `red_required`, `red_waiver_reason`, `landing_route` (`main`, `integration-branch`, or `none` for check and corpus), `new_symbols`, `added_oracles`. Oracle ids are `ac:<AC-id>` (the verify command of each live script-mode AC in `ac_scope`), `test:<path>` (an unfiltered whole-file run of each anchored test file), `typecheck`, and, for a corpus task only, `corpus:files-unchanged` (proved by `finish` itself, AC-DCS1-19, AC-DCS1-21). The three commands the contract runs come from `.lore/config.yaml` keys `workflow.done_contract.install`, `.typecheck` and `.test_file` (a template with `{file}`); a missing key is a compile cause, not a skipped step (AC-DCS1-2, AC-DCS1-9). This repository sets `bun install --frozen-lockfile`, `bun run typecheck` and `bun run test:file {file}`. The three commands are copied into the contract at approve, so a later config change reaches an in-flight task only through stage 2's drift check; the `ac:` oracles are the exception, resolved by AC id to the AC's current command (AC-DCS1-7, AC-DCS1-16).

**Kinds.** A `code` task changes files and is worked in a claimed worktree. A `check` task proves something at main's head and changes nothing. A `corpus` task changes the corpus only through lore commands, never files (#472). Both are completed by `lore finish` in the shared checkout and are never claimed (AC-DCS1-19, AC-DCS1-21). The shared checkout is the main working copy; it is always detached (BR-1342), so `finish` tests "HEAD equals the tip of `main` and the tree is clean", never a branch name. They differ in purpose and in oracles: `check` is read-only proof and needs at least one script-mode AC oracle (cause `no-oracle` otherwise); `corpus` runs its lore commands before `finish`, which proves the result by its AC oracles and by `corpus:files-unchanged`, so a corpus task with no script-mode AC (a plan close, a migration run) still has a legitimate executor (#472). The contract is the only copy later verbs read; `extra.kind` is immutable once approved (AC-DCS1-4).

**Write set.** A claim carries a write set: the files it will touch, by default all the task's approved anchors (AC-DCS1-10). It judges overlap only, in both overlap computations: the claim gate and the ready report's anchor conflicts. The oracle set is the contract plus the test files the write set adds; it never shrinks (ledger D30(2), AC-DCS1-11). A write-set test file adds an oracle only when the claim's branch changed it, so a mistaken declaration binds nothing and a directory entry still reaches every test file the branch touched under it. The additions are written by release and run end (AC-DCS1-11) and by `finish` (AC-DCS1-15), because a claim released without `finish` would otherwise lose them. The edit hook's declarations extend the claim's write set, not the task's anchors, so the 50-anchor cap applies only to approved anchors (AC-DCS1-12). The logic lives in `service/edit-scope.ts` (`declareEditPath`, `readEditScope`).

**Red.** A code task requires a red run unless the approver declares `--red-waiver "<reason>"` (ledger D30(3), AC-DCS1-5). The flag is not named `--no-red`: the argument parser reads any `--no-<x>` as a negation and drops the value after it (the reason `done.ts` already records for `--declare-no-new-tests`), so AC-DCS1-5 reads the stored reason back. `red_required` is derived from kind and that declaration; `finish` and `done` never change it. A migrated task that already worked without a red row is listed with the exact correction command (AC-DCS1-22).

**Claim lease.** `finish` reads HEAD before it runs anything and binds itself to that commit: it runs the oracles at it, stamps the rows with it, and stores it as `finished_commit` (a write after HEAD moved or the tree went dirty is exit 5, AC-DCS1-15, AC-DCS1-16). `finish` keeps the claim, marked finished, until `lore done` releases it, so another run cannot claim the task between `finish` and landing. A claim is finished only while its branch tip equals `finished_commit`; a later commit makes it an ordinary claim again, and `lore done` of a task whose claim recorded a `finished_commit` refuses `finish-stale` (exit 4, second in BR-209's order, naming `lore finish`) while the tip of the task's own branch (once gone, the tip recorded for its claim at release or landing; none recorded is `finish-tip-unknown`, never a guess) is not that commit, never comparing against the integration or landing commit, so a commit made after `finish` never lands untested (AC-DCS1-18). A task that never ran `finish` is judged by its rows as before. A finished claim does not count in overlap judgement only when its commit is an ancestor of the claiming task's base tip, that is, when its work is already in the base the next task builds on (otherwise chained tasks on an integration-branch plan would block each other until the one final integrate, but unfolded work would conflict late). A code claim on the plan's integration branch or on a branch another live claim records is refused (`shared-branch`), so a branch tip is always one claim's own. When the branch is gone after the landing, the landed tip of BR-1423 decides. Stage 1 has no verb that folds a finished branch into the integration branch (stage 2's `land` adds it), so until the orchestrator folds it by hand (`git -C <int-worktree> merge --ff-only <branch>`, named in the shipped implementer text, AC-DCS1-24) a chained task touching the same files is still refused for overlap. A first claim from a worktree cut at the plan's integration branch is accepted (BR-1353 as modified): without it `lore start` of a chained task would be refused.

**New-file anchors.** A non-resolving anchor is never a refusal (`service/CLAUDE.md`): a task may anchor a file it is about to create, and the approved task is itself a task of its plan. The only existence check at compile is the falsifier literal, which must be present at its path unless the AC is marked `--falsifier-new-symbol` (AC-DCS1-2, AC-DCS1-3).

### Invariants

- I1: one copy of each done predicate; `finish`, `claim`, `start` and `lore done` import the same functions (the contract compile calls the existing `definitionOfDone` and floor predicates).
- I2: the contract is fixed at approve; it only grows, by the test files a write set adds. `finish` and `done` never raise or waive a requirement.
- I3: no partial contract: a compile that cannot complete refuses with every cause and writes nothing (AC-DCS1-2).
- I4: evidence comes only from the runner's exit status; `finish` records in one corpus write (AC-DCS1-20).
- I5: a check or corpus task never has a worktree or a claim (AC-DCS1-21).
- I6: a claim's write set bounds what the claim may write; the task's anchors bound what the task was approved to do.
- I7: every refusal has a stable name and an exact exit code in its criterion.

## Migration (breaking)

AC-DCS1-22 and AC-DCS1-23 define `lore migrate done-contract`. Kind is inferred: a task with file anchors, or any claim that named a branch, is `code`; one without is `check` when its `ac_scope` holds a script-mode AC, else `corpus`. The preview exits 4 while anything is uncompilable, unlike the other migrate previews, because an uncompilable task is a finding to act on. There is no waiver: a task that cannot compile is listed, never moved (there is no approved-to-draft transition). A task archived with the old flag keeps its stored reason.
