# A baseline parent's children list is generated from the tree, and multi-node baseline changes are approved once as a batch (resolves #416)

## Overview/Goal

A baseline root, branch or section never states its children by hand. Every surface renders the children list from the live tree, so it needs no human upkeep. A body that tries to author such a list is refused at write. The one-time removal of today's authored lists, and any other change spanning many baseline nodes, is approved by a person once, as one reviewable batch. Before that approval readers see the old text; after it they see the generated list; never both.

Today parent bodies hand-enumerate their children:
- the root's "The twelve branches" table (13 live branches since `baseline-evaluation` was added on 2026-10-25; on 2026-10-26 two more leaves were added under `baseline-issue-loop` and `baseline-product-baseline`, and neither branch table lists them);
- each branch's `### Children` table, as the shipped `branch.md` template asks.

Nothing derives or compares these lists, and `lore baseline add` neither warns nor updates the parent.

**Mechanism.** Parent bodies hold an authored copy of tree membership.

**End state (user decision D18, 2026-10-26).**
1. Rendering: `lore get` (text and `--json` `rendered_children`), the mirror export and the review judge (a v9 derived bundle part) show `Children (from the tree)` for every baseline root, branch and section. The list is generated by the system; nobody approves it.
2. No authored lists: creating or revising a root, branch or section whose body has a children-list heading is refused (exit 4). A heading line counts only in these exact forms, at level 2-4 and ignoring case and surrounding spaces: `Children`, `Children (from the tree)` (the rendered heading pasted back), `The <number> branches` or `The <number> sections` (digits or the English words one to twenty). Any other heading that mentions children, such as `How children are ordered`, is accepted.
3. Order instead of a transitional mode: the rendering code is not landed until this corpus's single migration batch (shared with #409) is approved. The batch removes every written list from all 20 parents at once. So readers see the old text before approval and the generated list after it, and rendering never needs to inspect a body. The write refusal keeps written lists from returning. Task-level links enforce this order: the migration task blocks the rendering tasks.
4. Change batch: one new generic mechanism for any change spanning several baseline nodes.
   - `lore batch stage --file <changes.json>` creates ONE draft document (knowledge sub_type `change-batch`). Each entry holds the node, its base version, the new body and an optional structured patch. The batch body renders the full per-node diff set for review.
   - Staging writes nothing to any node.
   - `lore approve <batch>` (a person; the same human gate as any approval) applies every entry in ONE store transaction: one version per node, attributed to the approving party and naming the batch.
   - If any node's version differs from its entry's base version, the approval is refused (exit 5, STALE_VERSION) and nothing is applied. `lore reject <batch>` applies nothing.
   - An approved batch is a locked record.
5. Migration (throwaway): `scripts/migrations/baseline-generated-parts.ts` is run once by a task. Its transform (throwaway, inside the script) computes the changes for every parent body (removing authored lists and count sentences, and rewriting the root's reading guide) and for every current-values table of #409, as ONE batch. The script is deleted in the same task once the batch is approved. No migration verb ships.

Issue: GitHub #416 (bound through this spec's plan). It uses the v9 derived-part mechanism of `spec-each-document-type-declares-which-structured-fields-the` (#414). #409's spec uses the same batch.

## Scope

**In**
- Baseline root, branch and section nodes (20 live on 2026-10-26).
- Rendering on `lore get`, the mirror export and the judge; the write refusal.
- The change batch: the `change-batch` sub_type, `lore batch stage` and atomic apply on approval.
- The shipped `branch.md` template and SKILL.md node table.
- The throwaway migration and its single batch, shared with #409.

**Out**
- PRD and plan bodies: no template asks them for a children list, and the Navigation line already lists children.
- A child's one-line scope text: the branch's own Boundary section stays the authority.
- A standing comparison check: the write refusal makes an authored list impossible, so a check could only find what the refusal already prevents (review finding design-2).

## Design

### Rendering

`renderBaselineChildren(parent, children)` (pure, `packages/lore/src/service/baseline-generated-parts.ts`) takes the live (not deleted) children in tree order (ordinal, then title). It returns a table, `| Child | Label | Kind | Live rules |`, plus the line `<n> children`. #409 adds `renderCurrentValues` to the same module, so the generated parts of a baseline node have one home.

### Batch file shape

`changes.json` is `{ "title": "...", "entries": [{ "node": "<slug>", "base_version": 7, "body": "<new body>", "patch": { "current_values": [...] } }] }`.
- `lore batch stage` refuses (exit 4, nothing created) an entry naming a non-baseline document, a duplicate node, or a base version that is not the node's current version.
- The batch document's body is the per-node unified diff (body and patch), followed by the entry count.

### Concurrency

- Approval is all-or-nothing under one transaction with a per-node version check, so a node edited after staging refuses the whole batch.
- Two batches touching one node: the first approval wins, and the second refuses with exit 5. It is re-staged from the new versions.
- Staging twice from the same file creates two drafts. The second one's approval refuses (exit 5) once the first has applied.

### Public interface (falsifier literals, verbatim, once each)

- `baseline-generated-parts.ts`: `.filter((child) => child.deleted_at === null)`; `const CHILDREN_HEADING = /^#{2,4}\s*(children|children \(from the tree\)|the (\d+|one|two|three|four|five|six|seven|eight|nine|ten|eleven|twelve|thirteen|fourteen|fifteen|sixteen|seventeen|eighteen|nineteen|twenty) (branches|sections))\s*$/im;`
- `packages/lore/src/service/change-batch-service.ts`: `if (current.version !== entry.base_version) return staleBatch(`.
- `export-docs-service.ts`: `const childrenSection = renderBaselineChildren(doc, children);`.
- `corpus-service.ts`: `if (isBaselineParent(input) && hasAuthoredChildrenHeading(nextContent)) return refuseAuthoredChildren(`.

## Design Decisions

Decided with Sequential Thinking; batch approval per user decision D18.

| # | Choice | Chosen | Rejected (why) |
|---|---|---|---|
| D1 | End state | Render from the tree; refuse authored lists at write; migrate once | Keep a comparison check beside rendering (S2 draft): a guard for a state the write refusal makes impossible. Require a parent revision on every child add: couples each add to a review, and count sentences still drift |
| D2 | Row content | Title, label, kind, live rule count | A new authored `summary` field on each child: another hand-written field. The first sentence of the child body: a heuristic |
| D3 | Approving the migration (D18) | One change batch: one diff set, one human approval, atomic apply | Per-node pending revisions (S2 draft): about 111 approvals, and readers see migrated and unmigrated nodes side by side. An unreviewed machine write: forbidden by D18 |
| D4 | Readers during migration | Ordering: rendering lands only after the one batch is approved, so it renders unconditionally | A transitional mode that suppresses rendering while a body still has a written list (S3 draft): a branch that serves only the migration window, written into a permanent rule |
| D5 | Migration code | A throwaway script producing the batch file | Shipped inventory/import verbs (S2 draft): one-time code kept in the binary forever (review finding design-4) |
| D6 | Batch home | A knowledge document (sub_type `change-batch`) approved with `lore approve` | A new top-level type or verb family: duplicates the review queue, approval gate, audit and lock that documents already have |
| D7 | What the refusal matches | The exact written-list forms (Children, the rendered heading, 'The <n> branches/sections') | Any heading containing 'Children' (S3 draft): refuses legitimate headings such as 'How children are ordered' |

## Acceptance Criteria

Stored with `lore ac add`; repeated here for readers of the body.

- **AC-CL-1** (BR-1429): in a throwaway corpus, `lore get` of a branch whose body has no authored list and which has three leaves (one deleted) ends with `Children (from the tree)`, two rows and `2 children`; `--json` `rendered_children` matches. After another leaf is added, it shows three without any edit of the branch. The branch's text is shown first, unchanged, followed by the generated list. Test: `packages/lore/tests/integration/cli/baseline-rendered-children.test.ts`.
- **AC-CL-2** (BR-1429, BR-960): the mirror export and the v9 judge prompt of that branch show the same rendered list. Test: `packages/lore/tests/integration/baseline-children-everywhere.test.ts`.
- **AC-CL-3** (BR-1463, BR-614): creating or revising a root, branch or section whose body has `### Children`, `## Children (from the tree)` or `### The twelve branches` exits 4, naming that children are generated from the tree, and nothing is written. A parent body with `### How children are ordered` is accepted (exit 0), and so is a leaf body with `### Children`. Test: `packages/lore/tests/integration/cli/baseline-authored-children-refused.test.ts`.
- **AC-CL-4** (BR-1464, BR-266): `lore batch stage` over 3 nodes creates one draft change-batch whose body holds 3 diffs, and writes 0 node versions; `lore get` of each node is unchanged. `lore approve <batch>` applies all 3 (one version each, naming the batch). In a second fixture, one node edited after staging makes the approval exit 5 and apply none. `lore reject` applies none. Test: `packages/lore/tests/integration/cli/change-batch.bun.test.ts`.
- **AC-CL-5** (BR-1429, BR-1464): end-state oracle on a fixture corpus. A root with "The twelve branches" and 13 live branches has a batch staged that removes the table; staging changes nothing a reader sees. After the batch is approved, `lore get` shows the rendered 13 and no "twelve", and a revision re-adding a children table exits 4. This corpus's own migration is a plan-close step, not an AC (it needs the D18 human approval). Test: `packages/lore/tests/integration/cli/baseline-children-end-state.test.ts`.
