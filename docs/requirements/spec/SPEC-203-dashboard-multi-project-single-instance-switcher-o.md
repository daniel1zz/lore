## 22. Dashboard Multi-Project (single-instance switcher over the machine's registered corpora)

**Vision (owner, 2026-07-25)**: one `lore dashboard` instance mounts every lore corpus registered on this machine and serves them all behind a project switcher — every existing page (home/list/tree/detail/pending/issues/execution/settings) works inside the selected project's context, and every write surface follows the switch. **Why now (owner self-report, not telemetry)**: the owner's machine runs multiple lore-governed repos (the §17 P1 install base), and each needs its own `lore dashboard` two-process pair (API + Vite) on its own ports in its own tab — the owner reports the relaunch/port ceremony as daily friction. No telemetry backs this yet (§21 F2 landed 2026-07-24, days of data at most): committing §22 ahead of F2 data is an **explicit owner override of §21's measure-first staging discipline** — same standard as the §21 D2 / §20 v0.12 owner-overrides-recorded precedent, with the kill criterion below as the counterweight. **Honest scope of the fix**: the switcher collapses N×2 processes to 2 and removes per-project relaunch; it does NOT collapse browser tabs for someone monitoring ≥2 projects *simultaneously* — that is the F4(i) aggregation candidate's job, admission-gated on switcher telemetry. **Owner decisions (Phase 1A, 2026-07-25)**: (D1) target shape = single-instance project **switcher**, not aggregation; (D2) discovery = explicit machine-level config registration (SPEC-064 machine scope), no auto-scan, fail-loud on bad entries; (D3) write scope = ALL existing write surfaces follow the switch from day one — structurally safe because `GateEnforcer` runs in each corpus's own service layer (`createApp` already yields fully independent App instances), so per-project gates hold with zero new *enforcement* code; the new code is mount lifecycle, request routing, and auth — named in Open technical questions, not hidden under D3.

- **F1 Project registry (committed)** — machine-level config `dashboard.projects: [{name, path}]` (name unique — duplicates rejected at config validation; path = repo root carrying `.lore/`, the `findLoreDbPath` contract). Named sub-deliverable: `GlobalLoreConfigSchema` is `.strict()` and today carries only `defaults` — the registry needs its own validated schema section (machine scope, SPEC-064 channel). Registry non-empty → multi-project mode; absent/empty → current single-project behavior (no flag day). Mount-time per-entry diagnosis, three classes: **mountable** / **missing** (path absent or no `.lore/`) / **schema-skew** (corpus `PRAGMA user_version` ≠ the serving binary's expected version — reusing the `probeUpstreamDb` readonly-probe precedent, §20 R-5(b) rail: mounting MUST NOT auto-migrate a registered corpus). Problem entries are NEVER silently dropped: they render in the switcher as explicit error entries with the named diagnosis + the literal per-project repair command; mountable projects serve normally. **Post-upgrade reality (accepted, named cost)**: because ONE shared binary serves all corpora, a lore upgrade makes every not-yet-migrated corpus schema-skew *simultaneously*; repair remains per-project and deliberate (run the migration from that project — skew diagnosis carries the exact command), and "N of M unmountable the morning after an upgrade" is the designed, loud behavior — never silent auto-migration of someone's corpus (the §20 rail outranks convenience). v1 registry editing = YAML/CLI; in-UI registry management is F4(ii).
- **F2 Switcher + project context (committed)** — global nav switcher lists registered projects, each with a lightweight per-project pending-review count badge (count-only cross-project signal, no doc data crosses projects — deliberately less than F4(i) aggregation). URL carries the project identity: every route bookmarkable, refresh-stable; switching is a FULL context switch. **Explicit addressing invariant**: every API request names its target project in the URL; unregistered identity → 404-class rejection; NO session-sticky "current project" server state (the 2026-07-07 pollution incident mechanized as an addressing rule). **Client read-side isolation is a first-class deliverable, not an assumption**: today the dashboard client has ZERO project dimension — ~31 hardcoded `/api/…` literals and ~43 bare `queryKey` sites — so the landing spec MUST route all client fetches and query keys through a single project-scoped factory (one seam bounds the blast radius), and R-16 pins the no-stale-bleed behavior. Default project on launch = cwd project if registered, else last-viewed (client-side localStorage only — server stays stateless per the addressing invariant), else first registry entry.
- **F3 Write surfaces follow the switch (committed)** — adjudication (approve/reject + calibration capture), doc editing, issue triage, and corpus-scope config editing (SPEC-062, targeting the selected project's `.lore/config.yaml`) operate on the selected project's corpus through that corpus's own service layer: same GateEnforcer checkpoints, same `http_cookie` surface attribution and actor resolution, same If-Match semantics — per project, unchanged. Machine-scope config editing (SPEC-064) stays global. Gate denials render that project's feeding pack. **Wrong-project-write prevention (R-13 clause)**: the selected project's identity renders persistently adjacent to every write control (adjudication bar, editor save, config save) — keyboard-first triage speed (§21 F1(c)) must never leave the human guessing which corpus a verdict lands in.
- **F4 Staged candidates (admission-gated; §18 P5 rule)** — (i) cross-project aggregation views (unified pending inbox, all-projects plans board): admitted on F2 telemetry showing ≥2 distinct projects visited per week over 4 consecutive weeks; (ii) in-UI registry add/remove (SPEC-064 write channel): admitted on ≥2 recorded registry-edit friction reports (issue/retro docs — quantified, not "first complaint"); (iii) production build + single-process serving remains §21 F4(i), unchanged.

**Auth model (requirement-level semantics; mechanism = Open question Q1)**: one local bootstrap login (SPEC-016 flow) grants access to every registered project on this machine; logout invalidates globally; server keeps binding 127.0.0.1 only. **Honest blast-radius accounting**: today a leaked/held session cookie exposes ONE corpus; under this model it exposes EVERY registered corpus. The owner accepts this on the single-user-machine trust model (the machine login is the boundary; any local process that can read the cookie can already read every corpus file directly on disk — the cookie adds write-path convenience, not a new reader), BUT two rails are non-negotiable: 127.0.0.1 bind (unchanged) and the e2e-suite foreign-server guard pattern (`assertServerIsOurs`) extended to refuse writing through an unrecognized multi-project instance — the 2026-07-07 lesson says scripts, not humans, are the realistic wrong-corpus writers, so the guard must be script-facing, not display-only.

**Open technical questions (§17 precedent — named, not buried)**: (Q1) session/API-key home — `SessionStore`/`ApiKeyStore` are constructed per-corpus on each corpus DB (`app.ts`), and HTTP auth currently runs against one hardcoded App *before* any project resolution; single-login needs a machine-level session home or an explicit replication design. **The landing spec MUST pin Q1 before any F2/F3 implementation begins** — it is the hardest unresolved piece of this section, and R-14 stays unimplementable until it is decided. (Q2) N-App lifecycle — mount/unmount, per-request App routing, and runtime failure isolation (R-17) have no precedent in the codebase (today: exactly one App per process); the landing spec owns the lifecycle design. (Q3) `GlobalLoreConfigSchema` extension shape for `dashboard.projects`.

**Boundary notes**: (a) §21's "no hosted/multi-tenant dashboard" non-goal UNCHANGED — multi-project is same-machine, same-user, multiple local corpora; cross-machine stays §17 P2+. (b) §13.5 Home-as-resolved-PRD UNCHANGED — home renders the *selected project's* living PRD. (c) `dashboard.projects` and §20's `feedback.upstream` remain SEPARATE registries — merging them would let "I want to see it" imply "it may be written to", the consent collapse §20 avoided. (d) Two instances mounting the same corpus (project-local dashboard + multi-project instance) remains possible: SQLite WAL tolerates the writes and services are stateless over the store, but this is a known confusion surface — the UI renders the serving instance's identity (port + registry name) for humans, and the script-facing guard in the auth note covers automation; residual risk accepted and named.

**Launch oracles (pre-release, CI-verifiable)**: (1) bun-test over the mount diagnoser: three-class classification incl. byte-identity of a schema-skew corpus after a mount attempt, duplicate-name rejection, and the all-entries-unmountable boundary state (dashboard up, explicit all-error switcher, no crash); (2) Playwright e2e on TWO `mkdtemp` throwaway corpora (registry file generated at e2e setup pointing at both; `assertServerIsOurs`-equivalent guard authenticated against both corpora): one login → both readable; approve + doc edit in A lands in A while B's doc set is byte-unchanged; a gate-armed write in A is denied with A's feeding pack while the same write in B succeeds; an If-Match token minted under A replayed against B is rejected, never silently applied; (3) switch-then-read e2e: after switching A→B, no A-corpus data renders under B's URL (stale-cache bleed assertion, R-16); (4) component test: switcher renders a problem entry as an explicit error state, and project identity is visible adjacent to write controls; (5) registry-absent regression: existing single-project suite passes unchanged AND at least one NEW assertion pins the registry-less URL/route shape (never only "unmodified suite exits 0" — the SPEC-077 vacuous-oracle lesson).

**Post-launch KPIs (operational, NOT CI gates; provisional n=1 thresholds, §21 caveat)**: ≥3 projects registered on the owner's machine within 2 weeks of landing; F2 route telemetry shows sessions touching ≥2 distinct projects per week within 4 weeks; outcome metric — `lore dashboard` process launches per week (proxy for relaunch friction) drops vs the pre-landing week.

**Kill criterion (§8 family, confound-checked per §21 discipline)**: if 4 consecutive weeks of F2 telemetry after landing show the multi-project instance serving ≤1 distinct project per week, F4(i)/(ii) freeze pending owner re-decision — and the freeze review MUST consult per-project route data plus two named confounds first: (a) whether the switcher failed the workflow vs multi-project demand being absent (End-User review flagged these as telemetry-indistinguishable; the review must include an owner self-report), (b) whether a post-upgrade all-skew window suppressed usage. The switcher itself remains (it still removes relaunch friction for sequential use).

**Non-goals**: no hosted/multi-tenant serving; no cross-project search or cross-project doc links this round (per-DB link tables; cross-corpus references are §19-class at most); no auto-discovery of corpora (explicit registration IS consent + blast-radius control); no per-project auth separation (single-user machine trust model; revisit only with §17 P2+ hosting).
