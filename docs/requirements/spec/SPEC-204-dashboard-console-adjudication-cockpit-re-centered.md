# 21. Dashboard Console (adjudication cockpit re-centered; admin-console breadth admission-gated)

**Vision (owner, 2026-07-24; re-anchored 2026-07-28)**: the dashboard's positioning broadened from the §13.5 "PRD projection + adjudication surface" into the team's **general admin console** over the corpus (D1). **The 2026-07-28 evidence-first grill round (D4) re-anchors investment priority**: the primary human job on the dashboard is **adjudicator/supervisor** — adjudication throughput + situational awareness are the first-weight dimensions. Console breadth (D1) is NOT revoked — the bridge is explicit: any non-cockpit surface (read/browse/edit growth, DAG views, share modes) re-admits ONLY through its F4 trigger firing on F2 route-level demand evidence, never by default investment (D8). Evidence source: `knowledge-dashboard-human-friendliness-evaluation-2026-07-28` — each verdict grounded in an external oracle run during the session (`lore pending --json` queue composition, bootstrap claim/session state, CLI capability probes) and resolved explicitly by the owner. Owner overruled the 6-role ideation consensus recommendation of a narrower "adjudication cockpit" in D1 (dissent recorded in `knowledge-ideation-dashboard-capability-expansion-6-role`); D4 partially restores the consensus direction on priority (cockpit first) while keeping the console ceiling — both moves recorded, neither hidden. **Re-review discipline (anti-oscillation)**: the D4-D8 direction is itself scheduled for a mandatory evidence re-review 4 weeks after F5a lands, against F2 route data — including a specific re-test of D8 (read-view demotion was measured while the two-process launch friction existed; post-F5a route data must confirm or overturn it before D8 is treated as settled). **Structural bound that makes the console positioning safe**: `GateEnforcer` runs at the service layer, so every dashboard write already passes the same deterministic gates as CLI/MCP — console breadth can never become gate bypass; the residual risk is UX-affordance design, and each new write surface still pays the SPEC-062-class consistency tax, which is why batches are staged and telemetry-gated. Batch ordering is itself an owner decision (D2): the ideation consensus ranked the execution view first; owner chose the adjudication workbench first — recorded, not hidden. The console serves all human collaborators (3-5 people), not only the owner: every F1 surface is cookie-session-scoped with actor attribution through the existing audit trail, no owner-only affordances.

**Owner decisions 2026-07-28 (grill round; each resolved explicitly by the owner, not inferred):**

- **D4 Persona re-anchor**: primary human dashboard job = adjudicator/supervisor. Evaluation and investment weights follow: adjudication throughput + situational awareness first; authoring/reading are secondary.
- **D5 Home identity reversal (the §13.5 reversal this document reserved, now exercised)**: Home ceases to be the resolved living PRD and becomes a **situational cockpit**: (a) decisions awaiting me — the human-review slice after tiered-review triage (consumes `spec-tiered-review-ledger-fast-track-judgment-required-promote`; this document only references, never restates, that policy); (b) an activity stream over the existing `lore audit --since/--actor/--limit` global query (a read-only HTTP projection + UI is the missing piece, not a data model) — window defaults to "since last visit" with a 48h floor, and the stream MUST NOT reinherit the pending-queue's signal-to-noise failure: default view filters to decision-relevant events (approve/reject/create of durable types, gate denies once traced, handoffs), with raw firehose behind an explicit toggle; (c) health signals (drift / stale / archive candidates from `lore status`) — v1 is read-only, each signal naming its CLI repair command (`lore doctor` family), no in-place fix affordances. The resolved living PRD (§13.5 / SPEC-033) moves to a dedicated route — the projection surface itself is unchanged, only its address. Rationale: the returning human's first question is "what happened while I was away, where am I needed".
- **D6 Packaging admission-gate overturned — prerequisite, ordered BEFORE the cockpit**: F4(i)'s "admitted after a size spike" condition is replaced by a commitment: `lore dashboard` serves a production static build from `lore serve` in ONE command (still local-only). Rationale: a cockpit gated behind a two-process vite-dev launch never forms a check-in habit (distribution-first ADR: an improvement without a delivery surface does not exist). This also resolves the kill-criterion confound (a) below by construction. The `dist/lore` size delta is still measured and recorded at landing time — as an observation, no longer an admission gate. **Boundary vs the distribution freeze**: `knowledge-grill-review-2026-07-28-seven-product-direction` decision 1 freezes *distribution/auth/sync* investment (multi-machine, external users, hosting) pending the cross-corpus retro — local single-binary packaging is NOT that: no network surface, no tenancy, no auth model change; the term collision is nominal only.
- **D7 Execution surface demoted**: corpus progress granularity (plan/phase/task, evidence landed, claims) is the accepted monitoring boundary — Lore is a memory SSOT, not a process monitor; live agent activity belongs to the agent runner's own surfaces. F3 (landed as SPEC-077) remains as a narrow-window local-value surface; no further execution-surface investment; execution verbs stay out (F4(iii) unchanged, its dual admission trigger intact).
- **D8 Read views demoted to adjudication context**: search/tree/library serve as context surfaces attached to the adjudication flow; AI proxying (`lore search/get` inside agent sessions) is the primary human query channel. No standalone read-surface investment absent new demand evidence from F2 route data. Subject to the post-F5a re-test named in the Vision paragraph (the demotion was measured under launch friction; it is a provisional, not permanent, verdict).

- **F1 Adjudication workbench (first batch, committed — landed)** — adjudication becomes evidence-grounded on one screen:
  - (a) **Evidence/AC tab on doc detail**: task docs render the `extra.verification_evidence` timeline (result, oracle type, command, attested-vs-self-reported trust label — the SPEC-039 distinction made visual, `output_tail` in a monospace terminal-style panel); spec docs render the structured AC list (SPEC-038) with per-AC coverage state derived from evidence `ac_ref` joins; plan docs surface the plan-wide attestation ratio (SPEC-069 `attestationFloor` input). **Named backend deliverable**: a read-only aggregation surface (service method + HTTP route) for AC-coverage and attestation-ratio — today these are computed only transiently inside gate predicates; no standing query path exists. Read-only projection, no new write semantics. Boundary states are first-class: zero evidence entries and spec-without-ACs render explicit empty states (never blank/crash).
  - (b) **Adjudication context panel**: on any doc carrying pending review, the approve/reject controls render adjacent to (a)'s evidence summary + AC coverage state — zero additional navigation steps between evidence and verdict. A layout spike on the existing DocDetail component tree is the first task of the landing plan (feasibility before commitment — if the same-screen constraint proves unachievable, the fallback of a one-click evidence popover requires owner sign-off as a requirement change to R-8).
  - (c) **Keyboard-first triage**: the pending/triage queue operable with keyboard alone — `j`/`k` selection, `a` approve, `x` reject-with-reason modal, `e` expand blocking questions, `o` open doc detail (Linear-inbox pattern). Keyboard shortcuts are suppressed whenever an editable element (CodeMirror editor, input, textarea) holds focus — keystrokes pass through to the editor, never trigger adjudication. Calibration capture (SPEC-033 §2.1 hoisted hook) fires identically for keyboard and pointer paths.
  - (d) **Judgment drill-down**: `JudgmentBadge` gains an expansion revealing the structured judgment record — decision, confidence, per-dimension qualitative reasons (`reasons[]: {dimension, finding}` — the actual SPEC-034 data shape; there are NO numeric per-dimension scores and none are invented), blocking questions, prompt_version — so the human sees WHY before ruling. Docs with no judgment record (pre-SPEC-034 or never judged) render the existing "unreviewed" state with no drill-down affordance, never an error.
  - **F1 queue precondition (2026-07-28 finding)**: the workbench's value is gated on queue signal-to-noise, not UI polish — with the pending queue ~100% system-generated execution-exhaust, human adjudication does not happen on ANY surface. The tiered-review line (`spec-tiered-review-ledger-fast-track-judgment-required-promote`, plan `plan-implementation-tiered-review-spec-103`) owns the fix; the cockpit's "decisions awaiting me" panel consumes its output. No further queue-UI investment until the human slice is ≤3 docs/day worth reading.
- **F2 Usage telemetry (ships WITH F1 — owner decision D3; landed)**: route-level view events (`route_id`, `doc_type` when applicable, timestamp, session marker) recorded to the existing SPEC-012 local JSONL sink under the existing opt-in config. **Named backend deliverable**: telemetry writes are server-side (the browser has no fs access — Node-free invariant), so F2 includes one cookie-gated ingestion route in the `/api/dashboard/*` family. Sink write failure is logged server-side and never surfaces to the UI as an error (deliberate, documented exception to fail-loud: observability must not break the observed surface). No new sink, no remote export, no doc-content capture. Purpose: replace assumption with measurement (ideation A1) before later batches commit — and, via `route_id`, attribute demand to specific surfaces (F1 vs F3) so the kill criterion can distinguish "workbench unused" from "wrong batch shipped first".
- **F3 Execution read surface (landed as SPEC-077; demoted per D7)**: `GET /api/ready/:plan` (SPEC-037 D1) plus the UI layer over it: read-only views for claims with TTL countdown, derived sessions, anchor conflicts, evidence timelines, phase progress (§18 `lore phase status` family). Status: narrow-window local-value surface — claims exist only inside dispatch windows, so the page legitimately renders quiet states most of the time; this is accepted, not a defect. Read-only: execution verbs stay out.
- **F5 Delivery & cockpit (2026-07-28 batch; ordered F5a → F5b with distinct ship-gates). F5a LANDED 2026-07-28** (`spec-dashboard-production-packaging-one-command-lore-dashboard`, plan `plan-implementation-dashboard-production-packaging-f5a-one`: 13 tasks, 8/8 ACs attested by `lore verify` on a clean isolated worktree). As-built deltas worth carrying in the domain narrative: (i) the packaged-path auth mechanism is a **one-time nonce redirect**, NOT the request-time token injection the first draft proposed — a security review found loopback+Origin insufficient on a multi-user machine (TCP loopback carries no UID isolation, so a co-resident user could `curl` the long-lived machine key with a forged Origin), so the machine key is now never served over HTTP at all; (ii) assets are embedded in the compiled binary (`dist/lore` ≈ 69.3 MiB, dashboard payload ≈ 1.5 MiB), making binary↔asset skew structurally impossible; (iii) two defects that three green tasks missed were caught only by the single-process e2e harness — packaged sessions minted against a non-existent `api_keys` owner (every `/api` read 401'd, so the UI was a shell) and a missing `/api/health` stamp — which is why an end-to-end reachability check (redeem session → authenticated `/api` read) now belongs in the exit gate of any phase that ships an auth path, not in a later e2e phase:
  - (a) **Production packaging (D6, prerequisite — committed unconditionally)**: vite production build wired into the repo build; `lore serve` mounts the built static assets; `lore dashboard` becomes the one-command daily entry. Retires the two-process dev topology as the only launch path (dev mode remains for dashboard development itself). Fixes the stale `packages/dashboard/CLAUDE.md` out-of-scope claims at landing time. **Named landing-spec sub-decisions (load-bearing, must be resolved in the F5a spec, not discovered mid-implementation)**: (i) auth bootstrap replacement — the current SPA bootstrap depends on a dev-only Vite plugin injecting the local-key token at dev-server request time, which by design never runs against built output; the packaged path needs its own mechanism (e.g. server-injected index.html at serve time, or a cookie-set redirect flow) preserving the SPEC-016 anti-leak invariant; (ii) asset delivery mode — embedded into the compiled binary (precedent: the assets-manifest embed plugin in `scripts/build.ts`) vs sibling directory read at runtime, decided with the recorded size delta; (iii) origin allowlist for the packaged single-origin path (dev-port pins no longer apply); (iv) build-freshness/version-skew — the served bundle must be provably from the same build as the binary (staleness check at build/release time, surfaced loudly, mirroring the `lore verify` dist-freshness precheck pattern); (v) SPA catch-all routing must not shadow `/api/*` route priority; (vi) interaction with the SPEC-078 multi-project mount registry stated explicitly.
  - (b) **Situational cockpit home (D5) — ship-gated, not merely referenced**: F5b ships only AFTER the tiered-review triage mechanism has landed and the human-review slice is verifiably ≤3 docs/day (external oracle on the live queue, not assertion). Dependency chain stated honestly: `plan-implementation-tiered-review-spec-103` is itself sequenced behind the trace-layer plan (SPEC-102 line) — the KPI clocks below start only after both. If tiered review slips, F5a still lands (unconditional) and Home keeps its current identity until the gate opens — the cockpit must never debut pointing at a noise queue. **Named backend deliverable**: a read-only activity-stream HTTP route projecting the existing audit query (since/actor/limit), spec-pinned shape (SPEC-036 shape-drift lesson), bounded (row cap + pagination — the 10k-row corpus case carries an explicit render-bound oracle). No new write semantics anywhere in F5.
- **F4 Staged candidates (admission-gated; §18 P5 rule — no consumer, no commitment)**: each candidate carries its admission trigger: (i) ~~production build + single-binary embed~~ — **promoted to F5a by D6** (size delta recorded at landing, no longer a gate); (ii) ~~home-page evolution toward attention-feed/inbox~~ — **exercised as F5b by D5** (the §13.5 owner reversal this clause required has been made explicitly, with its ship-gate); (iii) **execution-verb writes** (claim/release/evidence buttons) — requires BOTH an independent, explicit owner reversal of the "execution verbs stay CLI-only" ideation consensus (a separate decision from D1, same standard as the exercised home-identity reversal) AND F2 telemetry showing ≥3 F3-route sessions/week over 4 consecutive weeks; (iv) calibration/attestation trust panel + read-only share mode — admitted after F1 lands; share mode additionally requires a redaction pass before any external exposure; (v) corpus DAG graph view — admitted on demand evidence from F2 route data. Anything without its trigger fired stays out of every landing spec.

**Privacy/consent boundary**: F2 telemetry is local JSONL under the existing opt-in flag; no route data leaves the machine; no doc content is captured in events. F5b's activity stream is a projection of the existing local audit trail — same machine boundary, no new data collection.

**Launch oracles (pre-release, CI-verifiable — distinct from the KPIs below)**: (1) component tests prove the full keyboard loop with keyboard-only event dispatch, including the editor-focus suppression case; (2) component tests prove the boundary states — zero evidence, spec without ACs, missing judgment record, telemetry-disabled zero-write, sink-write-failure invisible to UI; (3) Playwright e2e proves an adjudication performed with the evidence panel visible on the same screen writes the same calibration record a CLI adjudication would; (4) [F5a] a clean-checkout build produces static assets that `lore serve` mounts, and `lore dashboard` alone yields a browsable, authenticated UI on a fresh corpus with NO vite process — this requires a dedicated single-process e2e harness config (the current global-setup hardcodes the two-process topology; the new harness is a named F5a deliverable, not an afterthought); (5) [F5b] cockpit renders correct states at both extremes — a fresh corpus (zero pending decisions, empty activity stream, green health: explicit empty states, never blank/crash) AND a large corpus (≥1k audit rows: bounded render via row cap/pagination); (6) [F5a] the packaged single-origin path passes the auth/origin checks (bootstrap succeeds, cross-origin request classes still rejected) — the packaged path's origin behavior is a launch oracle, not an implementation detail.

**Post-launch KPIs (operational, NOT CI gates; thresholds provisional — n=1 human baseline, to be recalibrated against the first month of real F2 data)**: (1) audit trail records ≥5 dashboard-surface adjudications (`http_cookie`) with paired calibration captures within 4 weeks of the F5b gate opening (tiered-review triage landed + human slice ≤3 docs/day — measuring before that measures noise, not the workbench); (2) dashboard sessions/day computable from the JSONL sink within 2 weeks of F5a landing.

**Kill criterion (§8 family)**: if 4 consecutive weeks of F2 telemetry after F5a lands show <3 dashboard sessions/week (threshold provisional, same n=1 caveat), F4 candidate admission freezes pending an owner re-decision — and the freeze review MUST consult per-`route_id` data before attributing cause. The former confound (a) (two-process dev-launch friction) is resolved by construction once F5a lands — a low session count after F5a is signal, not launch friction; confound (b) (which routes were actually visited) remains. This 4-week checkpoint doubles as the mandatory D4-D8 re-review named in the Vision paragraph. The F1/F5 surfaces themselves remain (sunk, small, harmless).

**Non-goals**: no CLI feature parity for its own sake — the console grows only surfaces where a UI has structural leverage (timelines, matrices, drill-downs, graphs); no hosted/multi-tenant dashboard in this round (§17 P2+ home — and F5a's local packaging is explicitly not this, per the D6 boundary); no SSE/live push until an explicit evidence-visibility latency SLA is decided (polling stays the default — the cockpit polls); no live agent-session monitoring (D7 boundary: corpus granularity only); no numeric judgment scores invented where the data model has none; no restatement of the tiered-review policy here (owned by its own spec line); no in-place fix affordances on health signals in v1 (read-only + named CLI repair command).
