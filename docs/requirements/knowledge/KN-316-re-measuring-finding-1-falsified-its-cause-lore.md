## Context

Measured 2026-07-30 while integrating `fix/governance-never-discard-lore-output` (60 commits, a full day of work) into `main` and preparing the follow-up slice named by `knowledge-handoff-agent-main-orchestrator-41`. The handoff's first two next-steps rested on findings 1 and 3 of `knowledge-eight-findings-from-building-and-closing-the-plan`. Re-measuring finding 1 before building its fix falsified its stated CAUSE while confirming — and enlarging — its recorded CONSEQUENCE.

## 1. `lore verify --ac <id>` is NOT inert — the flag works in all four dimensions

Finding 1 of the retro states the flag is silently inert ("the FIFTH false-oracle vector recurring on a different flag"). Measured against the compiled binary built from the tree under test (`8227dd1`, the exact code those runs used — `git diff main 8227dd1 -- packages/lore/src/adapters/cli/commands/verify.ts` is EMPTY), in a throwaway `mkdtemp` corpus with three script-mode ACs:

| experiment | requested | executed | exit |
|---|---|---|---|
| A single value | `--ac AC-RAF-2` | `AC-RAF-2` only | 0 |
| B control, no `--ac` | (all) | `AC-RAF-1`, `AC-RAF-2`, `AC-RAF-3` | 0 |
| C repeated flag | `--ac AC-RAF-1 --ac AC-RAF-3` | exactly those two | 0 |
| D unknown id | `--ac AC-RAF-99` | — | **4**, `Validation failed on field 'acIds'` |

The decisive artifact is not stdout but the attested `ac_ref` multiset the runner wrote: `{AC-RAF-1: 2, AC-RAF-2: 2, AC-RAF-3: 2}` — 6 entries, exactly the union of the three runs' requested sets (A: 1, B: 3, C: 2). Experiment B is the control proving the assertion is live rather than vacuously true; experiment D proves the unknown-id path is loud, not silent.

Source agrees with the measurement: `normalizeRepeatableFlag` (`commands/verify.ts:151`) normalizes both the single-string and the array shape, and `verify-runner-service.ts:416-428` filters the declared criteria by the requested id set and returns `VALIDATION_ERROR` for any undeclared id.

**Why the retro concluded otherwise.** Its evidence was real but its premise was not: all 8 plan tasks carry exactly 16 attested entries covering all 16 distinct ACs, each set sharing ONE timestamp — i.e. 8 plan-wide runs, 128 attested entries. The retro describes "six per-task attestation runs each passed one or more `--ac` values"; the corpus says eight runs, each unrestricted. The parsimonious reading — and the only one consistent with the flag demonstrably working on the same code — is that those runs never passed `--ac` at all.

## 2. The real defect is the DEFAULT write-scope, and it is worse than an inert flag

`lore verify <plan>` with no `--ac` executes every declared script-mode AC and writes an attested entry for each one onto the SINGLE resolved target task, with no warning. Measured on run B: three warnings printed (trust-tier notice, draft-spec notice, execution-root fallback) and NOT ONE of them mentions that a plan-wide AC set is being attributed to one task.

This entangles with how the claimed set is defined. `deriveClaimedAcCoverage` (`packages/core/src/evidence-panel.ts:176`) derives `claimed_acs` as "declared script-mode criteria carrying >= 1 evidence reference". The claimed set is therefore GENERATED BY THE EVIDENCE ITSELF, not declared independently by the task. Consequences, in the order they matter:

1. A single plan-wide `lore verify` makes every declared script AC simultaneously *claimed* and *attested*, so `unattested_acs` is empty and `meets_coverage` is `true` — the per-claimed-AC conjunct this very slice landed as its "default teeth" is satisfiable in one command, independent of what any task actually did. The conjunct still measures something real (the spec's script ACs pass at close time), but it cannot express per-task scope, and the set it checks is authored by the run being checked.
2. Per-task evidence scope is destroyed rather than merely overstated: with all 8 tasks claiming all 16 ACs, "which task proved which AC" is unrecoverable for this plan. `verification_evidence` is append-only, so this is permanent.
3. This is the mechanism behind retro finding 8's cost complaint. `attestationFloor` condition 1 (every evidence-bearing task needs >= 1 attested entry) plus a runner that writes to exactly one task per run means the cheapest way to satisfy it for N tasks is N plan-wide runs — N x M command executions (8 x 16 = 128 here), each one widening another task's claim to the whole spec. Finding 8 asks whether condition 1 still earns its cost; this is the sharper answer: as implemented, condition 1 does not merely cost N runs, it FORCES the scope inflation that destroys per-task fidelity.

**Mechanization direction (a decision, not yet a fix).** The `--ac`-assertion oracle the retro proposed would be green from day one and would mechanize nothing. The real options are: refuse to attest an AC outside the target task's declared scope (which requires a task-declared AC scope — `taskExtraSchema.ac_scope` already exists and is currently consumed only by assessment facts); or emit a loud diagnostic when a run's AC set exceeds the target task's scope; or retire condition 1 in favour of the AC-granular conjunct so N runs are never needed. Choosing among these is ADR work, and it belongs with finding 8 rather than with finding 1's stated cause.

## 3. A spawn-heavy test in `tests/unit/` with the default 5s budget is a false-RED generator

Full-suite verdict at `8227dd1` in a clean isolated worktree (`git status --porcelain` empty): typecheck 0, vitest 401 files / 6816 pass / 0 fail, `bun test` 1600 pass / **1 fail** across 147 files in 615s.

The single failure was NOT the AC-072-9 concurrency flake the retro measured at the same commit (that one did not fire this run, consistent with its ~10% rate). It was `cli-plan-promote-advisory.bun.test.ts:203` → "prints ZERO advisory lines and exits 0 when the ancestor spec declares >= 1 script-mode AC (AC-VRW-5b)", reported as `error: create plan failed:` with an EMPTY stderr — the tell-tale shape of a child killed mid-flight — followed by `this test timed out after 5000ms` at 6222ms.

Attribution, measured rather than reasoned: 3/3 green re-running that file in isolation; the file EXISTS on `main` and `git diff main 8227dd1 -- <file>` is empty, so the 60-commit range never touched it; machine load average 5.19 with unrelated GUI processes competing. Root cause is the test's shape, not the range: one `it` spawns the compiled binary six-plus times (init, create prd, create spec, ac add, create plan, approve) inside bun's DEFAULT 5000ms budget, while its lighter sibling in the same file passes.

**Do not fix this by raising the timeout.** The question is why an e2e-shaped, multi-spawn, compiled-binary test lives in `tests/unit/` on a default budget at all. Any spawn-count-vs-budget mismatch of this shape converts machine load into a phantom regression, and a phantom regression at integration time is exactly what makes a real one invisible.

## 4. The notification-exit-code trap fired again, on this session's own run

Retro finding 5 recorded that a background command's harness-reported exit code describes the outer shell line. It fired again here: the completion notification for the full-suite run reported **exit code 0** while the log's own captured line read `BUNTEST_EXIT=1`. The countermeasure worked because it was in place BEFORE the run — every step's exit code was echoed into the log from inside the command. The lesson is now twice-measured on two different sessions; it is not a one-off.

## Standing lesson

A recorded finding carries two separable claims — the CONSEQUENCE it observed and the CAUSE it inferred — and they fail independently. Here the consequence was real and in fact understated, while the cause was wrong, and the fix the cause implied (assert the flag's side effect) would have been a test that could never fail. Re-measure the cause before building its mechanization; a retro is evidence about what happened, not an oracle about why.
