## Violations (most severe first)

### V1 [I4 — commit-before-done] — Implementer reported DONE with full oracle evidence, never committed
- **Evidence**: `lore audit --json` shows zero claim/evidence/release rows anywhere in the session window (nothing to cross-check against in the first place — see V3), and the recovery commit `8db5843` states outright: *"Recovers work lost from an uncommitted worktree... BUG-013... BUG-015 source fixes recovered verbatim from stash-commit remnants... BUG-009... recovered from `recover/w4-bug009`."* Confirmed live: `recover/w4-bug009`, `recover/w4-bug013`, `recover/w4-bug015` are real branches, each tipped by a `git stash`-shaped commit (`On worktree-agent-...: wip-bugNNN-source-only`), and none is an ancestor of `main` (`git merge-base --is-ancestor` returns false for all three) — i.e. the ORIGINAL commit the implementer should have made never existed; only stash residue did.
- **Consequence**: four fixed defects (BUG-005/009/013/015) existed nowhere except an uncommitted worktree and a `STATUS: DONE` report. This is the textbook Fast-Completion/Self-Verification failure mode: a subagent's own "done" claim was the only signal, and it was wrong.
- **Correction**: terminal-executor discipline — a completion report on file-modifying work is invalid without `git log --oneline -1` output attached; the orchestrator should treat a DONE report with no commit hash as `BLOCKED`, not `DONE`, and never proceed to merge.

### V2 [I5 — merge-verify-before-cleanup] — Merge printed the tell ("Already up to date") and the orchestrator proceeded to force-remove the worktree anyway
- **Evidence**: dossier (self-reported, and consistent with the recovery commit's own narrative): `git merge <branch>` → `Already up to date.` → `git worktree remove --force` executed immediately after, destroying the only remaining copy of the work. The retro doc (`knowledge-retro-2026-07-20-whole-repo-static-bug-audit-fix-sweep`, read live) confirms: *"orchestrator merged ('Already up to date' on an empty branch — the tell), then worktree-removed --force, destroying the tree."*
- **Consequence**: this is the step that turned V1 (an implementer mistake, recoverable in principle) into near-permanent data loss. `--force` removal without first inspecting `git log <branch>` is precisely the invariant catalog's own cited incident (I5's description is a verbatim match to what happened here — this review is not finding a new class, it is confirming the exact one the catalog was built to catch, on the session that IS the catalog's source incident).
- **Correction**: already adopted by the orchestrator post-incident and recorded in both the retro and CLAUDE.md — *"verify `git log` on the branch BEFORE merge+cleanup; an empty branch after a DONE report = protocol violation → recall the agent, never clean."* Confirming this rule actually landed (not just narrated) is the one thing this review could not verify — no regression test or hook enforces it; it is prompt discipline only. Recommend mechanizing: a pre-`worktree remove` check that greps the merge's own stdout for "Already up to date" before allowing cleanup to proceed, per this repo's own stated preference for gates over prompts.

### V3 [I2 — claim-before-work] — Entire fix-sweep batch (≈19 findings across 2 waves, ~20 commits) ran with zero `lore claim`/`evidence`/`release`
- **Evidence (confirmed live, not just narrated)**: `lore audit --json --limit 50` over the session window shows exactly two entries touching this session's own artifact — both `actor: "system"`, both `action: "create"`/`"update"` on the retro **knowledge doc itself** — and nothing else. No `claim`, `evidence`, or `release` actions appear anywhere in the window for any of BUG-001 through BUG-015, ASYNC2-001/002, or ASYNC2D-001/002. `lore bootstrap --json` shows no active plan for this work at all (only pre-existing SPEC-05x plans, none touching this audit). The dossier's own framing — "the orchestrator hand-partitioned files instead" — is confirmed by the absence of any corpus trace.
- **Consequence**: this is precisely the invariant catalog's own cited real incident for I2, and it is high-severity by the catalog's own rubric ("a safety mechanism was dark for real work"). The `task-claim`/`phase-claim` anchor-overlap gate (SPEC-042, the mechanism this very audit's BUG-011 hardened against TOCTOU) protected **none** of this session's ~20 concurrent-worktree fixes — not because the gate is weak, but because it was never invoked. Manual file-partitioning is a real substitute in the narrow sense that no file-level collision occurred, but it leaves zero durable, queryable trace: a future `lore search`/`lore get` for "BUG-011" or "claim gate TOCTOU" surfaces only free-text inside one narrative retro, not a structured task with ACs, evidence, and a plan-level readiness view. This also means D4 fails independently of D5/I3 — see below.
- **Correction**: for any multi-agent fix batch this size, create a lightweight plan + one task per finding (or per wave) BEFORE dispatch, with `--anchor` on the touched files, so the SPEC-042 mutex is live and the delivery is queryable later. If the overhead of per-bug tasks feels wrong for an audit sweep, that itself is useful signal for a lighter-weight task-batch primitive — but the current answer was "skip the corpus chain entirely," not "use a lighter one."

### V4 [uncatalogued] — 3 recovery-archaeology branches left unmerged with no explicit forward-looking cleanup note
- **Evidence**: confirmed live — `git branch --no-merged main` still lists `recover/w4-bug009`, `recover/w4-bug013`, `recover/w4-bug015`; none is an ancestor of `main` (their content was manually re-applied via `8db5843`, not merged as commits). The retro documents the INCIDENT thoroughly but contains no line saying "these 3 branches are now safe to delete" or any instruction for a future session to do so. `lore search "handoff"` shows the most recent handoff doc is from 2026-07-16 — none was created at the end of this session.
- **Consequence**: low severity (content is safe — verified equivalent in main via `8db5843`'s diffstat matching the claimed BUG-009/013/015 files) but real: without an explicit note, a future session either re-discovers these branches cold (mild waste) or — worse — someone unfamiliar with the incident sees 3 unmerged branches named after "recovered" bugs and hesitates to delete them without re-verifying equivalence themselves, which is exactly the archaeology this review just had to redo.
- **Correction**: `git branch -d recover/w4-bug009 recover/w4-bug013 recover/w4-bug015` (safe — content confirmed on `main` at `8db5843` by this independent review) plus one line in the next session's handoff/CLAUDE.md noting they were verified-equivalent and removed. This does not rise to the level of I9 (no *lore-tracked* work is unfinished — these are plain git branches, not corpus artifacts) but the invariant catalog has no line item for "git-level archaeology debt with no forward pointer," which is why it's reported here as uncatalogued rather than folded into I9.
