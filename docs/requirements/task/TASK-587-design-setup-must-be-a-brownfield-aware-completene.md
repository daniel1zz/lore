Current 'lore setup' (global) + 'lore setup --project' are one-shot file copiers: they scaffold assets deterministically and exit, silently leaving a project in a partially-initialized state with no defined end-state contract. Observed on a real brownfield adoption (babyai, 428 pre-existing docs migrated, 2026-07-28) — after ALL available setup paths completed successfully, the project was still inconsistent: (1) verification profiles unconfigured (init never seeded the template); (2) feedback.upstream absent so report-issue failed; (3) spec-create rule doc unseeded, gate running in degraded mode; (4) lore.tree.yaml scaffolded a single-root min-1-spec blueprint that immediately reports mass drift against the actual 30-root corpus, with no guidance on whether to relax the blueprint or restructure the corpus; (5) CLAUDE.md module index left as an empty placeholder pointing at a skill the operator may never run. Every gap was SILENT — discovered only when a downstream command failed or a check was run by hand. Proposed design, three principles: [P1 Brownfield-first with an end-state contract] setup may be multi-step, but there must be a machine-checkable definition of 'lore-consistent' (all advertised commands runnable, all gates armed with rule docs, config keys complete, blueprint reconciled with actual corpus shape, CLAUDE.md governance layer filled) and a completeness oracle (e.g. 'lore setup --check --project' or 'lore doctor') that exits non-zero until the contract holds. [P2 Judgment-or-automation, never silence] every setup step is classified: deterministic steps run automatically; steps requiring human judgment (which PRD is the corpus root; relax blueprint mins vs attach specs; archive vs approve legacy drafts; upstream corpus location) must surface an explicit guided prompt with options — silent skipping that leaves hidden incompleteness is a defect by definition. [P3 Skill as the orchestrator] deliver setup as a lore-setup skill (lore already ships skills via its asset pipeline) that drives the interaction loop, elicits the judgment calls, and invokes CLI primitives as its deterministic executors — the CLI remains scriptable for CI, the skill owns conversation-level orchestration and multi-session resumability. This subsumes previously filed reports on unseeded verification profiles, unprovisioned feedback.upstream, and the dev-only rule-doc seed script: those are symptoms; the root cause is that no component owns the end-state contract.
