# Module: store

Architecture card: `baseline-module-card-store`

## Purpose

Async persistence abstraction: `StoreInterface` with SQLite / Turso / InMemory implementations and FTS5 escape. Services depend on this one contract, never on a concrete store:

- `SQLiteStore` (`bun:sqlite`) — production local-only.
- `TursoStore` (`@libsql/client`) — embedded replica for `sync.enabled` mode.
- `InMemoryStore` — unit-test double; substring search instead of FTS5.

Row mappers, FTS5 query escaping, and JSON helpers are shared in `store-shared.ts`. `escapeFtsQuery` wraps each whitespace-separated piece of user input in `"…"` phrase quotes and doubles any internal `"`, which renders every FTS5 operator (`-`, `()`, `*`, `OR`, `AND`, `NOT`, `:`) inert rather than blocklisting them; empty input short-circuits and never reaches `MATCH`.

Full pre-eviction file (per-invariant empirical measurements, incident chains, per-spec design decisions) is archived verbatim: `lore get knowledge-module-claude-md-snapshot-packages-lore-src-store`.

## Key Invariants

- **All `StoreInterface` methods are async** — they return `Promise<Result<T, LoreError>>`. `SQLiteStore` wraps synchronous `bun:sqlite` calls; `TursoStore` is natively async.
- **`@libsql/client` is loaded LAZILY, only via a literal-specifier dynamic `import()`** (`turso-store.ts::loadLibsqlClientModule`). Rules: (a) ⛔ never replace it with `createRequire`/`import.meta.require` (broken in a compiled binary); (b) `TursoStore`'s constructor takes an optional pre-resolved `injectedClient`, which `adapters/cli/commands/sync.ts` injects; (c) `TursoStore`'s synchronous `createRequire` fallback is source-mode only; every compiled-binary route that opens a sync-enabled corpus (CLI, MCP, dashboard mount) first awaits `adapters/cli/replica-priming.ts` → `primeLibsqlClientForSyncConstruction()`, so the cached module is used and the fallback never runs. `AC-LL-10` pins which files may hand a sync-bearing config to `createApp` (`PRIMED_SYNC_BEARING_FILES`) and that the priming calls exist; ⛔ a new such caller must prime first, never get a scan exception; (d) `probeTmpdirUsability()` runs after credential validation and before any native load. ⛔ Never restore an eager load or add delay. Mechanism and history: `knowledge-evicted-from-the-store-module-doc-lazy-libsql-load`. SSOT: `spec-eager-libsql-load-makes-every-command-depend-on-a-healthy`.
- **Single SQL migration set** — `migrations/migration-001` … `027` (022 = autonomy_thresholds, 023 = decision_log `superseded` verdict rebuild, 027 = baseline nodes converted to approved + pending items, BR-1341: `extra.rules`/`label`/`glossary`/`depends_on`/`commands` hold the APPROVED versions, `extra.pending` the pending ones, read only through `service/baseline-items.ts`; each converted node gets a version row and a chained audit row authored by `migrationActor`), inlined constants both stores apply; `LATEST_SCHEMA_VERSION` moves with each new migration. ⛔ **Never edit a shipped migration in place** — add a new one.
- **A corpus schema upgrade runs ONLY through `lore migrate schema`** — `SQLiteStore`/`TursoStore` THROW `SchemaBehindError` (`schema-behind.ts`, exit 4 via `foreign-schema-guard.ts` at the loader) on an existing corpus (`user_version` > 0) older than the schema, and never migrate as a side effect of opening. Only an open with `{ migrate: true }` upgrades (the command, and test fixtures that build an old-schema file); a NEW file (`user_version` 0) is built at the latest schema with no flag. ⛔ Never add `migrate: true` to a production open other than `adapters/cli/migrate-schema.ts`. The command writes one `migrate_schema` audit row (actor, from, to, duration, working copy).
- **`decision_log` (migration-020, AC-AU-2) is the append-only, hash-chained autonomy decision log** — rows written ONLY via `appendDecisionRecord` (head-read + insert in ONE write transaction in all three stores; hashes computed store-side by `decision-log.ts::computeDecisionEntryHash`, never caller-supplied), BEFORE UPDATE/DELETE triggers refuse in-product rewrites, and `verifyDecisionChain` names the first broken row. Local-only, never replicated. Effective verdict rules (latest human-tty, else worst machine) live in `decision-log.ts`; the only adapter-facing writer is `service/decision-service.ts`.
- **`autonomy_thresholds` (migration-022, AC-AU-9) is the ONE governed threshold record** — one row (`id = 1`), written ONLY by `service/autonomy-threshold-service.ts` right after it appends the `autonomy-threshold-write` decision row carrying the content's sha256; ⛔ not append-only on purpose (the chain, not a trigger, detects an outside edit). Local-only, never replicated.
- **`runs.harness_pid` / `harness_pid_start` / `worktree` (migration-021, AC-AU-5)** record the OS process a run lives in; written ONLY by `recordRunProcess` (newest registration wins, unlike the first-wins identity columns), read by `listRunLifecycles`. A NULL pid is a LEGACY run: its death is unprovable, never "dead". Consumed by `service/run-reap-service.ts`.
- **Run identity (016)** — ⛔ every `AuditEntry`/`VersionRecord` write is stamped by `write-context-store.ts::withWriteContext`; a new such `StoreInterface` method MUST join its `STAMPED` table.
- **migration-001 is crash-safe / idempotent** — every `CREATE TABLE/INDEX/VIRTUAL TABLE/TRIGGER` uses `IF NOT EXISTS`, so a process killed mid-`db.exec` (leaving `PRAGMA user_version` at 0) re-runs the identical SQL without throwing. ⛔ Do NOT drop the `IF NOT EXISTS` guards.
- **`SQLiteStore.init` sets `PRAGMA busy_timeout` to the DECLARED bound, FIRST** — before `journal_mode`/`foreign_keys`. The bound is `SQLiteStoreOptions.writeWaitMs` (default `@lore/core`'s `DEFAULT_WRITE_WAIT_MS`, the ONE home of the number); a non-integer/negative bound throws at construction (never a silent clamp). ⛔ **ANY `bun:sqlite` handle opened against a corpus another process may write needs the bound** (it defaults to 0 PER CONNECTION), including `store/schema-probe.ts::probeSchemaVersion`. Always the NATIVE busy handler, never a JS timer/retry (`bun run check:no-timer-retry`). ⛔ **A bound does not make construction infallible**: every `Result`-returning caller MUST catch it; a failed `init()` closes its own handle before re-throwing. Regression: `tests/unit/store/busy-timeout.bun.test.ts`. Measurements and rationale: `knowledge-evicted-from-the-store-module-doc-lazy-libsql-load`. SSOT: SPEC-078 D9, `spec-report-issue-has-no-specified-concurrency-contract-ac-072` D4.
- **FTS5 maintenance is trigger-driven** — `MIGRATION_001_SQL` installs `docs_ai`, `docs_ad`, `docs_au` triggers. Both stores rely on these; no manual `fts*` calls. Verified by `tests/unit/store/libsql-compat.bun.test.ts`.
- **`UpdateOpts.expected_version` → conditional UPDATE** — when set, `UPDATE … WHERE id = ? AND version = ?`. Zero `RETURNING` rows → `err({ code: "STALE_VERSION", expected, actual })`. ⛔ Never decide a write's outcome from the driver's affected-row count (`.changes` / `rowsAffected`): bun reports a stale non-zero count for a zero-row UPDATE inside a multi-statement transaction; every guarded UPDATE/DELETE uses `RETURNING id` and counts rows (`tests/unit/store/version-guarded-update-in-transaction.bun.test.ts` greps both stores). Without it the unconditional path is preserved (backward-compatible).
- **`findMany` excludes soft-deleted by default** — `StoreFilters.exclude_deleted` defaults to `true`. Pass `false` to include `deleted_at !== null` rows.
- **`findMany` supports optional `limit`/`offset` paging** — both absent → unbounded (no implicit truncation). When used, ordering is deterministic across all three stores (`updated_at DESC, id ASC` tiebreaker) so offset paging is stable; applied AFTER the in-memory `tags` filter, never before. CLI `lore list` exposes `--limit`/`--offset` (no default cap); MCP `lore_list` caps at 100 when `limit` is omitted and always returns an explicit `truncated: boolean` (probed via `limit+1` fetch, no COUNT query). ⛔ No silent cap on any surface.
- **Batch fetch methods avoid N+1** — `findByIds(ids)` → `Map<DocId, DocRecord>` (empty input → empty Map, no malformed query) and `findLinksByFromIds(fromIds, direction?)` → `Map<DocId, LinkRecord[]>`. Consumed by `CorpusService._getImpl`, `SessionService` bootstrap, and `TreeCheckService.reconcile` — each issues ONE batch call, never a per-item loop. Cross-store parity enforced by `tests/unit/store/batch-methods.shared.ts`.
- **Self-referencing parent link is always rejected** — `detectParentCycle(fromId, toId)` in all three stores short-circuits `fromId === toId` → `err(LINK_CYCLE)` before walking the chain (SQLite/Turso previously accepted `X→X` silently).
- `DUPLICATE_SLUG.existing_id` names the doc already holding the slug, resolved per store: `knowledge-duplicate-slug-existing-id-names-the-doc-that-already`.
- **Audit `LIMIT` is bound, not interpolated** — every `LIMIT`/`OFFSET` uses bind parameters; no string interpolation anywhere in the store SQL.
- **Tamper-evident audit hash chain (migration-009, SPEC-079 G3)** — `audit` gained nullable `prev_hash`/`entry_hash`, backfilled over every pre-existing row in `id` ASC order inside the migration transaction (post-migration a NULL pair is a tamper/corruption finding, never a legal state). `entry_hash = sha256(canonicalJson({timestamp, actor, session_id, action, doc_id, details, prev_hash}))` via pure helpers in `store-shared.ts` (`node:crypto`, deliberately NOT in `@lore/core`'s browser-safe barrel), `details` keys recursively sorted; genesis `prev_hash = ""`. ALL THREE stores compute the chain at EVERY audit insert point by reading the current head inside the SAME transaction/serialized write as the insert. ⛔ The hash fields are deliberately OFF the public `AuditEntry` read/write contract — the only read surface is `listAuditChain()`, so no caller can read (and therefore forge-and-resupply) a chain hash. Regression: `audit-chain.bun.test.ts` + `in-memory-audit-chain.test.ts`.
- **`trace_events` (migration-011, SPEC-102) is append-only, NOT hash-chained, and NEVER replicated** — read/deny observability rows; no CHECK on kind/surface (Zod validates at the recorder seam, so new kinds need no migration) and no FKs by design (fire-and-forget inserts must not fail on referential state; traces of deleted docs survive). The ONLY sanctioned DELETE is retention pruning via bounded `id IN (SELECT … LIMIT)` batches. Stays OUT of the sync-push replicated set; in Turso mode trace writes go through a separate local handle on the replica file. ⛔ Every trace COUNT method is DERIVED from its list sibling (`countTraceZeroHitSearches` → `listTraceZeroHitSearches(…).length`) — there is exactly ONE tally per fact in all three stores. A second, independently-tallied counter is the defect this closed: a count can then drift from the member list a caller enumerates and nothing notices. A new `*_count` fact adds its list FIRST and derives the number from it. ⛔ **A doc read writes NO `trace_events` row** (migration-031, BR-1373): `incrementReadCount(day)` bumps `trace_read_counts(day PRIMARY KEY, count)` with ONE atomic upsert (`ON CONFLICT(day) DO UPDATE SET count = count + 1`) in all three stores, `listReadCounts(sinceDay)` feeds `lore trace stats`'s `reads`. Migration-031 deleted every old `kind='get'` row and `idx_trace_doc`; there is no never-read-docs report (it had no data source left).
- **`check_outcomes` (migration-033, BR-1373) is append-only: one row `(check_id, outcome pass|deny|error, ts)` per run of a retained gate or hook.** Written ONLY via `appendCheckOutcomes(rows)` (one transaction per batch; gates append one row, `lore checks stats` ingests the hooks' local JSONL file), read ONLY as the per-check aggregate `listCheckOutcomeStats()`. No update or delete exists; there is no replication.
- **`escapeFtsQuery` is mandatory before FTS5 MATCH** — wraps each whitespace piece in `"…"`, doubles internal `"`. Empty input → empty string; callers MUST short-circuit (FTS5 errors on empty MATCH). `InMemoryStore` does substring search and does not use it.
- **CJK bigram shadow columns fix `unicode61`'s contiguous-CJK-run tokenization (migration-008)** — `docs` gained `fts_title`/`fts_content`/`fts_tags`; `docs_fts` is redefined against THESE as its own FTS5 column names, not the real `title`/`content`/`tags` — required for `'integrity-check'`/`'rebuild'` to stay consistent, since SQLite re-tokenizes the `content=` table's OWN same-named columns, never whatever a trigger last inserted. ⛔ `computeFtsShadowValues` (on `expandCjkForFts`, a pure overlapping-bigram expander) MUST be computed and persisted at EVERY `docs` INSERT/UPDATE touching title/content/tags — a raw `INSERT INTO docs` that skips these columns (e.g. a test helper) silently defaults them to `''`, making that row FTS5-unsearchable regardless of its real title. `escapeFtsQuery` mirrors the same expansion on the QUERY side per CJK run (phrase query for runs ≥2 chars, unquoted `char*` bareword for a lone char — FTS5 does NOT honor `*` inside quotes); pure-ASCII input is byte-identical to the pre-migration algorithm. A trigram tokenizer was evaluated and rejected (cannot match 2-char queries, the dominant Chinese query shape). SSOT: `task-fts5-cjk-search-returns-zero-hits-unicode61-tokenizes`.
- **Row mappers handle libsql `bigint`** — `rowToDocRecord`/`rowToVersionRecord` apply `Number()` to `version`. Direct row reads bypass this at the caller's risk.
- **`findLinksByToIds(toIds, linkType)` is a batch link query** (SPEC-025 D7) — one round trip instead of an N+1 loop over `findLinks` when `TaskWorkflowService.ready()` computes readiness across a whole plan. Returns `ok([])` immediately for an empty array (no query issued).
- **`listAllVersions(since?)` is corpus-wide, unlike `findVersions` (per-doc)** (SPEC-035 D5) — no `doc_id` filter. It reads every column of every version row (full `content`/`extra`), so `AuditService.verify` does NOT use it: verify's versions⋈audit completeness join reads `listVersionKeys(since?)` — only `(doc_id, version, action, created_at)`, answered from the covering index `idx_versions_keys` (migration-025), so its cost does not grow with document size. ⛔ Never widen `listVersionKeys` back to payload columns. `SQLiteStoreOptions.readonly` opens the file read-only (no migration, no journal change) for the audit-verify worker.
- **`findByIdPrefix(prefix)` powers `resolveDoc`'s unique-ID-prefix resolution** (SPEC-065 D1/D2) — a discovery-shaped query, UNLIKE `find`/`findByIds` (direct-address, deliberately do NOT filter soft-deleted rows): it EXCLUDES `deleted_at IS NOT NULL`. Matching is case-INSENSITIVE in all three stores, mirroring the `/i` prefix regex `resolve.ts` tests input against. Called only after an exact `find`/`findBySlug` miss.

## Patterns

- **`store-shared.ts` is the SSOT for row shapes and mappers** — `DocRow`, `LinkRow`, `VersionRow`, `AuditRow`, `FtsRow` and their `rowToX` mappers. Both stores import these; do not duplicate.
- **Error wrapping via `wrapStoreError`** — unknown thrown driver values become `err({ code: "STORE_ERROR", message, cause })`. Service-layer errors (duplicate slug, validation) are constructed directly, not via `wrapStoreError`.
- **`InMemoryStore` mirrors `SQLiteStore` semantics, not FTS5** — substring scoring differs intentionally. Recall-rate scenarios must run against `SQLiteStore`/`TursoStore`, not in-memory.
- **`api_keys` is one of the 5 replicated tables** — see `packages/lore/src/adapters/http/sync-push.ts`. `app.ts` opens a separate `bun:sqlite` `Database` for `ApiKeyStore` when using `TursoStore`, so it shares the same local replica file.
