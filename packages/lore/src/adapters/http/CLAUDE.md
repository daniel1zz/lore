# Module: adapters/http

## Purpose

`Bun.serve` HTTP adapter. Mounts `/health` (unauthenticated) and `/api/*` (bearer-token authenticated) routes. Also hosts `sync-push.ts`, the manual logical-replication helper used by `lore sync push` to replicate the 5 core tables into a remote libsql. Optionally (`HttpConfig.dashboard`) also serves the packaged production dashboard SPA — static assets + a one-time nonce auth endpoint — so `lore dashboard` can run as a single process with no vite child (`static-serving.ts` + `dashboard-assets-loader.ts`; spec-dashboard-production-packaging-one-command-lore-dashboard, "F5a").

## Key Invariants

- **All `/api/*` requests require a valid identity.** `authenticateRequest` checks the `lore_sid` HttpOnly cookie first (resolved via `SessionStore`); if absent or expired, it falls back to the bearer-token path (`ApiKeyStore`). Unauthenticated requests return `401 UNAUTHORIZED`. `/health` is the only unauthenticated route. `POST /api/auth/local-bootstrap` self-authenticates via `X-Lore-Token` header + Origin allowlist (SPEC-016).
- **Dashboard cookie auth is MACHINE-scope, unconditionally (SPEC-078 D1)** — `machine-auth.ts::createMachineAuthStores()` opens/creates ONE `dashboard-auth.db` at the real XDG state dir (`$LORE_STATE_HOME` > `$XDG_STATE_HOME/lore` > `~/.local/state/lore`, mode 0600) and reuses `ApiKeyStore`/`SessionStore` verbatim over it — this is where the "dashboard-local" bootstrap key and every cookie session now live, NEVER the per-corpus `app.apiKeyStore`/`app.sessionStore`. Bearer API keys (SPEC-010 `lore serve`/`lore agent`) explicitly STAY per-corpus, untouched by this move. `startHttpServer` resolves the machine store LAZILY (memoized, only on an actual `lore_sid` cookie or the bootstrap/logout routes) so bearer-only callers — including most of this adapter's own test suites — never touch the real filesystem path; `HttpConfig.machineAuth` lets a caller (`lore dashboard`, tests) inject/share one explicit instance instead. `handleLocalBootstrap(req, machineAuth)` takes NO `App` parameter — the bootstrap flow no longer needs one. `handleApiRoute`'s `getMachineAuth?: () => MachineAuthStores` is OPTIONAL (invoked only by the `/api/auth/logout` branch) so pre-existing direct-call test suites need no changes. Corpus-DB `sessions` tables are now vestigial (rows simply expire; schema untouched, no corpus migration).
- **API keys are SHA-256 hashed at rest.** Raw key format is `lore_ak_` + 32 hex chars (`generateApiKey`). Only the SHA-256 hash is written to `api_keys`; the raw key is shown to the user once on creation and never stored.
- **Revoking an API key invalidates its cookie sessions immediately.** `SessionStore.resolve`/`touch` join `api_keys` with `WHERE ... revoked_at IS NULL` — a session backed by a revoked (or purged) key resolves as UNAUTHENTICATED and cannot be sliding-renewed. `ApiKeyStore.revoke` additionally cascade-deletes that key's `sessions` rows (same shared `db`, guarded by a `sqlite_master` existence check). A stolen cookie can no longer outlive `lore agent revoke` (previously it kept working — and self-renewed 30 days — via a null-owner `"admin"` fallback).
- **Session cookie `Secure` flag is context-conditional.** `lore_sid` gets `Secure` when the request is HTTPS (`X-Forwarded-Proto`/scheme) OR the bind host is non-loopback; loopback plain-http (`lore dashboard` local dev) is unaffected. `SameSite=Strict; HttpOnly; Path=/api; Max-Age=2592000` unchanged.
- **Dashboard write routes enforce the Origin allowlist.** `/api/dashboard/*` state-changing routes run `assertAllowedOrigin` (reusing `middleware.ts::isOriginAllowed`/`ALLOWED_ORIGINS`) before `assertCookieActor` — a present-but-disallowed `Origin` → `403`; a missing `Origin` passes through (unchanged, matches `local-bootstrap` convention) — CSRF defense-in-depth beyond `SameSite=Strict`.
- **`ApiKeyStore` takes a `bun:sqlite Database` directly**, not a `StoreInterface`. With `TursoStore` enabled, the composition root opens a separate `Database` against the same local replica file so `api_keys` shares the replicated dataset. Verified by `tests/unit/store/libsql-compat.bun.test.ts`.
- **JSON envelope** — success → `{ ok: true, value: T }` via `jsonOk`; failure → `{ ok: false, error: { code, message } }` via `jsonError` or `loreErrorResponse`. Status codes mirror the CLI exit-code semantics (4xx for validation/lifecycle, 404 for not-found, 409 for stale version, 5xx for store errors). Never leak raw `Error.stack`.
- **CORS preflight** — `OPTIONS` requests are short-circuited by `corsPreflightResponse` before auth runs. The actual API routes also guard against `OPTIONS` reaching service code.
- **`sync-push` is idempotent.** Uses `INSERT OR IGNORE` in chunks of 500 rows across the 5 replicated tables: `docs`, `links`, `versions`, `audit`, `api_keys` (D-006 / R3). Re-running on the same state yields zero new rows. Per-table `local_rows` / `remote_rows` reconciliation is in the returned `PushReport`.
- **`GET /api/phase-status/:planIdOrSlug` (SPEC-077 S3)** — the dashboard execution read surface's phase-progress projection: `{plan:{id,slug,title}, phases: PhaseScorecard[]}` (empty `phases: []` for a plan with none, not an error). Zero derivation in `routes.ts` — thin pipe over `../../service/phase-workflow-service.js::PhaseWorkflowService.planPhaseStatus` (the plan-wide sibling of that same service's `ready()`; NOT the single-phase `flows/phase-status-flow.ts::buildPhaseStatusPayload` `lore phase status`/MCP `lore_phase_status` use — the two independently reuse the SAME `computeAcCoverage`/`computePhaseCompletion` core pipeline so they never disagree on what "done" means for a phase). Same v1 read-family auth duality (cookie OR bearer); unknown id → 404 `DOC_NOT_FOUND`, a resolvable non-plan doc → 422 `VALIDATION_ERROR` naming the actual type (both from `resolveDoc`/the method's own type check, mirroring `ready()`'s identical pattern).
- **`GET /api/ready/:planIdOrSlug` carries a top-level `claim_ttl_minutes` (SPEC-077 S4)** — additive HTTP-layer enrichment (`handleGetReady` spreads `app.taskWorkflowService.claimTtlMinutes` onto the response); core `ReadyReport` (`../../service/task-workflow-service.js`) stays pure/untouched. The dashboard's claim-countdown UI divides by this field instead of hardcoding the TTL.
- **The Origin allowlist is a FUNCTION of the actual configured ports, not a hardcoded constant** (task-dashboard-bootstrap-origin-allowlist-hardcodes-port-5173) — `auth.ts::buildAllowedOrigins(apiPort, dashPort)` is the SSOT; `ALLOWED_ORIGINS` is just `buildAllowedOrigins(8787, 5173)` (the default-port case). `isOriginAllowed`/`corsPreflightResponse`/`applyCorsOrigin` (middleware.ts), `handleLocalBootstrap` (routes.ts), `handleApiRoute`/`handleDashboardRoute`/`assertAllowedOrigin` (routes.ts/dashboard-routes.ts) all take an OPTIONAL trailing `allowedOrigins` param defaulting to `ALLOWED_ORIGINS` — every pre-existing direct call site is unaffected. `HttpConfig.allowedOrigins` (index.ts) is the ONE production seam: `startHttpServer` resolves it once per server instance and threads it through every Origin-checking call site (CORS echo, bootstrap, dashboard CSRF). `lore dashboard` computes its own via `buildAllowedOrigins(apiPort, dashPort)` using the REAL ports it launches on (see `../cli/CLAUDE.md`'s `dashboard` entry) — a non-default `--dashboard-port` (or a Vite auto-increment, now prevented by `--strictPort`) previously 403'd the bootstrap POST forever. Packaged mode (below) computes a narrower single-origin allowlist inline in `commands/dashboard.ts` (just the api origin at `apiPort`) rather than calling `buildAllowedOrigins`, which always also includes a dashboard-port pair that is meaningless in a single-process topology.
- **Packaged dashboard serving is dispatch-order gated: `/api/*` → `/auth/bootstrap` → exact static match → SPA fallback — the SPA fallback NEVER shadows `/api/*`.** `HttpConfig.dashboard` (optional; omitted → this whole branch is inert, byte-identical pre-existing 404 behavior) wires `static-serving.ts::createDashboardHandler` into `index.ts`'s `fetch` closure, invoked STRICTLY AFTER the untouched `/api/*` branch has already run and returned — an unknown `/api/*` route returns its JSON `404` from that branch and never reaches the dashboard handler, so it can never fall through to `index.html`. Within the dashboard handler itself, `createDashboardHandler(config).handle(req, url)` checks, in order: (1) `GET /auth/bootstrap` — the nonce redemption endpoint; (2) an EXACT manifest-key match against `url.pathname` (hashed filenames); (3) for any other `GET` request, the SPA fallback serving the manifest's `/index.html` entry. `handle()` returns `null` (never claims the request) for a non-GET on a non-bootstrap path, or when the assets manifest is unavailable — the caller then falls through to the pre-existing generic `404`.
- **`GET /auth/bootstrap?nonce=<n>` is the packaged-mode one-time session-mint endpoint (DD-2)** — `static-serving.ts::createDashboardHandler`'s in-memory `NonceStore` (`createNonceStore`, default 60s TTL) hands out tokens via `mint()`; each token is single-use, consumed atomically on first redemption (`consume()`). First valid GET: mints a `lore_sid` session via the machine-scope `sessionStore` (owner `"dashboard-local"`, same store/cookie attributes `handleLocalBootstrap` uses) and answers `302` with `Set-Cookie: lore_sid=...` + `Location: /`. Any subsequent redemption of the SAME token — or an unknown/expired token — answers `410` + `Content-Type: text/html` (AC-F5A-10; `static-serving.ts::renderNonceFailurePage`) — a self-contained HTML page stating the launch link has already been used or expired and naming re-running `lore dashboard` as the fix, all three outcomes collapsed to the SAME page (the caller never needs to distinguish which; only the one embedded sentence varies per outcome). The page's inline `<script>` client-side-probes `GET /api/auth/me` and, on an authenticated response, forwards the browser to `/` — CLIENT-side because `lore_sid` is `Path=/api` (`auth.ts:187`, minimal-exposure choice noted at `routes.ts:122`), so `/auth/bootstrap` itself never receives the cookie and cannot detect an existing session server-side (widening the cookie path to `/` was considered and rejected — it would expose the session cookie to every static asset request and require a spec security-narrative amendment plus an ADR). A request whose `Sec-Fetch-Dest` is present and not `"document"`, or whose `Sec-Fetch-Mode` is present and not `"navigate"` (i.e. a subresource/iframe/fetch-initiated call, not a top-level browser navigation), is rejected `403` JSON BEFORE the nonce store is even touched, so a rejected embed attempt never burns a legitimate token. The endpoint is deliberately EXEMPT from Origin checking (it is a GET navigation, not the POST-CSRF case `assertAllowedOrigin` guards) — its guard is the nonce plus the `Sec-Fetch-*` check instead.
- **Machine-auth store failure NEVER produces a blanket `500` on page loads.** `handleNonceBootstrap` resolves `config.machineAuth()` inside its own `try/catch`, scoped to ONLY that one request path — a throwing (or omitted) resolver degrades to a named `503` (`MACHINE_AUTH_UNAVAILABLE`) for the bootstrap redemption alone; plain static-asset and SPA-fallback serving are completely unaffected and continue to answer `200` (the unauthenticated UI still renders). Symmetrically, a missing/corrupt embedded asset at serve time (`serveManifestEntry`) answers a named `500` for THAT one asset only, logged server-side, never an uncaught throw that would take down the whole request.

## Patterns

- **Route dispatch is a flat conditional table** in `routes.ts::handleApiRoute` — `if (method === "X" && path === "Y") return handleX(...)`. Returns `null` for unmatched routes; the server then returns 404.
- **Body parsing via `parseJsonBody`** — returns `Result<unknown, LoreError>`. Routes never `await req.json()` directly.
- **`ActorContext` flows from auth to routes** — `{ name, session_id }`. Routes pass it through to services as the audit-log actor where applicable.
- **Server lifecycle** — `startHttpServer(app, { port, host })` returns the `Bun.Server` instance. Caller (typically `lore serve`) is responsible for `app.close()` on shutdown.

## Files

- `index.ts` — `startHttpServer`; `Bun.serve` wrapper, `/health` route, auth gate, top-level error handler.
- `auth.ts` — `generateApiKey`, `hashApiKey`, `ApiKeyStore`, `authenticateRequest` (cookie-first → bearer-fallback), `extractSessionCookie`, `ALLOWED_ORIGINS`, `buildAllowedOrigins`, `ActorContext`.
- `sessions.ts` — `SessionStore` (CREATE TABLE IF NOT EXISTS on construct + pruneExpired): `create / resolve / touch / delete`. Sliding 30-day TTL (SPEC-016).
- `machine-auth.ts` — `createMachineAuthStores(opts?)` (SPEC-078 D1): machine-scope `dashboard-auth.db` reusing `ApiKeyStore`/`SessionStore` over a NEW `Database` handle, 0600, injectable `baseDir` (tests).
- `routes.ts` — `handleApiRoute`; per-endpoint handlers calling services. Auth routes: `POST /api/auth/local-bootstrap`, `GET /api/auth/me`, `POST /api/auth/logout`.
- `middleware.ts` — `jsonOk`, `jsonError`, `loreErrorResponse`, `parseJsonBody`, `corsPreflightResponse`.
- `sync-push.ts` — `pushToRemote(localPath, remoteUrl, authToken)`; libsql batch INSERT OR IGNORE.
- `static-serving.ts` — `createDashboardHandler`, `createNonceStore`, `DashboardServingConfig`; packaged-mode dashboard request dispatch (dispatch-order + nonce-endpoint invariants above). Declares its OWN `DashboardAssetsManifest`/`DashboardAssetsManifestEntry` types (`embedded: string`, what `Bun.file()` needs) — a separate, narrower shape from `dashboard-assets-loader.ts`'s (`embedded: z.unknown()`, boundary-agnostic about the dynamically-imported file handle); `commands/dashboard.ts::resolveAssets` bridges the two with one scoped cast, since both describe the same runtime value.
- `dashboard-assets-loader.ts` — `loadDashboardAssets(modulePath?)`; the COMMITTED loader that guarded-dynamic-imports the git-ignored generated manifest `../../generated/dashboard-assets.ts` (produced only by `bun run build`'s dashboard step). Never throws; `{available:false,reason}` names `bun run build` / `--dev` on any failure (module absent on a fresh clone, malformed export, etc.) — this asymmetry (committed guard, git-ignored payload) is what keeps a never-built fresh clone's `bun run typecheck` green.
