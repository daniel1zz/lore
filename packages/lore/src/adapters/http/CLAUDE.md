# Module: adapters/http

Architecture card: `baseline-module-card-http-adapter`

## Purpose

`Bun.serve` HTTP API adapter: bearer-token auth and sync-push. Mounts `/health` (unauthenticated) and `/api/*` (bearer-token authenticated) routes. Also hosts `sync-push.ts`, the manual logical-replication helper `lore sync push` uses to replicate the 5 core tables into a remote libsql. Optionally (`HttpConfig.dashboard`) serves the packaged production dashboard SPA — static assets + a one-time nonce auth endpoint — so `lore dashboard` runs as a single process with no vite child (`static-serving.ts` + `dashboard-assets-loader.ts`).

Full pre-eviction file (per-route mechanism walkthroughs, rejected-alternative rationale, per-spec design decisions) is archived verbatim: `lore get knowledge-module-claude-md-snapshot-packages-lore-src-adapters-3`.

## Key Invariants

- **All `/api/*` requests require a valid identity.** `authenticateRequest` checks the `lore_sid` HttpOnly cookie first (via `SessionStore`); if absent or expired, it falls back to the bearer-token path (`ApiKeyStore`). Unauthenticated → `401 UNAUTHORIZED`. `/health` is the ONLY unauthenticated route. `POST /api/auth/local-bootstrap` self-authenticates via `X-Lore-Token` + Origin allowlist (SPEC-016).
- **Dashboard cookie auth is MACHINE-scope, unconditionally** (SPEC-078 D1) — `machine-auth.ts::createMachineAuthStores()` opens ONE `dashboard-auth.db` at the real XDG state dir (`$LORE_STATE_HOME` > `$XDG_STATE_HOME/lore` > `~/.local/state/lore`, mode 0600) and reuses `ApiKeyStore`/`SessionStore` verbatim over it. ⛔ The bootstrap key and every cookie session live THERE, never in the per-corpus `app.apiKeyStore`/`app.sessionStore`; bearer API keys (SPEC-010) explicitly STAY per-corpus. `startHttpServer` resolves the machine store LAZILY (memoized, only on an actual `lore_sid` cookie or the bootstrap/logout routes) so bearer-only callers — including most of this adapter's own suites — never touch the real filesystem path; `HttpConfig.machineAuth` lets a caller inject/share an explicit instance. Corpus-DB `sessions` tables are now vestigial (rows expire; schema untouched, no corpus migration).
- **API keys are SHA-256 hashed at rest.** Raw format `lore_ak_` + 32 hex (`generateApiKey`). Only the hash is written to `api_keys`; the raw key is shown once on creation and never stored.
- **Revoking an API key invalidates its cookie sessions immediately.** `SessionStore.resolve`/`touch` join `api_keys` with `WHERE … revoked_at IS NULL`, so a session backed by a revoked or purged key resolves as UNAUTHENTICATED and cannot be sliding-renewed; `ApiKeyStore.revoke` additionally cascade-deletes that key's `sessions` rows (same shared `db`, guarded by a `sqlite_master` existence check). ⛔ A stolen cookie must never outlive `lore agent revoke` — it previously kept working, and self-renewed 30 days, via a null-owner `"admin"` fallback.
- **Session cookie `Secure` flag is context-conditional.** `lore_sid` gets `Secure` when the request is HTTPS (`X-Forwarded-Proto`/scheme) OR the bind host is non-loopback; loopback plain-http (`lore dashboard` local dev) is unaffected. `SameSite=Strict; HttpOnly; Path=/api; Max-Age=2592000`.
- **Dashboard write routes enforce the Origin allowlist.** `/api/dashboard/*` state-changing routes run `assertAllowedOrigin` (reusing `middleware.ts::isOriginAllowed`) BEFORE `assertCookieActor` — a present-but-disallowed `Origin` → `403`; a missing `Origin` passes through (matching the `local-bootstrap` convention). CSRF defense-in-depth beyond `SameSite=Strict`.
- **The Origin allowlist is a FUNCTION of the actual configured ports, never a hardcoded constant** — `auth.ts::buildAllowedOrigins(apiPort, dashPort)` is the SSOT and `ALLOWED_ORIGINS` is just its default-port case. Every Origin-checking function takes an OPTIONAL trailing `allowedOrigins` defaulting to that constant, so pre-existing direct call sites are unaffected; `HttpConfig.allowedOrigins` is the ONE production seam, resolved once per server instance and threaded through every call site (CORS echo, bootstrap, dashboard CSRF). ⛔ `lore dashboard` computes its own from the REAL ports it launches on — a non-default `--dashboard-port` (or a Vite auto-increment, now prevented by `--strictPort`) previously 403'd the bootstrap POST forever. SSOT: `task-dashboard-bootstrap-origin-allowlist-hardcodes-port-5173`.
- **`ApiKeyStore` takes a `bun:sqlite Database` directly**, not a `StoreInterface`. With `TursoStore` enabled the composition root opens a separate `Database` against the same local replica file, so `api_keys` shares the replicated dataset. Verified by `tests/unit/store/libsql-compat.bun.test.ts`.
- **JSON envelope** — success → `{ ok: true, value: T }` via `jsonOk`; failure → `{ ok: false, error: { code, message } }` via `jsonError`/`loreErrorResponse`. Status codes mirror CLI exit-code semantics (4xx validation/lifecycle, 404 not-found, 409 stale version, 5xx store). ⛔ Never leak raw `Error.stack`.
- **CORS preflight** — `OPTIONS` is short-circuited by `corsPreflightResponse` before auth runs; the actual routes also guard against `OPTIONS` reaching service code.
- **`sync-push` is idempotent.** `INSERT OR IGNORE` in chunks of 500 across the 5 replicated tables (`docs`, `links`, `versions`, `audit`, `api_keys`; D-006/R3). Re-running on the same state yields zero new rows; per-table `local_rows`/`remote_rows` reconciliation is in the returned `PushReport`.
- **Read routes are thin pipes — zero derivation in `routes.ts`.** `GET /api/phase-status/:planIdOrSlug` (SPEC-077 S3) delegates to `PhaseWorkflowService.planPhaseStatus`; an empty `phases: []` for a plan with none is a SUCCESS, not an error. ⛔ It is NOT the single-phase `flows/phase-status-flow.ts` path `lore phase status`/MCP use — the two independently reuse the SAME `computeAcCoverage`/`computePhaseCompletion` core pipeline so they can never disagree on what "done" means. `GET /api/ready/:planIdOrSlug` adds only a top-level `claim_ttl_minutes` (spread from `app.taskWorkflowService`), leaving the core `ReadyReport` pure — the dashboard's claim countdown divides by that field instead of hardcoding the TTL. Both carry the v1 read-family auth duality (cookie OR bearer); unknown id → 404, a resolvable non-plan doc → 422 naming the actual type.
- **Decision read routes are PURE (HR-T3, AC-HR-3).** `GET /api/decisions`, `GET /api/decisions/:id` (an open decision OR an audit item; the view's `kind` says which; unknown id 404, non-integer 422) and `GET /api/audit-items` forward to `app.decisionReadService.read*` (cookie or bearer; 503 when unwired). ⛔ Never route them through `DecisionService.listPending`/`getPending`: those run `closeStalePending`, which APPENDS marker rows to the hash-chained log. ⛔ No route path may contain `decide` (AC-AU-3 (4) scan); answering stays `lore decide` on the human TTY, the views carry only the command text.
- **Packaged dashboard serving is dispatch-order gated: `/api/*` → `/auth/bootstrap` → exact static match → SPA fallback. ⛔ The SPA fallback NEVER shadows `/api/*`.** `HttpConfig.dashboard` is optional; omitted → the whole branch is inert (byte-identical pre-existing 404 behavior). It is invoked STRICTLY AFTER the untouched `/api/*` branch has returned, so an unknown `/api/*` route answers its JSON `404` and can never fall through to `index.html`. Within the handler: (1) `GET /auth/bootstrap`; (2) an EXACT manifest-key match on `url.pathname` (hashed filenames); (3) the SPA fallback for any other `GET`. `handle()` returns `null` — never claims the request — for a non-GET on a non-bootstrap path, or when the assets manifest is unavailable.
- **`GET /auth/bootstrap?nonce=<n>` is the packaged-mode one-time session mint (DD-2)** — an in-memory `NonceStore` (default 60s TTL) whose tokens are single-use, consumed atomically on first redemption. First valid GET mints a `lore_sid` session via the machine-scope store (owner `"dashboard-local"`) and answers `302` + `Set-Cookie` + `Location: <resolveSameOriginNext(next)>` — the optional `?next=` survives ONLY as a same-origin path (exactly one leading `/`; no `//`, no `\`, no scheme, no control chars, checked raw AND percent-decoded; AC-HR-7, changes BR-862); an absent or rejected `next` yields `Location: /`. ⛔ Any re-redemption of the same token, and any unknown/expired token, answers `410` + a self-contained HTML page naming `lore dashboard` as the fix — all three outcomes collapse to the SAME page (only one embedded sentence varies). That page's inline script probes `GET /api/auth/me` CLIENT-side and forwards to `/` when already authenticated, because `lore_sid` is `Path=/api` and so never reaches `/auth/bootstrap` — widening the cookie path to `/` was considered and REJECTED (it would expose the session cookie to every static asset request and require a spec security-narrative amendment plus an ADR). A request whose `Sec-Fetch-Dest`/`Sec-Fetch-Mode` is present and not `document`/`navigate` (a subresource/iframe/fetch call, not a top-level navigation) is rejected `403` BEFORE the nonce store is touched, so a rejected embed never burns a legitimate token. ⛔ Deliberately EXEMPT from Origin checking (a GET navigation, not the POST-CSRF case) — its guard is the nonce plus `Sec-Fetch-*`.
- **A machine-auth store failure NEVER produces a blanket `500` on page loads.** `handleNonceBootstrap` resolves `config.machineAuth()` inside its own try/catch scoped to that ONE request path — a throwing or omitted resolver degrades to a named `503` (`MACHINE_AUTH_UNAVAILABLE`) for bootstrap redemption alone, while static-asset and SPA-fallback serving keep answering `200` (the unauthenticated UI still renders). Symmetrically, a missing/corrupt embedded asset answers a named `500` for THAT asset only, logged server-side, never an uncaught throw taking down the whole request.

## Patterns

- **Route dispatch is a flat conditional table** in `routes.ts::handleApiRoute` — `if (method === "X" && path === "Y") return handleX(...)`. Returns `null` for unmatched routes; the server then 404s.
- **Body parsing via `parseJsonBody`** — returns `Result<unknown, LoreError>`. ⛔ Routes never `await req.json()` directly.
- **`ActorContext` flows from auth to routes** — `{ name, session_id }`, passed through to services as the audit-log actor where applicable.
- **Server lifecycle** — `startHttpServer(app, { port, host })` returns the `Bun.Server`. The caller (typically `lore serve`) owns `app.close()` on shutdown.

## Files

- `index.ts` — `startHttpServer`; `Bun.serve` wrapper, `/health`, auth gate, top-level error handler.
- `auth.ts` — `generateApiKey`, `hashApiKey`, `ApiKeyStore`, `authenticateRequest` (cookie-first → bearer-fallback), `extractSessionCookie`, `ALLOWED_ORIGINS`, `buildAllowedOrigins`, `ActorContext`.
- `sessions.ts` — `SessionStore` (CREATE TABLE IF NOT EXISTS on construct + pruneExpired): create/resolve/touch/delete, sliding 30-day TTL.
- `machine-auth.ts` — `createMachineAuthStores(opts?)`: machine-scope `dashboard-auth.db` over a NEW `Database` handle, 0600, injectable `baseDir` for tests.
- `routes.ts` — `handleApiRoute` + per-endpoint handlers. Auth routes: `POST /api/auth/local-bootstrap`, `GET /api/auth/me`, `POST /api/auth/logout`.
- `middleware.ts` — `jsonOk`, `jsonError`, `loreErrorResponse`, `parseJsonBody`, `corsPreflightResponse`.
- `sync-push.ts` — `pushToRemote(localPath, remoteUrl, authToken)`; libsql batch INSERT OR IGNORE.
- `static-serving.ts` — `createDashboardHandler`, `createNonceStore`, `DashboardServingConfig`, `renderNonceFailurePage`. Declares its OWN narrower `DashboardAssetsManifest` (`embedded: string`, what `Bun.file()` needs); `commands/dashboard.ts::resolveAssets` bridges it to the loader's boundary-agnostic shape with one scoped cast.
- `dashboard-assets-loader.ts` — `loadDashboardAssets(modulePath?)`; the COMMITTED loader that guarded-dynamic-imports the git-ignored generated manifest (produced only by `bun run build`'s dashboard step). ⛔ Never throws; `{available:false,reason}` names `bun run build`/`--dev` on any failure. That asymmetry — committed guard, git-ignored payload — is what keeps a never-built fresh clone's `bun run typecheck` green.
- `concurrency.ts` · `config-routes.ts` · `issue-reports-routes.ts` · `projects-route.ts` — write-contention helper and the config / issue-report / multi-project route groups.
