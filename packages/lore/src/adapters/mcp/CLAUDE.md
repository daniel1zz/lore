# Module: adapters/mcp

## Purpose

MCP (Model Context Protocol) stdio adapter. Entered via `lore --mcp-server` (top-level flag intercepted in `packages/lore/src/index.ts`) or `lore agent`. Registers 24 `lore_*` tools (16 original + 4 SPEC-025 task-workflow tools + 1 SPEC-026 assess tool + 1 SPEC-035 audit tool + 1 SPEC-034 review tool + 1 SPEC-039 verify tool) and a small set of MCP resources against `@modelcontextprotocol/sdk`'s `McpServer` and connects over `StdioServerTransport`.

## Key Invariants

- **Never throws across the MCP boundary.** Every tool handler returns `{ content: [text] }` on success or `{ content: [text], isError: true }` on failure. Map service `LoreError` codes inside the handler — do not let them propagate.
- **3-arg `server.tool(name, desc, handler)` registration, then patch `inputSchema`** — see `tools.ts` header comment. The 4-arg overload with an inline ZodRawShape causes tsc to OOM (>7 GB heap) across 16 call sites. The current pattern (`registerToolWithArgs` helper, post-registration `inputSchema = z.object(...)` patch) keeps tsc check-time within seconds. **Do not rewrite to the 4-arg form.** Source: ADR-01KVYFJ5G8EVB6S5NMD3PNY5KA "Fast Path" Pattern 1.
- **Schema constants are module-level `z.object(...)` declarations**, not inline literals. Re-using `DOC_TYPE_ENUM` / `DOC_STATUS_ENUM` keeps tsc from re-resolving the shape per call site.
- **One registration per tool name.** Re-registering the same name corrupts the SDK's `_registeredTools` map.
- **Idempotent transport lifecycle** — `startMcpServer(app)` awaits `server.connect(transport)` and blocks until the transport closes. Caller is responsible for `app.close()` after return.

## Patterns

- **App is the only dependency** — `registerTools(server, app)` and `registerResources(server, app)` receive the wired App; tools never touch a store or service constructor directly.
- **`schema-info.ts` carries `CORPUS_SCHEMA_INFO`** — a static description of the corpus shape exposed as an MCP resource. Update it when adding a new doc type or required `extra` field.
- **Tool naming convention: `lore_<verb>`** — `lore_create`, `lore_get`, `lore_set`, `lore_search`, `lore_list`, `lore_tree`, `lore_link`, `lore_pending`, `lore_approve`, etc. Mirrors the CLI subcommand surface. SPEC-025 adds `lore_claim`, `lore_release`, `lore_evidence_add`, `lore_ready` (`by` is a required arg on these — MCP callers pass actor identity explicitly, unlike the CLI's `$LORE_ACTOR`/OS-username fallback). `lore_evidence_add`'s `oracle` enum is sourced from `@lore/core`'s `ORACLE_KINDS` SSOT tuple (SPEC-038 §7 D3) and it gains an optional `ac_ref?: string` — pointer to a structured AC id declared on the plan's parent spec, passed through untouched (validation that it names a *declared* AC is `TaskWorkflowService.addEvidence`'s job, SPEC-038 §4 D4). SPEC-026 adds `lore_assess` (`plan_id_or_slug`, `diff_text?`, `ai?`) — unlike `lore_create`'s `ai` (default `false`, MCP is always-agent), assess has no non-AI mode: `ai: false` is a contradiction (always errors), and the mcp surface's built-in AI-off default does NOT brake it — only an explicit `ai.default_per_surface.mcp = false` config override does (`isAssessAiBraked` from `../../ai/resolve-ai.js`). SPEC-035 adds `lore_audit` (`id_or_slug?`, `actor?`, `action?`, `since?`, `limit?`, `verify?`) — `verify: true` runs the versions⋈audit completeness oracle (ignores the other query filters); otherwise a filtered `AuditFilters` query, optionally scoped to one doc via `id_or_slug`. SPEC-034 adds `lore_review` (`id_or_slug`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`) — mirrors the CLI's single-doc `lore review <doc>`: deterministic pre-checks (`runDeterministicChecks`, `@lore/core`) run first; any failure records a `decision: "reject"` judgment WITHOUT invoking the AI provider; otherwise `aiProviderService.judgeDoc` runs. No `ai` override field on this tool — the surface-brake check (`isAssessAiBraked`) runs unconditionally, same as the CLI. `lore_pending` gains `include_judgments?: boolean` — when true, each returned doc is enriched with `judgment: ReviewJudgment | null` (its latest review judgment via `judgmentService.latestFor`). SPEC-033 F1: `lore_approve` gains `calibration_note?: string` and, after a successful approve, runs the same surface-neutral `runCalibrationHook` (`../../flows/calibration-hook.ts`) the CLI `approve` command and the HTTP dashboard's approve route run — MCP is NOT a second-class adjudication surface. `lore_approve` is the only MCP adjudication tool that mutates doc status via `ReviewService`; there is no `lore_reject` MCP tool (no reject-side wiring exists to mirror). SPEC-039 adds `lore_verify` (`plan`, `ac?: string[]`, `task?`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`/`lore_evidence_add`/`lore_ready`) — the agent-facing equivalent of the CLI's `lore verify <plan>`: a thin pipe over `VerifyRunnerService.verifyPlan` (guarded against `App.verifyRunnerService` being the optional-typed `undefined` pre-existing test stubs may carry — production `App` always wires it). `ac` restricts the run to a subset of the parent spec's declared script-mode AC ids (omitted = every declared AC); `task` overrides claim-based target-task resolution. Returns `{task, results, skipped, warnings}` on success (`isError` only on a `LoreError` — e.g. ambiguous target task, no structured ACs declared, or a command launch failure; an executed AC that itself failed is NOT an MCP error, it's a `"fail"` entry in `results`, mirroring the CLI's exit-0-vs-exit-1 split between "invocation invalid" and "ran fine, assertion failed"). `attestation` is never an accepted field on `lore_evidence_add`'s schema — `TaskWorkflowService.recordVerifiedEvidence` (the sole injection point, SPEC-039 §2 D2) is never registered as an MCP tool; `lore_verify` is the only MCP-reachable path to attested evidence.

SPEC-040 §T3 D3: `lore_assess`'s response envelope gains an additive `summary: string` field (alongside the pre-existing `assessment`/`result`) — a compact Markdown digest built by `assess-render.ts::buildAssessSummaryText`, extracted into its own module (kept out of `tools.ts`, the tsc-hotspot file) so it's unit-testable without registering a full MCP server. It renders the same legacy shape (verdict/AC table/gaps/recommendations/judge line) as the CLI's `formatAssessmentSummary`, additively extended with SPEC-040 typed-field tables (dimension scores, typed gaps, typed recommendations, rubric warnings) — Markdown pipe tables (not the CLI's Unicode box-drawing), escaped for `|` characters in judge-authored text via a local `escapeCell` helper.

## Files

- `index.ts` — `startMcpServer(app)`; wires `McpServer` + `StdioServerTransport`.
- `tools.ts` — 23 tool registrations, schema constants, Zod input shapes.
- `assess-render.ts` — `buildAssessSummaryText(result)` (SPEC-040 §T3 D3) — Markdown digest for `lore_assess`'s `summary` envelope field.
- `resources.ts` — MCP resource registrations (corpus snapshots, etc.).
- `schema-info.ts` — `CORPUS_SCHEMA_INFO` constant describing doc types and `extra` requirements (knowledge `sub_type` includes `"assessment"`, SPEC-026).
