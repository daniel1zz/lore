# Module: adapters/mcp

## Purpose

MCP (Model Context Protocol) stdio adapter. Entered via `lore --mcp-server` (top-level flag intercepted in `packages/lore/src/index.ts`) or `lore agent`. Registers 31 `lore_*` tools (SPEC-054 adds `lore_uat_record` — the sole MCP write path for a structured UAT verdict; `plan` + `by` + `verdict` reusing `uatVerdictSchema`, thin pipe over `UatService.record`) (16 original + 4 SPEC-025 task-workflow tools + 1 SPEC-026 assess tool + 1 SPEC-035 audit tool + 1 SPEC-034 review tool + 1 SPEC-039 verify tool + 1 IoC vertical-slice tech-spec §4.1/§11 P4 feed tool + 2 SPEC-041 session tools: `lore_bootstrap`, `lore_handoff` + 1 SPEC-042 session tool: `lore_anchor_set` + 1 SPEC-043 tool: `lore_invalidate` + 1 SPEC-044 tool: `lore_staleness_probe`) and a small set of MCP resources against `@modelcontextprotocol/sdk`'s `McpServer` and connects over `StdioServerTransport`.

## Key Invariants

- **Never throws across the MCP boundary.** Every tool handler returns `{ content: [text] }` on success or `{ content: [text], isError: true }` on failure. Map service `LoreError` codes inside the handler — do not let them propagate.
- **3-arg `server.tool(name, desc, handler)` registration, then patch `inputSchema`** — see `tools.ts` header comment. The 4-arg overload with an inline ZodRawShape causes tsc to OOM (>7 GB heap) across 16 call sites. The current pattern (`registerToolWithArgs` helper, post-registration `inputSchema = z.object(...)` patch) keeps tsc check-time within seconds. **Do not rewrite to the 4-arg form.** Source: ADR-01KVYFJ5G8EVB6S5NMD3PNY5KA "Fast Path" Pattern 1.
- **Schema constants are module-level `z.object(...)` declarations**, not inline literals. Re-using `DOC_TYPE_ENUM` / `DOC_STATUS_ENUM` keeps tsc from re-resolving the shape per call site.
- **One registration per tool name.** Re-registering the same name corrupts the SDK's `_registeredTools` map.
- **Idempotent transport lifecycle** — `startMcpServer(app)` awaits `server.connect(transport)` and blocks until the transport closes. Caller is responsible for `app.close()` after return.

## Patterns

- **App is the only dependency** — `registerTools(server, app)` and `registerResources(server, app)` receive the wired App; tools never touch a store or service constructor directly.
- **`schema-info.ts` carries `CORPUS_SCHEMA_INFO`** — a static description of the corpus shape exposed as an MCP resource. Update it when adding a new doc type or required `extra` field.
- **Tool naming convention: `lore_<verb>`** — `lore_create`, `lore_get`, `lore_set`, `lore_search`, `lore_list`, `lore_tree`, `lore_link`, `lore_pending`, `lore_approve`, etc. Mirrors the CLI subcommand surface. SPEC-025 adds `lore_claim`, `lore_release`, `lore_evidence_add`, `lore_ready` (`by` is a required arg on these — MCP callers pass actor identity explicitly, unlike the CLI's `$LORE_ACTOR`/OS-username fallback). `lore_evidence_add`'s `oracle` enum is sourced from `@lore/core`'s `ORACLE_KINDS` SSOT tuple (SPEC-038 §7 D3) and it gains an optional `ac_ref?: string` — pointer to a structured AC id declared on the plan's parent spec, passed through untouched (validation that it names a *declared* AC is `TaskWorkflowService.addEvidence`'s job, SPEC-038 §4 D4). SPEC-026 adds `lore_assess` (`plan_id_or_slug`, `diff_text?`, `ai?`) — unlike `lore_create`'s `ai` (default `false`, MCP is always-agent), assess has no non-AI mode: `ai: false` is a contradiction (always errors), and the mcp surface's built-in AI-off default does NOT brake it — only an explicit `ai.default_per_surface.mcp = false` config override does (`isAssessAiBraked` from `../../ai/resolve-ai.js`). SPEC-035 adds `lore_audit` (`id_or_slug?`, `actor?`, `action?`, `since?`, `limit?`, `verify?`) — `verify: true` runs the versions⋈audit completeness oracle (ignores the other query filters); otherwise a filtered `AuditFilters` query, optionally scoped to one doc via `id_or_slug`. SPEC-034 adds `lore_review` (`id_or_slug`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`) — mirrors the CLI's single-doc `lore review <doc>`: deterministic pre-checks (`runDeterministicChecks`, `@lore/core`) run first; any failure records a `decision: "reject"` judgment WITHOUT invoking the AI provider; otherwise `aiProviderService.judgeDoc` runs. No `ai` override field on this tool — the surface-brake check (`isAssessAiBraked`) runs unconditionally, same as the CLI. `lore_pending` gains `include_judgments?: boolean` — when true, each returned doc is enriched with `judgment: ReviewJudgment | null` (its latest review judgment via `judgmentService.latestFor`). SPEC-033 F1: `lore_approve` gains `calibration_note?: string` and, after a successful approve, runs the same surface-neutral `runCalibrationHook` (`../../flows/calibration-hook.ts`) the CLI `approve` command and the HTTP dashboard's approve route run — MCP is NOT a second-class adjudication surface. `lore_approve` is the only MCP adjudication tool that mutates doc status via `ReviewService`; there is no `lore_reject` MCP tool (no reject-side wiring exists to mirror). SPEC-039 adds `lore_verify` (`plan`, `ac?: string[]`, `task?`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`/`lore_evidence_add`/`lore_ready`; `allow_new_commands?: boolean`, SPEC-039 §M2) — the agent-facing equivalent of the CLI's `lore verify <plan>`: a thin pipe over `VerifyRunnerService.verifyPlan` (guarded against `App.verifyRunnerService` being the optional-typed `undefined` pre-existing test stubs may carry — production `App` always wires it). `ac` restricts the run to a subset of the parent spec's declared script-mode AC ids (omitted = every declared AC); `task` overrides claim-based target-task resolution. Returns `{task, results, skipped, warnings}` on success (`isError` only on a `LoreError` — e.g. ambiguous target task, no structured ACs declared, a command launch failure, or (§M2) an unapproved command with `allow_new_commands` not `true`; an executed AC that itself failed is NOT an MCP error, it's a `"fail"` entry in `results`, mirroring the CLI's exit-0-vs-exit-1 split between "invocation invalid" and "ran fine, assertion failed"). `attestation` is never an accepted field on `lore_evidence_add`'s schema — `TaskWorkflowService.recordVerifiedEvidence` (the sole injection point, SPEC-039 §2 D2) is never registered as an MCP tool; `lore_verify` is the only MCP-reachable path to attested evidence. **SPEC-039 §M2 trust-hardening (2026-07-13)** — `lore_verify`'s handler NEVER supplies a `confirmUnapprovedCommand` callback to `verifyPlan` (MCP is non-interactive by design, unlike the CLI's TTY prompt) — `allow_new_commands: true` (default `false`) is the ONLY way an MCP caller approves a new/changed script-AC command; omitted or `false` on an unapproved command returns `isError` with `code: "NEEDS_APPROVAL"` naming the `ac_id`/`command`. The env-allowlist (`verify.env.*` config) and per-AC `attestation.first_seen` annotation apply identically regardless of caller surface — both are resolved inside `VerifyRunnerService`, not this adapter.

SPEC-040 §T3 D3: `lore_assess`'s response envelope gains an additive `summary: string` field (alongside the pre-existing `assessment`/`result`) — a compact Markdown digest built by `assess-render.ts::buildAssessSummaryText`, extracted into its own module (kept out of `tools.ts`, the tsc-hotspot file) so it's unit-testable without registering a full MCP server. It renders the same legacy shape (verdict/AC table/gaps/recommendations/judge line) as the CLI's `formatAssessmentSummary`, additively extended with SPEC-040 typed-field tables (dimension scores, typed gaps, typed recommendations, rubric warnings) — Markdown pipe tables (not the CLI's Unicode box-drawing), escaped for `|` characters in judge-authored text via a local `escapeCell` helper.

IoC vertical-slice tech-spec §4.1/§11 P4 adds `lore_feed` (`checkpoint`, `parent_id_or_slug?`) — the MCP counterpart to `lore feed`, always succeeding for the gate-checkpoint branch (`buildFeed`, `../../flows/feed-flow.ts`): an unknown checkpoint, no approved skill, or an unresolvable parent all degrade to an advisory note in the response, never `isError`.

**SPEC-041 §3 D2, D3, D5, D6 (session bootstrap + lossless handoff)** extends `lore_feed` and adds two new tools:
- `lore_feed` gains `plan?`/`handoff?`/`by?` fields; `checkpoint === "session-resume"` is a SEPARATE dispatch (`buildResumeFeed`/`SessionService.resume`, D5) consulted BEFORE the `CHECKPOINT_PRODUCED_TYPE` lookup — deliberately NOT a `CHECKPOINT_PRODUCED_TYPE` entry. Unlike the gate-checkpoint branch (never fails), this dispatch CAN return `isError` — an unresolvable `plan`/`handoff` is `SessionService.resume`'s own documented input error, not an advisory-degrade case. Response shape: `{checkpoint: "session-resume", resume: ResumeResult, feed: string}`.
- `lore_bootstrap` (`by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`/`lore_evidence_add`/`lore_ready`/`lore_review`/`lore_verify`) — the S1 volatile session pointer-set, thin pipe over `SessionService.bootstrap`. Response: `{report: BootstrapReport}`. Read-only — zero store mutations.
- `lore_handoff` (`by` — required; every other field is `handoffExtraSchema`'s typed shape verbatim — `LoreHandoffSchema` REUSES `handoffExtraSchema` directly rather than redeclaring it, SSOT) — the sole write path for a `knowledge`/`sub_type: "handoff"` doc besides `lore handoff` (writer-identity guard, D4). Response: `{doc: DocRecord}`. `registerToolWithArgs`'s `schema` parameter type had to widen its Input generic to `unknown` (from the implicit `Input = T` default) to accept `handoffExtraSchema`'s `.default([])`-bearing array fields, whose Input type (pre-default, optional) differs from its Output type (post-default, required) — see that function's JSDoc in `tools.ts` for the full mechanism; every pre-existing schema (Input === Output) is unaffected.

**SPEC-042 §Design Decisions D2, D3, D7, D9 (session registry + file-anchor claim safety)**:
- `lore_claim` gains optional `machine`/`worktree` (alongside the pre-existing `branch`) — BOTH explicit-only on this surface (no ambient server-side auto-capture; the MCP server process's own hostname/cwd would describe the server, not the caller). The CLI auto-captures `machine` as `os.hostname()`; MCP callers must pass it themselves.
- `lore_create` gains optional `file_anchors: string[]` (task branch only) — merged into `extra.file_anchors` by the handler before the call reaches `CorpusService.create`, the single validation + normalization gate (`normalizeFileAnchors`, `@lore/core`); a malformed entry fails loud with `VALIDATION_ERROR`, mirroring the CLI's repeatable `--anchor` flag.
- `lore_anchor_set` (`id_or_slug`, `anchors: string[]`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`) — declarative REPLACE of a task's `file_anchors` via `TaskWorkflowService.setAnchors`, read-modify-write (preserves `extra.claim`/`extra.verification_evidence` untouched, AC-S3-5) — deliberately NOT routed through `lore_set`'s wholesale-`extra` replace (D3).
- `lore_ready`'s response (`{ready: ReadyReport}`) is now the FULL `ReadyReport` object (`{records, sessions, anchor_conflicts}`) — `TaskWorkflowService.ready`'s return type changed from a flat `ReadyRecord[]` to this wrapper (D7); the handler needed no code change (it already passed `result.value` through verbatim), only this documented shape change. `lore_bootstrap`'s `BootstrapReport.active_sessions` (same `ReadySession[]` shape, corpus-wide scope) was already wired by the SPEC-042 T1 slice.

**SPEC-043 §Design Decisions D2, D6, D11 (bi-temporal invalidation, T2)**:
- `lore_invalidate` (`id_or_slug`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`; `superseded_by?`, `reason?`, `undo?`) — the SOLE MCP write path for a `knowledge`/`adr` doc's `extra.validity`, thin pipe over `ValidityService.invalidate`. Response `{doc, decision_status_unchanged?}` — the SAME shape `lore invalidate --json`'s `data` field carries (structural parity, not a spawned-CLI comparison; both call sites invoke `ValidityService.invalidate` with identical opts).
- `lore_get` gains a computed `validity_state: {invalidated, invalid_at?, invalidated_by_slug?, reason?}` field on every response (`computeValidityState`, `../../flows/validity-state.js` — shared with the HTTP doc route, review U3: MCP agents parse JSON, never markdown banners). `invalidated_by_slug` is resolved via one `corpusService.get` call, which applies no `deleted_at` filter — a soft-deleted successor still resolves (the "(deleted)" text marker is a CLI/export-docs projection-only concern, not part of this structured field).
- `lore_create` gains optional `supersedes`/`by` (SPEC-043 D11) — when `supersedes` is set, composes `corpusService.create` THEN `ValidityService.invalidate` via the SAME `createWithSupersedes` orchestration (`../../flows/supersede-flow.js`) the CLI's `lore create --supersedes` uses. `by` is then required (runtime-checked, not schema-level, since it's only meaningful in this branch) — omitting it is a `VALIDATION_ERROR`. Half-failure (create ok, invalidate fails) still returns success (the doc is real) with an additive `supersede_error`/`supersede_repair_command` field — loud orphan, never silent, mirroring the CLI's nonzero-exit + stderr repair line.
- `lore_search`/`lore_list` gain optional `include_invalid?: boolean` (excluded by default, mirrors the CLI's `--include-invalid`).
- `lore_list` gains optional `limit?`/`offset?` and pushes them into the store query (previously it fetched everything then `.slice()`d in memory — the real unbounded-payload bug). Because MCP callers are always agents, an omitted `limit` applies a default cap of `MCP_LIST_DEFAULT_LIMIT = 100`; an explicit `limit` overrides it verbatim. Every response carries `truncated: boolean`, derived from a `limit+1` probe fetch (no separate COUNT). This default cap is MCP-only — the CLI `lore list` stays unbounded when no `--limit` is passed. No silent cap: `truncated` always surfaces when more rows exist.
- **`executeBatchOp` validates each op's `args` against the same Zod input shape the single-op tool uses** before dispatching to the service (previously `create`/`set`/`link` cast `args` straight to the param type with only ad-hoc `typeof` checks). A malformed batch op returns a per-op validation error entry in the existing batch-error shape — fail loud, consistent with the `registerToolWithArgs` Zod-boundary invariant every other tool follows.

**SPEC-044 §Design Decisions D10, D14 (staleness probes)**:
- `lore_staleness_probe` (`limit?`, `min_age_days?`, `id_or_slug?`, `list?`, `by` — required, same MCP actor-identity precedent as `lore_claim`/`lore_release`/`lore_review`; ALSO load-bearing here as the audit-row actor for every probe the call commissions, D4) — batch (`limit`/`min_age_days` override `workflow.staleness.*` config for this call only; `App` carries no parsed `LoreConfig`, so the OMITTED-arg fallback is a literal `5`/`14` mirroring the config schema's own defaults, same "hardcoded default mirrors the schema" precedent `AIProviderService`'s `stalenessBudgets` constructor default uses) / single-doc (`id_or_slug` set, bypasses selection filters, still refuses an already-invalidated target) / list (`list: true`, a pure read — ZERO provider calls, exempt from the AI surface-brake check). The `{probes, skipped, total_candidates, excluded_by_limit}` (batch/single) and `{docs, total}` (list) response shapes are built by `../../flows/staleness-flow.js`'s `buildStalenessBatchJsonPayload`/`buildStalenessSingleJsonPayload`/`buildStalenessListJsonPayload` — the SAME functions the CLI's `lore review --staleness --json` calls, so the two surfaces' payloads are identical BY CONSTRUCTION (never two independently-authored JSON envelopes to keep in sync).
- `lore_status`/`lore_bootstrap` gain a computed `open_stale_candidates` count (D14), spliced in by the tool handler itself via `../../flows/staleness-flow.js::listFreshStalenessEscalates` — the SAME query `lore_staleness_probe {list: true}` runs (one derivation site) — rather than inside `CorpusService.status`/`SessionService.bootstrap` (service files outside this feature's adapter-layer scope).

**SPEC-045 §Design Decisions D5, D7 (doc-code drift oracle) — NO new tool, three existing tools change**:
- `lore_status` MIGRATED off its argless 3-arg `server.tool()` registration onto `registerToolWithArgs` — its FIRST input schema, `LoreStatusSchema = {check_drift?: boolean}`. Omitted/`false` → the response is byte-identical to pre-SPEC-045 (REGRESSION); `true` → the response additionally gains `code_drift: CodeDriftPayload` (`../../flows/drift-flow.js::runDrift` against `buildDriftFlowDeps(app, app.driftCheckService)` + the real `../real-fs-probe.js::buildRealFsProbe(process.cwd())` — the SAME `code_drift` shape CLI `lore status --check-drift --json`'s `data.code_drift` carries, one shared payload builder). MCP carries no parsed `LoreConfig` (same limitation `lore_staleness_probe`'s `limit`/`min_age_days` fallback documents) — `workflow.drift.enabled` cannot be honored from this surface, so MCP always runs the check (enabled) when `check_drift: true` is passed.
- `lore_anchor_set` gains resolve-then-dispatch by target doc type (mirrors the CLI's `lore anchor`): task target stays byte-identical (declarative REPLACE via `TaskWorkflowService.setAnchors`, incl. loud `#` rejection, REGRESSION); spec target is ALSO declarative REPLACE but via `DriftCheckService.setCodeAnchors` — **this DIVERGES from the CLI's `lore anchor add`/`rm`, which are INCREMENTAL** (union/difference) — the tool's description states this explicitly, and `by` is accepted for schema uniformity but not consumed on the spec branch (spec anchor writes are attributed to `"system"`, mirroring `AcService`); any other target type → `isError: true`, naming "task or spec".
- `lore_bootstrap` gains a computed `code_anchor_specs` count (store-only, ZERO fs probing — `../../flows/drift-flow.js::countArmedSpecs`), spliced onto `report.corpus` alongside the pre-existing `open_stale_candidates`, same "one shared derivation site, computed by the adapter handler itself" pattern as D14 above.
- Tool count stayed 30 through SPEC-045 (`expectedTools` in `packages/lore/tests/unit/adapters/mcp-tools.test.ts`); SPEC-054 later added `lore_uat_record`, bringing it to 31.

## Files

- `index.ts` — `startMcpServer(app)`; wires `McpServer` + `StdioServerTransport`.
- `tools.ts` — 31 tool registrations, schema constants, Zod input shapes.
- `assess-render.ts` — `buildAssessSummaryText(result)` (SPEC-040 §T3 D3) — Markdown digest for `lore_assess`'s `summary` envelope field.
- `resources.ts` — MCP resource registrations (corpus snapshots, etc.).
- `schema-info.ts` — `CORPUS_SCHEMA_INFO` constant describing doc types and `extra` requirements (knowledge `sub_type` includes `"assessment"`, SPEC-026).
