# Module: adapters/cli

## Purpose

citty-based CLI adapter. 31 subcommands, each in its own `commands/<name>.ts`, lazily imported by `index.ts`. Thin adapter only — no business logic; every command resolves args, calls a service via the App composition root, formats the result, and exits.

## Key Invariants

- **No business logic.** Commands resolve args → call `app.<service>.<method>()` → render output → map error to exit code. New rules belong in `packages/lore/src/service`, not here.
- **DB discovery + App construction live in `loader.ts`, not `utils.ts`.** `loader.ts` imports `bun:sqlite` (via `app.ts`); `utils.ts` is vitest-reachable and must stay sqlite-free. Commands that need an App import `loadLoreApp` from `loader.ts`; commands that only format errors import from `utils.ts`.
- **`loadLoreApp()` always returns `App` (never `Result<App>`).** It strips `config.sync` before passing to `createApp`, so corpus-level commands never hit the TursoStore-failure path. Sync-aware commands (`lore sync ...`) manage TursoStore themselves.
- **`init`, `sync`, and `setup` commands bypass `loadLoreApp`** — `init` runs before a DB exists; `sync` manages TursoStore directly; `setup` (SPEC-046) targets `~/.claude`/a repo BEFORE any corpus exists (its `--project` path bootstraps the corpus itself via `flows/init-corpus.ts`). Document the exemption when adding a new bootstrap-stage command.
- **Telemetry must be wired (AC-K3-1)** — `loadLoreApp` always parses `.lore/config.yaml` (failures fall back to `NoOpTelemetry`) so user telemetry preferences apply to every command. Don't call `createApp(dbPath)` directly from a command.
- **Exit codes per SPEC-003 §5** — mapping is centralised in `utils.ts::exitCode`. `1 = STORE_ERROR / unknown`, `3 = DOC_NOT_FOUND | SLUG_NOT_FOUND`, `4 = validation / lifecycle / link errors`, `5 = STALE_VERSION | CLAIM_CONFLICT`, `6 = AI_PROVIDER_ERROR`, `7 = NEEDS_APPROVAL` (SPEC-039 §M2 — the `lore verify` command-provenance approval gate). The default branch uses an exhaustive `never` check; add new `LoreError` codes here too. `verify` (SPEC-039) additionally maps a NON-`LoreError` business outcome — "the service call succeeded but at least one executed AC's command exited non-zero" — to exit `1` too (the same "ran fine, an assertion failed" bucket `STORE_ERROR` already occupies), independently of `exitCode()`; see `verify.ts`'s header comment for the full rationale.
- **Actor resolution for workflow commands (SPEC-025)** — `claim` / `release` / `evidence` resolve the acting identity via `utils.ts::resolveActor`: `--by` flag > `$LORE_ACTOR` env var > OS username. Never silently falls back to an empty string.
- **`assess-render.ts` is split out of `commands/assess.ts` for testability (SPEC-040 §T3 D3)** — `commands/assess.ts` transitively imports `loader.ts` (`bun:sqlite`), which vitest cannot resolve, so `formatAssessmentSummary` (verdict + AC table + gaps/recommendations + judge line, additively extended with SPEC-040 typed-field tables — dimension scores, typed gaps, typed recommendations, rubric warnings — all presence-guarded so a legacy-only `AssessmentResult` renders unchanged) lives in its own module importing only `@lore/core` + `./utils.js`. `commands/assess.ts` imports it rather than defining it inline. Mirrors `../mcp/assess-render.ts`'s split for the same reason on the MCP side.
- **`pending-render.ts` (`commands/pending.ts`) and `create-task-validation.ts` (`commands/create.ts`) are split out for testability, same reason as `assess-render.ts`/`review-render.ts` (SPEC-065)** — `PENDING_TABLE_HEADERS`/`buildPendingTableRows` (D3, AC-065-4 — the Slug column addition alongside the pre-existing truncated 10-char ID column) and `checkTaskCreateRequiredFlags`/`formatTaskCreateMissingFlagsError`/`inferTaskParentId` (D4, AC-065-5/6 — single-pass missing-flag aggregation for `--plan-id`/`--parent`, plus `--parent`-defaults-to-resolved-`--plan-id` inference) live in `adapters/cli/` (sibling to `commands/`), imported by their respective command files verbatim.
- **`review-render.ts` is split out of `commands/review.ts` for testability, same reason (SPEC-044 §Design Decisions D11)** — `formatJudgmentSummary` (moved verbatim, byte-identical to pre-SPEC-044) plus `renderSupersededCandidateNudgeBlock` (the D11 byproduct — `""` when `judgment.superseded_candidate` is absent, a REGRESSION-safe no-op concatenation). It imports `../../flows/staleness-flow.js` (also vitest-safe — see that module's own note below) rather than `App`/`loader.ts`. **SPEC-053**: adds `renderAdvisoryBlock(judgment)` — pure (no injected deps, unlike the superseded nudge), `""` no-op when `judgment.advisory` is absent/empty (REGRESSION-safe), else a labelled non-blocking `Advisory (non-blocking):` list of the v2 judge's AC-quantifiability findings; `commands/review.ts` concatenates it between `formatJudgmentSummary` and the superseded nudge block.
- **Implicit calibration capture (SPEC-035 §3, hoisted surface-neutral SPEC-033 F1)** — `approve` / `reject` call the shared `../../flows/calibration-hook.ts::runCalibrationHook` after their `ReviewService` call succeeds. It is a byproduct, never a gate: a calibration write failure prints a stderr warning + records telemetry but never changes the command's exit code (still 0). The hook lives in `flows/`, not under this adapter — the HTTP dashboard's approve/reject routes (`../http/dashboard-routes.ts`) call the SAME function so calibration data is never adapter-specific. `calibration-hook.ts` takes a narrowed `{judgmentService, telemetry, onWarning?}` dependency shape (not the full `App`) so it stays unit-testable without a real store; `onWarning` is the additive hook HTTP/MCP callers use to surface a failure in their own response shape instead of stderr.
- **`flows/staleness-flow.ts` DOES import `type { App }` from `../app.js` and is STILL vitest-safe (SPEC-044)** — unlike `calibration-hook.ts`'s hand-rolled narrow deps, this module exports a convenience binder (`buildStalenessFlowDeps(app: App): StalenessFlowDeps`) alongside its narrow-deps-only public functions. `import type` is erased at compile time (no runtime import statement is ever emitted), so this does NOT pull `bun:sqlite` into a vitest resolution graph — proven by the PRE-EXISTING precedent `flows/validity-state.ts` (`import type { App }` too), transitively reachable from `routes.test.ts`, an already-passing vitest suite. Every OTHER public function in `staleness-flow.ts` still takes `StalenessFlowDeps` directly (never `App`), so a test can construct one from plain fakes with zero real store, same testability guarantee as `calibration-hook.ts`.
- **`stdio-sync.ts::installSyncStdio()` is wired at the TOP of `../../index.ts`'s CLI branch (SPEC-048 follow-up task `task-skill-implement-cli-stdout-non-blocking-truncation-fix-writ`) — before `citty`/consola are imported, and NEVER on the `--mcp-server` branch.** Root cause: Bun 1.3.10 sets fd 1 to O_NONBLOCK the first time `process.stdout` is getter-accessed in a process; `consola` (imported transitively by every command via `citty`) does this at import time, so every CLI invocation's fd 1 ends up non-blocking whether or not the command itself touches `process.stdout`. Once non-blocking, a single `console.log`/one-shot `fs.writeSync` call delivers at most ~64KiB to a slow-draining reader and silently drops the rest at process exit (real-world trigger: `lore setup --dry-run --json`'s ~135KB payload truncated under full-test-suite load, `SyntaxError: Unterminated string in JSON`). `installSyncStdio()` replaces `console.log/info/debug/warn/error` with a `writeAllSync`-backed implementation that loops through short writes and EAGAIN retries until every byte is delivered — see `stdio-sync.ts`'s module header for the full empirical chain + minimal repro command. Out of scope: `process.stdout.write` call sites (e.g. `export-docs`) are untouched — small, already-working line writes, not this defect's blast radius.
- **`setup-args.ts`'s `resolveBinPath`/`resolveAssetsRoot` realpath-resolve the compiled binary's `execPath` before deriving paths (SPEC-048 §Design D8)** — the ONE npm-layout assumption this covers: `node_modules/.bin/<name>` is a SYMLINK into the package's own `node_modules/<pkg>/dist/lore`, so deriving `assetsRoot` from the UNRESOLVED symlink path would compute `node_modules/.bin/../assets` (nonexistent) instead of the real package's `node_modules/<pkg>/assets`. This is otherwise the module's ONE controlled `fs` read (`resolveRealExecPath`, read-only, try/catch — a realpath failure falls back to the unresolved `execPath` rather than throwing; a resulting nonexistent `assetsRoot` is still caught loud by `RealAssetSource.load()`, unchanged from before). It covers a symlink chain rooted in the binary's own real package directory ONLY — a compiled binary physically COPIED (not symlinked) away from its package dir (e.g. `cp dist/lore /usr/local/bin/lore`) remains UNSUPPORTED until a P3 binary-embedded-assets payload; realpath of a hard-copied file just returns that same wrong location, there's no symlink to follow back to the real package tree.

- **Strict unknown-flag rejection is a single seam (SPEC-051 D1)** — citty's `parseArgs` never passes an `unknown` handler, so undeclared flags were silently accepted (real incidents: `link --kind blocks` → silent default `relates-to`; `approve --by` → silent OS-user attribution). `strict-flags.ts::findUnknownFlag` (pure; mirrors citty 0.1.6's name/alias/`--no-X` rules) + `wrapCommandStrict` (recursive over `subCommands`) are applied once per top-level lazy import in `index.ts::wrapDefault` — never per-command edits. Violation → `Unknown option: --<flag>` + help pointer, exit 2 (the codebase's own usage-error convention; citty's internal missing-arg path exits 1 — documented divergence in the module header). `approve`/`reject` take canonical `--by` with `--reviewer` as alias (conflicting values → exit 2), resolved via `utils.ts::resolveActorAlias`.

## Patterns

- **Subcommands are lazy ES module imports** — `index.ts` defines `subCommands: { create: () => import("./commands/create.js").then(m => m.default) }`. Keeps cold-start cheap; each command file's deps are not loaded unless invoked.
- **`findLoreDbPath` walks `cwd` → root** looking for `.lore/lore.db`. Exits with code 1 + `lore init` hint when absent.
- **Output helpers in `utils.ts`** — `formatTable`, `formatTree` (Unicode box drawing), `formatNavigation`, `relativeTime`. Pure; no `process.exit` calls. Reusable from tests.
- **Hyphen-quoted error mode** — `formatError` produces multi-line stderr output with contextual hints (`"Run \`lore get <id>\`..."`). Add a new case when introducing a new `LoreError` code.

## Subcommands

`requirement` (SPEC-055) — `lore requirement add <prd> <id> --statement --priority <P0|P1|P2>` / `list <prd>` / `rm <prd> <id> [--force]`: the sole structured writer of a PRD's `extra.requirements` inventory (thin pipe over `RequirementService`, mirrors `ac` one tier up). `lore ac add` gains a repeatable `--covers <R-id>` (→ `requirement_refs`) declaring which PRD requirements an AC covers. `lore status --check-requirements` (deterministic, zero-LLM, CI-runnable) audits every PRD's inventory against its descendant specs' AC `requirement_refs` — uncovered-P0 → exit 3, composing with `--check-tree`/`--check-drift` under the SAME pinned exit-precedence; `--json` emits `data.requirement_coverage = {checked, consistent, prds[]}`.

`gate` (IoC vertical-slice tech-spec §4.1/§11) — `lore gate spec-create --input-json '<json>'`: pre-flight, pure-predicate gate for a CANDIDATE spec-creation payload (`{type, title, parent_id?, content?, extra?: {spec_kind?}}`, the same shape as `lore_create`'s input), run BEFORE the doc is actually created. `LORE_GATE_BYPASS=1` short-circuits to exit 0 before any parsing (escape hatch). Otherwise resolves `parent_id` via `corpusService.get` (missing/unresolvable → treated as no parent) and runs the three `../../service/gate-predicates.js` checks (`parentLegal` / `specKindValid` / `hasSkeleton`); all pass → `"gate: pass"`, exit 0. Any fail → discovers its feeding rule doc via `corpusService.findFeedingSkill("spec")` (P1 slice-2: any APPROVED `knowledge` doc with `sub_type: "skill"` and `extra.skill.applies_to === "spec"`, most-recently-updated wins — no longer a hardcoded title lookup; `scripts/seed-write-spec-rule.ts` seeds one such doc but discovery is scope-based, not title-based), builds a `../../service/gate-feeding.js::FeedingPack` (rule slice + parent slice + `missing` reasons) and prints `renderFeedingPack(pack)` to stdout, exit 4. No matching approved skill doc → the same placeholder fallback as before (backward-compat). `--input-json` missing/malformed/shape-mismatched → exit 2 (CLI-usage error, not a `LoreError`). Structured as a command GROUP (`subCommands: {"spec-create": ...}`) so a future `spec-promote` gate can join it without a breaking rename. Command group is a new addition to this module — its own subtree, no interaction with the 26 pre-existing flat subcommands above.

`lore gate plan-promote --plan <id-or-slug>` / `lore gate task-claim --task <id-or-slug> [--by <name>]` are the two "commit-time cross-tier gates" joining the same `gate` command group: each resolves its target's ancestor spec via `corpusService.getPlanBundle` (the SAME plan→parent-spec traversal `TaskWorkflowService.ready()` uses for the `upstream_unapproved` advisory — see `../../../service/checkpoint-registry.js`'s third module invariant) and dispatches through `checkpointRegistry["plan-promote"|"task-claim"]`. No spec-tier ancestor (prd-parented or unparented plan) ⇒ vacuous pass, never a failure. `plan-promote` requires the ancestor spec `approved` AND ≥1 declared acceptance criterion; `task-claim` requires the ancestor spec `approved` AND (SPEC-042 §Design Decisions D5, evaluated UNCONDITIONALLY — not gated by spec-ancestor presence) no fresh sibling claim in the same plan whose declared `file_anchors` overlap this task's own. `task-claim`'s `--by` (or `$LORE_ACTOR`/OS username, same resolution order as `lore claim`) supplies the candidate actor for the anchor-overlap predicate's "different actor" test; `buildAnchorGateContext` (`checkpoint-registry.js`) builds the SAME ctx shape both this pre-flight command and `TaskWorkflowService.claim`'s `GateEnforcer` path consume — this parity was a real drift bug (fixed 2026-07-11): before the fix, this command only ever built the upstream-spec ctx, so an anchor conflict silently vacuous-passed here while `lore claim` correctly blocked it. Exit 0 = pass (incl. vacuous, incl. `LORE_GATE_BYPASS=1`); 3 = target doesn't resolve; 4 = wrong doc type, a spec-tier ancestor exists but fails its predicates, or an anchor-overlap conflict blocks.

`feed` (IoC vertical-slice tech-spec §4.1/§11 P4; extended by SPEC-041 §3 D5) — `lore feed <checkpoint> [--parent <id-or-slug>] [--json]`: feed-before-produce PULL, the advisory counterpart to `gate` (PULL the governing rule ahead of writing instead of discovering it via a rejected write). Thin pipe over `../../../flows/feed-flow.js::buildFeed` — this slice only wires `spec-create` → `"spec"` via `CHECKPOINT_PRODUCED_TYPE`; an unknown checkpoint degrades to a one-line advisory note, never a failure. Exit code is ALWAYS 0 for this branch. `lore feed session-resume [--plan <id-or-slug>] [--handoff <id-or-slug>] [--by <name>] [--json]` is a SEPARATE dispatch (SPEC-041 §3 D5, `buildResumeFeed`/`SessionService.resume`), consulted BEFORE the `CHECKPOINT_PRODUCED_TYPE` lookup — deliberately NOT a `CHECKPOINT_PRODUCED_TYPE` entry (that map's absent-key branch yields the generic "unknown checkpoint" note, wrong for a real, wired capability). Prints the resolved handoff's full rendered content (the one deliberate pointers-only exception), an age line, a `⚠ handoff older than the configured TTL` warning past `workflow.handoff_ttl_minutes`, a live readiness pointer block, and a multi-actor header (`"N actors have handoffs"`) when `--by` is omitted and the corpus/plan has handoffs from more than one actor. Unlike the gate-checkpoint branch, THIS branch CAN fail — an unresolvable `--plan`/`--handoff` maps through the normal `exitCode()`/`formatError()` pipeline (VALIDATION_ERROR → 4); "no handoff recorded yet" is a fact (exit 0), not an error.

`bootstrap` (SPEC-041 §3 D1, D2) — `lore bootstrap [--by <name>] [--json]`: the S1 volatile session pointer-set a fresh session (agent or human) queries in ONE deterministic, read-only call. Thin pipe over `SessionService.bootstrap` — zero store mutations. Reports the root PRD pointer, active plans + task readiness counts, the pending-review queue (bounded slug sample), the caller's own claims (`--by` filters this field only — every other field is corpus-wide), armed gate checkpoints + their discoverable feeding-skill source, the newest handoff per plan, and a corpus-wide resume hint. Deliberately excludes the STATIC layer (architecture, conventions — that's CLAUDE.md/AGENTS.md's job, "Division of labor"). `--json` prints the raw `BootstrapReport`; the default text mode (`formatBootstrapReport`, same file) is a compact pointer-only block. An empty corpus is legal output (`root: null`, every array `[]`), not an error. `corpus.code_anchor_specs: N` (SPEC-045 §Design Decisions D5, D7) is the SAME store-only, zero-fs-probing declared-anchor count `lore status`'s plain-text branch shows, spliced in via the shared `../../../flows/drift-flow.js::countArmedSpecs` helper — `lore bootstrap` never fs-probes.

`handoff` (SPEC-041 §3 D3, D6) — `lore handoff [--json-file <path> | (--file... --decision... --next... [--failing-command --failing-tail-file])] [--plan] [--by] [--json]`: the SOLE CLI write path for a lossless session-continuity handoff document (`knowledge`/`sub_type: "handoff"`). PRIMARY path `--json-file <path>` — the file IS the `extra.handoff` SSOT (Zod-validated, field-precise errors, exit 2). Human convenience path: repeatable `--file` (→ `modified_files`), `--decision "<judgment>[@<confidence 0-100>]"` (→ `key_decisions`, trailing `@NN` split off by `parseDecisionFlag`), `--next` (→ `next_steps`, required — an empty `next_steps` is a `handoffExtraSchema` violation, exit 2: "a handoff naming no next step is a status report, not a handoff"), `--failing-command` + `--failing-tail-file` (mutually required, exit 2 if only one is passed). `--plan`/`--by` work with BOTH paths — explicit values override the json-file's own `plan_ref`/`by`; omitted, the json-file's values are left untouched. `--json-file` is mutually exclusive with any field flag (exit 2, naming the conflict). The pure candidate-assembly functions (`parseDecisionFlag`, `assembleHandoffInput`, `parseHandoffJsonFile`) live in the sibling `../handoff-input.js` module (NOT `commands/handoff.ts` itself), mirroring `assess-render.ts`'s split — `commands/handoff.ts` transitively imports `loader.ts` (`bun:sqlite`), which vitest cannot resolve, but `handoff-input.ts` imports only `@lore/core`, so `session-roundtrip.test.ts` (SPEC-041 §4 AC-SL-7) can exercise both authoring paths without spawning a subprocess. There is deliberately no `--content`/`--content-file` flag — `content` is always the deterministic `renderHandoffContent(extra.handoff)` projection, never hand-authored. Direct `lore create knowledge --sub-type handoff` is rejected by `CorpusService._createImpl`'s writer-identity guard (VALIDATION_ERROR naming `lore handoff` as the sole legitimate writer) — see `create.ts`'s `KNOWLEDGE_SUB_TYPES` SSOT-import note below.

**Hook integration (SPEC-041 §3 D7 — REVERSED 2026-07-20, owner directive: `lore setup` now auto-registers a declared "core governance + security" subset of its vendored `assets/hooks/*` into `<claude-dir>/settings.json`).** Previously `lore setup` only COPIED hook files into `<claude-dir>/hooks/` — the `settings.json` PreToolUse/SessionStart/Stop/SubagentStart wiring that makes a copied file actually run was left entirely to the operator ("Lore does not install or manage hooks"). `@lore/core`'s `distribution-hooks.ts` (`HOOK_REGISTRATIONS`/`buildHookSettingsEntries`) is now the SSOT for 8 hooks auto-registered by every `lore setup` run — `pre-bash-git-safety-gate.mjs`, the four `lore-gate-g{1..4}-*.sh` checkpoints, `session-start-resume.mjs`, `stop-doc-sync.mjs`, `subagent-context.mjs` — deliberately EXCLUDING `pre-subagent-gate.mjs`/`pre-no-general-agent-gate.mjs` (orchestration-POLICY hooks, not governance/security, per that module's doc comment). `RealAssetSource` appends a synthetic `settings.json`/`kind: "settings-hook"` asset (content = `buildHookSettingsEntries("{{CLAUDE_DIR}}")`, a target-agnostic placeholder token); `SetupService.resolvePayload` substitutes the real `targetDir` for the placeholder in every hook `command`, THEN merges via `@lore/core`'s `mergeSettings` (`command`-string identity key) against the target's on-disk `settings.json` — a re-run is idempotent (zero writer calls when byte-identical) and `uninstall` restores a pre-existing foreign `settings.json` byte-identically via the pre-existing manifest+backup mechanism (unchanged — `settings.json` was already a manifest-tracked merge-target file before this reversal, only the REAL asset source previously never fed it any content). `bootstrap` is additionally SessionStart-hook-authorable on its own terms — it is a deterministic, read-only, zero-argument-from-the-agent call, so a shell hook can invoke it directly. `handoff` is NOT hook-authorable the same way — `key_decisions`/`next_steps` exist only in the agent's own context, a shell hook has no access to them. The honest integration model for an OPERATOR'S OWN custom (non-vendored) hook scripts, unaffected by the auto-registration above:

```bash
# SessionStart hook — script-authorable (bootstrap is deterministic + read-only)
lore bootstrap --by "$LORE_ACTOR" --json
# Optionally follow the printed resume_hint straight into a resume read:
# lore feed session-resume --plan <resume_hint.plan_slug> --handoff <resume_hint.handoff_slug>

# Stop / PreCompact hook — REMINDS the agent, does not author the handoff itself.
# Two legitimate shapes for this hook, per D7:
#   (a) a blocking prompt telling the agent to run `lore handoff` before exiting
#       (preferred — the agent supplies real key_decisions/next_steps); or
#   (b) a degraded, git-only capture when the agent cannot be prompted in time —
#       modified_files ONLY, no decisions, explicitly marked `degraded: true`:
lore handoff --by "stop-hook" \
  --next "review uncommitted changes" \
  --json-file <(git status --porcelain | awk '{print $2}' | \
    jq -R -s '{by: "stop-hook", modified_files: (split("\n") | map(select(length > 0))), next_steps: ["review uncommitted changes"], degraded: true}')
```

Shape (b) is a LAST RESORT, not the default path — a degraded handoff's `key_decisions` is always `[]`; `renderHandoffContent` prints a visible `⚠ degraded (git-only capture — no key decisions recorded, next_steps may be incomplete)` marker so a resuming session never mistakes it for a fully-authored one. This particular pattern (a custom Stop/PreCompact reminder script) is still operator-authored and NOT auto-registered by `lore setup` — only the 8 declared `assets/hooks/*` files above (including `hooks/lore-gate-g1-spec-create.sh` etc., which per the reversal above ARE now auto-wired into `settings.json`) get automatic `settings.json` registration; any additional custom hook an operator writes still needs manual wiring, same as before.

`ac` (SPEC-038 §4, §6) — `lore ac add <spec> <id> --statement <s> --mode <script|ai|human> [--oracle --command | --rubric | --note]` / `lore ac list <spec> [--json]` (renders `✔/✘/·` coverage badges when the spec has a child plan, plus a dangling-ids note) / `lore ac rm <spec> <id> [--force]` (exit 4 if any task evidence still references the id, unless `--force`). Thin pipe over `AcService`; candidate criterion objects are assembled untyped from CLI flags and validated entirely by `specAcceptanceCriteriaSchema` (single source of truth for mode-specific required fields).

`verify` (SPEC-039 §2, §3, §4 AC-VRF-10; §M2 trust-hardening AC-VRF-13..18) — `lore verify <plan> [--ac <id> repeatable] [--task <t>] [--by] [--json] [--allow-new-commands|--yes]`: trusted runner, thin pipe over `VerifyRunnerService.verifyPlan`. Actually EXECUTES every declared script-mode AC on the plan's parent spec (or the `--ac`-filtered subset — the flag may repeat, citty collapses repeated occurrences into a string array) against the resolved target task (`--task` override, else the plan's sole fresh claim via core's `resolveTargetTask`; 0 or >1 candidates → exit 4 listing every candidate slug), recording each outcome as runner-attested evidence (`result` derived from the command's exit code, never a caller assertion — contrast `lore evidence`, which is self-reported and whose `EvidenceInput` type structurally excludes `attestation`; the only production caller of the attestation-carrying `TaskWorkflowService.recordVerifiedEvidence` is this runner). Renders a per-AC pass/fail/timed-out line with `duration_ms`, a `[new]` suffix when `first_seen === true` (§M2), a skipped-ai/human-mode list, and any advisory warnings (e.g. parent spec not `approved`/`active` — never a hard gate). Exit codes: `0` all executed ACs passed (or none matched the selection — a clear notice prints, never silent); `1` at least one executed AC's command exited non-zero or timed out (a business outcome, NOT a `LoreError` — see `verify.ts`'s header for why it shares `STORE_ERROR`'s exit-1 bucket) OR a command failed to LAUNCH (`STORE_ERROR`, the run aborts, message lists every AC already recorded); `3` `DOC_NOT_FOUND`; `4` `VALIDATION_ERROR` (no parent spec / no structured ACs / unknown `--ac` id / ambiguous target task); `5` `STALE_VERSION`; `7` `NEEDS_APPROVAL` (§M2 — a new/changed command was rejected by the command-provenance approval gate; message names the exact `--allow-new-commands` recovery flag).

**§M2 trust-hardening (2026-07-13, review finding M2)** — three DEFAULT-ON layers, each independently config/flag-escapable, replacing the pre-M2 bare "full env passthrough, no approval" posture. (1) Env allowlist: a spawned command receives only `DEFAULT_VERIFY_ENV_ALLOWLIST` (`verify-spawn.ts`) + additive `verify.env.allowlist` config, never the full local environment (secrets like `LORE_SYNC_TOKEN` are scrubbed by default) — `verify.env.passthrough_all: true` restores full passthrough. (2) Command-provenance approval: a script AC's command not byte-identical to any prior entry in the target task's `extra.verification_evidence` (`isApprovedVerifyCommand`, `@lore/core`) requires approval before it runs — interactive TTY prompt (`process.stdin.isTTY && !args.json`, `promptYesNo` via `node:readline/promises`), or `--allow-new-commands`/`--yes` to approve every new/changed command in the run without prompting (required for CI/non-interactive invocations); neither → exit 7. A command already in evidence history is NEVER re-prompted. `verify.require_command_approval: false` disables the gate entirely. (3) Command-provenance annotation: an approved new/changed command's evidence carries `attestation.first_seen: true` — surfaced as the CLI's `[new]` suffix and `--json`'s `results[].first_seen`, computed independently of whether the gate is enabled. `verify.env.passthrough_all: true` + `verify.require_command_approval: false` together restore the exact pre-§M2 behavior.

`review` (SPEC-034 §4, §6) — `lore review <doc> [--by] [--ai|--no-ai] [--json]` / `lore review --pending [...]`: structured AI review judgment. Loads `lore.tree.yaml` if present (absence degrades the `tree_position` check to `"skipped"`, never fatal; a present-but-invalid blueprint IS fatal, mirrors `lore status --check-tree`), calls `corpusService.getReviewBundle` → `runDeterministicChecks` (pure fn, `@lore/core`) → any check `outcome: "fail"` records a judgment WITHOUT invoking the AI provider (`decision: "reject"`, `confidence: 1.0`, `judge.provider: "deterministic-checks"`) → otherwise `aiProviderService.judgeDoc` → `judgmentService.record`. Same AI-intent semantics as `lore assess` (SPEC-026 §3 D5, reused via `isAssessAiBraked`): `--no-ai` always exits 2; the surface's built-in AI-off default does NOT brake it, only an explicit `ai.default_per_surface.<surface> = false` config override does — and this brake check runs unconditionally BEFORE the deterministic checks, even for docs that would short-circuit before any AI call. Exit 0 on any recorded judgment (approve/reject/escalate all count as success); exit 6 on AI provider failure (no judgment row written); standard `LoreError` codes otherwise. `--pending` batches the same pipe over `reviewService.pending()`: per-doc failures are collected (not fatal), a summary table renders at the end, and the batch only exits 6 if EVERY doc failed. `lore pending` gained an "AI Judgment" badge column (`[AI: approve 0.93]` / `[AI: escalate ✋NQ]` / `[unreviewed]`, `(stale)` suffix when the judgment's `doc_version` trails the doc's current version) and a `--escalated` flag (fresh, non-stale escalations only, printing each doc's `blocking_questions` as indented bullets). A single-doc judgment whose `superseded_candidate` field is set (D11 byproduct, SPEC-044) renders an appended `Suggested: lore invalidate <old> --superseded-by <X>` block (or a plain note when the ref doesn't resolve) — via `../review-render.js::renderSupersededCandidateNudgeBlock`; absent field → byte-identical to pre-SPEC-044 output.

`review --staleness` (SPEC-044 §Design Decisions D6, D7, D9) — a SEPARATE pipeline sharing the `review` command name: `lore review --staleness [--limit N] [--min-age-days D] [--fail-on-candidate] [--json]` (batch, `StalenessProbeService.probeBatch`, top-N by `in_degree × age_days`) / `lore review <doc> --staleness [--fail-on-candidate]` (single-doc, `probeOne` — bypasses selection filters, still refuses an already-invalidated target, exit 4) / `lore review --staleness --list [--json]` (read-only fresh-`stale_candidate`-escalate listing, `../../flows/staleness-flow.js::listFreshStalenessEscalates`, ZERO provider calls). Deterministic pre-checks (SPEC-034) do NOT run for this pipeline. Same "no non-AI mode" semantics as regular review EXCEPT `--list` is fully exempt (both the `--no-ai` mutex and the AI surface-brake check skip it — a pure read needs no AI intent at all). `--pending` and `--staleness` are mutually exclusive (exit 2, disjoint populations) — checked synchronously before any IO, alongside the pre-existing `--ai`/`--no-ai` mutex. Partial-batch AI failures collect-and-continue (exit 0, per-probe `error` in the payload; exit 6 only when EVERY probe failed); `--fail-on-candidate` exits 3 when ≥1 fresh `stale_candidate` result exists (a `status --check-tree`-style CI gate). Every `stale_candidate` result's repair command (`../../flows/staleness-flow.js::renderStalenessRepairCommand`) and the `--json`/MCP payload shape (`buildStalenessBatchJsonPayload`/`buildStalenessSingleJsonPayload`/`buildStalenessListJsonPayload`, SAME file) are shared with the MCP `lore_staleness_probe` tool verbatim — never two independently-authored JSON envelopes. `lore status`/`lore bootstrap` gain `open_stale_candidates`, computed via the SAME `listFreshStalenessEscalates` call (one derivation site, mirrors SPEC-043's `computeArmedGates` precedent) — spliced in by the CLI adapter itself (`commands/status.ts`/`commands/bootstrap.ts`), never inside `CorpusService.status`/`SessionService.bootstrap`.

`audit` (SPEC-035) — `lore audit [<doc>] [--actor] [--action] [--since] [--limit] [--json]` queries the audit table (filters map 1:1 to `AuditFilters`); `lore audit --verify [--since] [--json]` runs the versions⋈audit completeness oracle (exit 0 clean, exit 4 with itemized misses). AI-judge actors (`ai:{provider}:{model}:{prompt_version}`, SPEC-034 §2) are decoded via `parseAuditActor` for human-readable output.

`calibration` (SPEC-035 §4) — `lore calibration --stats [--doc-type <type>] [--prompt-version <v>] [--json]`: read-only table of `{n, agreement_rate, wilson_lower_bound, window_limit}` per (doc_type × prompt_version), thin pipe over `JudgmentService.computeCalibrationStats`. `--stats` is required (only mode currently); omitting it exits 2.

`sync-docs` (SPEC-018) scans a directory of `*.md` spec files, creates corpus rows for missing specs matched by title, and reports body drift without auto-applying. Flags: `--from <path>` (scan dir), `--dry-run` (no writes), `--json` (machine-readable SyncReport).

`claim` / `release` / `evidence` / `ready` (SPEC-025; SPEC-042 D2/D7 additions) — task execution workflow: `lore claim <task> [--by] [--branch] [--machine] [--worktree] [--steal]` acquires an advisory lease (`--machine` auto-captures `os.hostname()` when omitted; `--worktree` is ALWAYS explicit — never `process.cwd()` capture, D2; a same-holder fresh refresh MERGES FORWARD `branch`/`machine`/`worktree` from the existing claim, `buildTaskClaim`; a fresh sibling claim in the same plan whose `file_anchors` overlap this task's own blocks the claim via the `task-claim` gate's `noAnchorOverlap` predicate, `--steal` does NOT bypass it); `lore release <task> [--by] [--reason] [--force]` clears it; `lore evidence <task> --oracle <kind> --command <cmd> --result <pass|fail> [--output-tail | --output-tail-file] [--by]` appends an oracle verification record; `lore ready <plan> [--json]` prints the computed readiness report (never stored) PLUS plan-scoped `sessions[]` (fresh claims grouped by `(by, machine, worktree)`) and `anchor_conflicts[]` (SPEC-042 D7) — `--json` emits the FULL `ReadyReport` object (`{records, sessions, anchor_conflicts}`) under `data.ready`, not the pre-SPEC-042 flat array. `lore tree` / `lore list --type task` render a claim/evidence badge on task rows, `@branch` appended when the claim declared one.

`anchor` (SPEC-042 §Design Decisions D3; extended by SPEC-045 §Design Decisions D6 to dispatch by target doc type) — `lore anchor add|rm|list <target> [<path>...]`: resolves `<target>` FIRST (`corpusService.get`), then dispatches by its doc type: task → manages the typed `extra.file_anchors` (repo-relative POSIX paths; trailing `/` = directory scope) — `add`/`rm` are read-modify-write via `TaskWorkflowService.addAnchors`/`removeAnchors` — validated + normalized through the shared pure `normalizeFileAnchors` (`@lore/core`), preserving `extra.claim`/`extra.verification_evidence` untouched (byte-identical to pre-SPEC-045, REGRESSION); spec → manages `extra.code_anchors` (`path[#Symbol]` grammar) via `DriftCheckService.addCodeAnchors`/`removeCodeAnchors` (incremental union/difference — CLI is deliberately incremental, unlike MCP `lore_anchor_set`'s declarative REPLACE on a spec target, see `../mcp/CLAUDE.md`); any other type → `VALIDATION_ERROR`, exit 4, naming "task or spec". Mirrors the `lore phase` command-group precedent. There is deliberately no `lore set --anchor` full-replace flag — see this file's `set` behavior note and `@lore/core`'s file-anchors.ts module header for why. `lore create task --anchor <path>` / `lore create spec --code-anchor <path[#Symbol]>` (both repeatable, DISTINCT flags — SPEC-045 D6) declare anchors at creation time instead, validated by `CorpusService._createImpl`.

`status --check-drift` (SPEC-045 §Design Decisions D5) — `lore status --check-drift [--json]`: deterministic, zero-LLM-call doc-code drift oracle. COMPOSES with `--check-tree` — `status.ts`'s `--check-tree` branch was restructured OFF early `process.exit` calls onto value-returning checks (D5 review S6/U1) so both flags combine under one exit precedence: any drift found (either check) → 3; else blueprint missing/invalid (`--check-tree` requested but unarmable) → 4; else 0 — a real code drift is never masked by a missing `lore.tree.yaml`, and vice versa; both requested reports always print/emit fully (worked example: `workflow.drift.enabled: false` + an inconsistent tree → the drift section prints its explicit "disabled" note, the tree section prints its drifts, exit 3). Every drift row renders `spec-slug → anchor (kind)` plus a literal `fix: lore anchor rm <spec-slug> '<anchor>' (or update the path/export)` repair hint, deterministically ordered (spec_slug, then anchor); a `symbol_missing` row additionally prints a footnote of the lexical scanner's documented false-positive forms (`export * from`, `module.exports`, re-export chains, `export type {}`, destructured exports). `--json` emits `data.code_drift = {armed, enabled, consistent, specs_checked, status_breakdown, drifts[]}` spliced alongside whatever `--check-tree`'s own `data` shape already carries (unwrapped at top level — REGRESSION when `--check-drift` is omitted). Plain `lore status` (no flags) prints a store-only `code anchors declared: N specs` line (and `--json`'s `code_anchor_specs`) — ZERO filesystem probing, via the shared `../../../flows/drift-flow.js::countArmedSpecs` helper (also used by `bootstrap`, above). The real `FsProbe` (`../real-fs-probe.js`, node:fs sync, repo root `process.cwd()`) is built here and shared with the MCP `lore_status {check_drift: true}` handler — `stat()` never throws, every failure collapses to `"missing"` (the safe zero-false-negative direction, G11).

`assess` (SPEC-026) — `lore assess <plan> [--diff <git-range> | --diff-file <path>] [--json] [--ai|--no-ai]`: AI plan-outcome assessment (LLM-as-judge). `--diff` shells `git diff <range>` (via `node:child_process.spawnSync`, mirrors `editor.ts`'s subprocess pattern); `--diff-file` reads pre-generated diff text (mirrors `set.ts`'s `--content-file` hermetic-test-seam idiom); passing both → exit 2. On success, persists a `knowledge` doc (`sub_type="assessment"`) linked to the plan via `informs` and prints a verdict + AC score table (or `--json` envelope).

`invalidate` (SPEC-043 §Design Decisions D2, D6) — `lore invalidate <id-or-slug> [--superseded-by <id-or-slug>] [--reason <text>] [--undo] [--by <name>] [--json]`: the SOLE CLI write path for a `knowledge`/`adr` doc's bi-temporal `extra.validity`, thin pipe over `ValidityService.invalidate`. `--superseded-by` accepts id-or-slug (resolved + persisted as its ULID); `--undo` clears a prior invalidation, never auto-reverting an ADR's `decision_status: "superseded"` — the asymmetry surfaces as a structured `decision_status_unchanged: "superseded"` field on `--json`.
