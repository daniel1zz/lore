# Module: adapters/cli

Architecture card: `baseline-module-card-cli-adapter`

## Purpose

citty CLI adapter: lazy command registry and exit-code mapping. Every subcommand lives in its own `commands/<name>.ts`, lazily imported by `index.ts` — that registry is the only count that stays true; ⛔ never restate the number here. Thin adapter only — no business logic; every command resolves args, calls a service via the App composition root, formats the result, and exits.

Full pre-eviction file (per-command mechanism walkthroughs, per-spec design decisions, rejected alternatives) is archived verbatim: `lore get knowledge-module-claude-md-snapshot-cli-adapter-pre-eviction`; the earlier pre-compression state: `knowledge-module-claude-md-snapshot-packages-lore-src-adapters`.

## Key Invariants

- **No business logic.** Commands resolve args → call `app.<service>.<method>()` → render output → map error to exit code. New rules belong in `packages/lore/src/service`, not here.
- **DB discovery lives in `corpus-resolution.ts`; App construction lives in `loader.ts`; neither lives in `utils.ts`.** `corpus-resolution.ts` builds on `@lore/core`'s pure `resolveCorpusProvenance` decision (spec-corpus-resolution-carries-provenance-and-a-foreign-write) and is vitest-safe (no `bun:sqlite`); `utils.ts` re-exports `findLoreDbPath` from it purely so pre-existing importers keep byte-identical import statements. `loader.ts` imports `bun:sqlite` (via `app.ts`) and is bun-only. Commands needing an App import `loadLoreApp` from `loader.ts`; commands only formatting errors import from `utils.ts`.
- **`loadLoreApp()` always returns `App` (never `Result<App>`)** — it hands the FULL config (sync section included) to `createApp`: with `sync.enabled` the store is the embedded replica (`replica-priming.ts`) and a sync fault exits 1 rather than running on the local file; the `config` it RETURNS to callers has `sync` stripped. A sync section that does not parse is not a sync fault but an unusable config: refused with exit 4 (BR-926), never run on defaults. `lore sync` manages TursoStore itself. ⛔ Any command mounting `startHttpServer` MUST pass `{surface: "http"}` — it keys the foreign-corpus-write guard on the ADAPTER; the `"cli"` default hands a long-lived server its launch directory, locking every HTTP write out of a nested worktree. Rationale + both oracles: `resolveForeignWriteProvenance`'s JSDoc.
- **`init`, `sync`, `setup` bypass `loadLoreApp`** — they run before a DB exists or manage their own store. Document the exemption when adding a new bootstrap-stage command.
- **Telemetry always wired** — `loadLoreApp` parses `.lore/config.yaml` on every command (file absent → `NoOpTelemetry`; file present but unparsable or schema-invalid → exit 4 naming the file and the parse error, BR-926 — never a silent default). Never call `createApp` directly from a command (it needs the entry's ambient: `loadLoreApp({ inv })` is the one door; `inv` is required, there is no process fallback).
- **Exit codes (SPEC-003 §5, centralised in `utils.ts::exitCode`)**: `1` STORE_ERROR/unknown/verify-assertion-failed, `2` CLI usage error, `3` DOC_NOT_FOUND/SLUG_NOT_FOUND, `4` validation/lifecycle/link errors, `5` STALE_VERSION/CLAIM_CONFLICT/WRITE_CONTENTION (the write-contention family — "someone else won the race, re-read and retry"), `6` AI_PROVIDER_ERROR, `7` NEEDS_APPROVAL, `8` AUTH_REQUIRED (never retryable), `9` TRANSPORT_UNAVAILABLE (retryable), `10` RATE_LIMITED (carries a reset). Exhaustive `never`-checked default branch — add new `LoreError` codes here too. ⛔ Adding a `LoreError` member ripples to EVERY exhaustive switch over it (e.g. `adapters/http/middleware.ts::loreErrorToStatus`, `eval/scenarios/placeholder-parse.ts::loreErrorMessage`), and those are NOT anchorable in advance. Why 8/9/10 exist + the ripple history: `knowledge-evicted-from-the-cli-adapter-module-doc-exit-codes`.
- **A run RETURNS its exit code; nothing below `src/index.ts` calls `process.exit` or sets `process.exitCode`** (`runCli` → `number`, AC-ES-2). A command `run` returns `number` (`defineLoreCommand` enforces it by type) or throws `CliExit` via `exitCli(code)`. ⛔ A `catch` that swallows `CliExit` swallows the exit. Tests calling `cmd.run` directly use `tests/live-invocation.ts::runHandlerForExit`. citty's own exits and `UnknownPartyError` (a write needed an actor and the invocation has no known party → 4) are decided by `run-cli.ts::dispatch`. Mechanism walkthrough: `knowledge-cli-run-returns-its-exit-code-mechanism-evicted-from`.
- **stdin and its TTY-ness come from `inv.io`** (`io.stdin`, `io.stdinIsTTY`, resolved once at the entry; the in-process runner defaults to an empty non-TTY input). Prompts go through `prompt.ts::promptYesNo(inv.io, ...)`; `openEditor` takes `stdinIsTTY`. Nothing below the entry reads `process.stdin`.
- **An invocation with no known party reads fine and is refused at its first write (BR-1351)**: with no per-call `LORE_HARNESS_RUN` (exported by the hook before each Bash call and verified by process ancestry; the old command-line flag is retired and exits 2) and no open human session, `inv.identity` is `{ harnessRun: null, claimed: null, claimedSource: null, unresolvedReason }` (no substitute name; the reason names `lore session start --human <name>` and `lore setup`). The store chokepoint (`withWriteContext`) refuses every stamped write before anything is written, `resolveWriteActorFor` and CLI `resolveActor` throw `UnknownPartyError`, and `dispatch` maps it to exit 4. A run the registry does not know is refused the same way, never downgraded.
- **Output goes through `inv.io`, never a process stream or `console`** (`output.ts`: `printLine(inv.io.stdout, ...)` is `console.log`-shaped; helpers that print take `io: CliIo`; services and adapters below the CLI take a `WarnSink` from `service/warn-sink.ts`, `App.warn`, or `AppAmbient.io`). Every child spawn names its `cwd`, and every path is resolved against `inv.cwd`: nothing below an entry reads the process working directory.
- **Actor resolution** (`utils.ts::resolveActor(inv)`) reads ONE thing, `inv.identity`, resolved once at the entry by core's `resolveInvocationIdentity` — NO write command takes `--by` (AC-ROI-1; the read-side `feed`/`bootstrap` filters are pinned in `adapters/read-side-by-filters.ts`). The identity is one of exactly four known parties (BR-1055): an agent run the integration attested (the per-call `LORE_HARNESS_RUN` export, verified by process ancestry, name `agent:session-<id8>`, source `run`), or the human session of this checkout (`lore session start --human <name>`, token file via `human-session-file.ts`, source `human`; never for a process carrying the agent marker `CLAUDECODE=1`), or — HTTP only — a bearer key / dashboard login. No `--by`, session-id, worktree or computer-user name exists. ⛔ This names WHO; the run instance is a separate captured claim fact (`extra.claim.session_id`, written by the task AND phase workflow claim verbs). `lore session start|end|show` (commands/session.ts) is the only place a human session is created or closed.
- **Vitest-unsafe commands get a sibling `*-render.ts`/`*-input.ts` split** (also `-validation`/`-wiring`/`-precheck` suffixes; these siblings sit in `adapters/cli/` NEXT TO `commands/`, never inside it) — the command file transitively imports `loader.ts` (`bun:sqlite`, unresolvable by vitest); the split module imports only `@lore/core` + `utils.ts` so unit tests can exercise the pure rendering/parsing logic. Apply this pattern to any new command needing vitest coverage.
- **Strict unknown-flag rejection is ONE seam** (`strict-flags.ts::findUnknownFlag` + `wrapCommandStrict`, wired once per lazy import in `index.ts::wrapDefault`) — never patch individual commands. Violation → exit 2. Single-dash multi-char tokens also rejected exit 2 (`findSingleDashViolation`, SPEC-073).
- **No `lore set --anchor`** — `set` replaces `extra` wholesale; anchors have dedicated writers (`lore anchor add/rm`, `lore create --anchor/--code-anchor`). Same dedicated-writer shape applies to `extra.ac_scope` (`lore scope add/rm/list`, `lore create task --ac-scope` — task AND phase tiers, wiring `assertScopeFreeze`), `extra.validity` (`lore invalidate`), `extra.handoff` (`lore handoff`), `extra.phases`/`extra.claim`/`extra.verification_evidence` (task/phase workflow verbs only), `extra.red_first` (`lore red-first <task>`; no create-time flag) — `commands/set.ts` never edits these.
- **`gate`/`feed` are pre-flight/advisory pairs, and `LORE_GATE_BYPASS=1` is `gate`-scoped ONLY** — ⛔ never honored by `GateEnforcer.enforce()` in the write path; the one supported write-path escape is `workflow.gates.<checkpoint>.enabled: false`. Full block incl. the rationale that stops a future reader "fixing" the asymmetry: `knowledge-evicted-from-the-cli-adapter-module-doc-the-gate-feed`

## Patterns

- Subcommands are lazy ES module imports (`index.ts`'s `subCommands` map) — cold-start stays cheap.
- `findLoreDbPath`/`findLoreDbPathQuiet` (`corpus-resolution.ts`) both delegate to `resolveCorpus()`: own-tree hit, else the MAIN checkout via git-common-dir (SPEC M4, no local `.lore/` needed in a fresh worktree), else a miss — loud (exit 1 + `lore init` hint) vs quiet (`undefined`). `gate-bypass-audit.ts` re-exports the quiet one; `utils.ts` re-exports the loud one.
- Output helpers live in `utils.ts` (`formatTable`, `formatTree`, `formatNavigation`, `relativeTime`) — pure, no `exitCli`, reusable from tests.
- `formatError` renders multi-line stderr with contextual hints; add a case per new `LoreError` code.

## Subcommands

One line per command group — mechanism/design-decision detail lives in the archived snapshot or `lore search "<term>"`.

- `init` `get` `set` `delete` `list` `search` `tree` `link` `unlink` `log` `diff` `restore` `migrate` — corpus CRUD/history, thin `CorpusService`/`VersionService` pipes. ⛔ Read-surface validity gating is ONE seam (`fetchGatedFullDocs` over `service/validity-service.ts`) that every validity-carrying surface consumes instead of re-deriving the predicate: invalidated docs excluded by default, restored under `--include-invalid`, `validity_status` on every `--json` record. `--governed-by` is gated inside `CorpusService.listGovernedBy` so MCP inherits it — ⛔ never re-apply the exclusion CLI-side. `get`'s HUMAN render is a lossy projection that ANNOUNCES its loss (`get-render.ts::formatStructuredExtraNotice`), keyed on what THAT render actually surfaced, ⛔ never a static key list; `--json` bytes untouched. ⛔ Residual: `ready` FILTERS correctly but carries no validity key.
- `create` — doc creation; `--anchor`/`--code-anchor` at creation time, `--supersedes` composes create+invalidate.
- `status` — health snapshot. Its check family (`--check-tree` / `--check-drift` / `--check-requirements` / `--check-claude-md` / `--check-memory-pointers` / `--check-prd-budget` / `--check-binary-provenance`) are deterministic CI oracles with composable exit precedence. ⛔ Full measured behaviour — provenance's four outcomes and its EXACT exit 3, the corpus-free dispatch order, why `invalid_docs` always prints, the 0.97-vs-0.9 floor split that makes this command say "within budget" while the suite reddens, and why `pass_unfalsified_count` / `unclaimed_oracle` are deliberately exit-code-inert — is at `knowledge-evicted-from-the-cli-module-doc-lore-status-s-check`.
- `pending` `approve` `reject` `review` — review workflow (SPEC-005/034/103); `review` adds structured AI judgment + `--staleness` probes (SPEC-044) + `backfill-ledger` (one-shot); approve/reject implicitly capture calibration (SPEC-035). `pending` hides task-type + ledger sub_types by default (`--all` restores); `approve` of spec/adr demands a current-version approve-judgment (worst-decision-wins; audited `--override-judgment` escape).
- `trace` — `trace stats [--since] [--json] [--raw-queries] [--enumerate <field>]` read-only aggregation over `trace_events` (SPEC-102); aggregates only unless `--raw-queries` or `--enumerate`. ⛔ A new `*_count` with no enumerator FAILS TO COMPILE; `zero_hit_search_count` withholds query text without `--raw-queries`. Detail: `knowledge-evicted-from-the-cli-adapter-module-doc-exit-codes`.
- `checks` — `checks stats [--quality] [--json]` (BR-1373): runs, denials and last denial per gate/hook id plus removal candidates (a check that can deny, >=30 days, >=50 runs, 0 denials; informational hooks show runs only, deny capability is declared in `@lore/core` `HOOK_DENY_CAPABILITY` and the gate checkpoint registry); `--quality` counts, per closed plan, issues filed within 14 days of close citing it, reopened tasks and fix tasks, and needs `feedback.upstream` (refused without it, never reported as 0). It first ingests the hooks' local outcomes file. All math is in `CheckStatsService`.
- `claim` `release` `evidence` `ready` `done` — task/phase execution workflow (SPEC-025/042/056); target-type dispatch tries `TaskWorkflowService` first, falling back to phase workflow only on a `type: "phase"` validation rejection. `done` requires ≥1 RUNNER-ATTESTED pass row; `evidence` requires `--capture` or `--oracle manual` for a self-reported pass to stick. Full mechanism (capture-timeout semantics, `--ac-scope`/`--declare-no-new-tests` red-first floor, `capture_source_*_count` enumerator contract): `knowledge-evicted-from-the-cli-adapter-module-doc-the-claim`.
- `red-first` — dedicated writer for a task's `extra.red_first` claim (`TaskWorkflowService.declareRedFirst`); see commands/red-first.ts's module header.
- `phase` — `add/list/rm/rename` (plan-level `extra.phases[]`, SPEC-023) plus `status/checklist/track` (phase-document verbs, SPEC-056).
- `assess` — the milestone review (BR-1372): `<plan>...` or `--where`, one row per plan (exit 0 all pass / 1 any fail), stores a `milestone-review` doc; plan close requires a passing review of the current state (or, for a failing one, an OPEN linked GitHub issue per failed dimension: "accepted with known defects"); no non-AI mode. Once per batch it runs `bun run check:plan-close` + `bun run test` on main in a throwaway worktree (`assess-suite-runner.ts`) for every plan's regression dimension; `--file-issues` files by root cause, one issue per fingerprint (`IssueFilingService`, port in `assess-file-issues.ts`); `--where needs-review` + `--close` is the post-landing review batch under a store lease (BR-1379).
- `audit` `calibration` — audit-trail query + `--verify` chain-integrity walk (SPEC-035/079), `audit anchor` pins `.lore/audit-anchor.json`; calibration stats are read-only.
- `ac` `requirement` — AC-as-code (SPEC-038) and PRD requirement inventory (SPEC-055) dedicated writers; `ac add --covers` links them.
- `verify` — trusted runner executing script-mode ACs, runner-attested evidence only (SPEC-039, §M2 env allowlist + command-provenance approval).
- `gate` `feed` — see Key Invariants; groups covering spec-create/spec-promote/plan-promote/task-claim/phase-claim and the matching feed checkpoints incl. `task-start`/`phase-start`/`session-resume`. ⛔ `feed task-start` REFUSES a RETRACTED task (exit 4 / MCP `isError`, NO pack, unconditional `RETRACTED` + `invalid_at=` tokens), implemented in `flows/task-feed-flow.ts` so both surfaces inherit it. UNPARSEABLE `extra.validity` is instead ANNOUNCED in `constraints`, ⛔ never read as live in silence.
- `bootstrap` `handoff` — S1 session pointer-set (read-only) and the sole write path for `knowledge/handoff` docs (SPEC-041).
- `anchor` `invalidate` — dedicated writers for `extra.file_anchors` (task) / `extra.code_anchors` (spec AND knowledge, `path[#Symbol]` grammar) and `extra.validity` (bi-temporal invalidation, SPEC-043). ⛔ The non-resolving stderr advisory (`anchor add`, `create task --anchor`, `ready <plan>`; `service/anchor-resolution.ts`) is TASK-ONLY and FILE-anchor grammar — never apply it to `path#Symbol`; spec/knowledge are checked by `--check-drift`. Non-blocking (exit untouched, anchor stored). Detail: `knowledge-evicted-from-the-cli-adapter-module-doc-exit-codes`.
- `sync` `sync-docs` `export-docs` — Turso replica management, one-shot dir→corpus scaffold (SPEC-018), corpus→`.md` reverse sync (SPEC-021).
- `serve` `dashboard` `agent` `eval` — HTTP adapter mount, in-process dashboard (packaged single-process by default: embedded static assets + one-time-nonce bootstrap redirect; `--dev` retains the Vite-child + injected-token topology of SPEC-016), API-key management (⛔ NOT an MCP launcher — MCP is the top-level `--mcp-server` flag), evaluation scenarios.
