# Module: adapters/cli

## Purpose

citty-based CLI adapter. 29 subcommands, each in its own `commands/<name>.ts`, lazily imported by `index.ts`. Thin adapter only — no business logic; every command resolves args, calls a service via the App composition root, formats the result, and exits.

## Key Invariants

- **No business logic.** Commands resolve args → call `app.<service>.<method>()` → render output → map error to exit code. New rules belong in `packages/lore/src/service`, not here.
- **DB discovery + App construction live in `loader.ts`, not `utils.ts`.** `loader.ts` imports `bun:sqlite` (via `app.ts`); `utils.ts` is vitest-reachable and must stay sqlite-free. Commands that need an App import `loadLoreApp` from `loader.ts`; commands that only format errors import from `utils.ts`.
- **`loadLoreApp()` always returns `App` (never `Result<App>`).** It strips `config.sync` before passing to `createApp`, so corpus-level commands never hit the TursoStore-failure path. Sync-aware commands (`lore sync ...`) manage TursoStore themselves.
- **`init` and `sync` commands bypass `loadLoreApp`** — `init` runs before a DB exists; `sync` manages TursoStore directly. Document the exemption when adding a new bootstrap-stage command.
- **Telemetry must be wired (AC-K3-1)** — `loadLoreApp` always parses `.lore/config.yaml` (failures fall back to `NoOpTelemetry`) so user telemetry preferences apply to every command. Don't call `createApp(dbPath)` directly from a command.
- **Exit codes per SPEC-003 §5** — mapping is centralised in `utils.ts::exitCode`. `1 = STORE_ERROR / unknown`, `3 = DOC_NOT_FOUND | SLUG_NOT_FOUND`, `4 = validation / lifecycle / link errors`, `5 = STALE_VERSION | CLAIM_CONFLICT`. The default branch uses an exhaustive `never` check; add new `LoreError` codes here too. `verify` (SPEC-039) additionally maps a NON-`LoreError` business outcome — "the service call succeeded but at least one executed AC's command exited non-zero" — to exit `1` too (the same "ran fine, an assertion failed" bucket `STORE_ERROR` already occupies), independently of `exitCode()`; see `verify.ts`'s header comment for the full rationale.
- **Actor resolution for workflow commands (SPEC-025)** — `claim` / `release` / `evidence` resolve the acting identity via `utils.ts::resolveActor`: `--by` flag > `$LORE_ACTOR` env var > OS username. Never silently falls back to an empty string.
- **`assess-render.ts` is split out of `commands/assess.ts` for testability (SPEC-040 §T3 D3)** — `commands/assess.ts` transitively imports `loader.ts` (`bun:sqlite`), which vitest cannot resolve, so `formatAssessmentSummary` (verdict + AC table + gaps/recommendations + judge line, additively extended with SPEC-040 typed-field tables — dimension scores, typed gaps, typed recommendations, rubric warnings — all presence-guarded so a legacy-only `AssessmentResult` renders unchanged) lives in its own module importing only `@lore/core` + `./utils.js`. `commands/assess.ts` imports it rather than defining it inline. Mirrors `../mcp/assess-render.ts`'s split for the same reason on the MCP side.
- **Implicit calibration capture (SPEC-035 §3, hoisted surface-neutral SPEC-033 F1)** — `approve` / `reject` call the shared `../../flows/calibration-hook.ts::runCalibrationHook` after their `ReviewService` call succeeds. It is a byproduct, never a gate: a calibration write failure prints a stderr warning + records telemetry but never changes the command's exit code (still 0). The hook lives in `flows/`, not under this adapter — the HTTP dashboard's approve/reject routes (`../http/dashboard-routes.ts`) call the SAME function so calibration data is never adapter-specific. `calibration-hook.ts` takes a narrowed `{judgmentService, telemetry, onWarning?}` dependency shape (not the full `App`) so it stays unit-testable without a real store; `onWarning` is the additive hook HTTP/MCP callers use to surface a failure in their own response shape instead of stderr.

## Patterns

- **Subcommands are lazy ES module imports** — `index.ts` defines `subCommands: { create: () => import("./commands/create.js").then(m => m.default) }`. Keeps cold-start cheap; each command file's deps are not loaded unless invoked.
- **`findLoreDbPath` walks `cwd` → root** looking for `.lore/lore.db`. Exits with code 1 + `lore init` hint when absent.
- **Output helpers in `utils.ts`** — `formatTable`, `formatTree` (Unicode box drawing), `formatNavigation`, `relativeTime`. Pure; no `process.exit` calls. Reusable from tests.
- **Hyphen-quoted error mode** — `formatError` produces multi-line stderr output with contextual hints (`"Run \`lore get <id>\`..."`). Add a new case when introducing a new `LoreError` code.

## Subcommands

`init` `create` `get` `set` `delete` `list` `search` `tree` `link` `unlink` `pending` `approve` `reject` `log` `diff` `restore` `migrate` `status` `serve` `agent` `sync` `eval` `dashboard` `sync-docs` `export-docs` `phase` `claim` `release` `evidence` `ready` `assess` `audit` `calibration` `review` `ac` `verify` `gate` `feed` `bootstrap` `handoff`

`gate` (IoC vertical-slice tech-spec §4.1/§11) — `lore gate spec-create --input-json '<json>'`: pre-flight, pure-predicate gate for a CANDIDATE spec-creation payload (`{type, title, parent_id?, content?, extra?: {spec_kind?}}`, the same shape as `lore_create`'s input), run BEFORE the doc is actually created. `LORE_GATE_BYPASS=1` short-circuits to exit 0 before any parsing (escape hatch). Otherwise resolves `parent_id` via `corpusService.get` (missing/unresolvable → treated as no parent) and runs the three `../../service/gate-predicates.js` checks (`parentLegal` / `specKindValid` / `hasSkeleton`); all pass → `"gate: pass"`, exit 0. Any fail → discovers its feeding rule doc via `corpusService.findFeedingSkill("spec")` (P1 slice-2: any APPROVED `knowledge` doc with `sub_type: "skill"` and `extra.skill.applies_to === "spec"`, most-recently-updated wins — no longer a hardcoded title lookup; `scripts/seed-write-spec-rule.ts` seeds one such doc but discovery is scope-based, not title-based), builds a `../../service/gate-feeding.js::FeedingPack` (rule slice + parent slice + `missing` reasons) and prints `renderFeedingPack(pack)` to stdout, exit 4. No matching approved skill doc → the same placeholder fallback as before (backward-compat). `--input-json` missing/malformed/shape-mismatched → exit 2 (CLI-usage error, not a `LoreError`). Structured as a command GROUP (`subCommands: {"spec-create": ...}`) so a future `spec-promote` gate can join it without a breaking rename. Command group is a new addition to this module — its own subtree, no interaction with the 26 pre-existing flat subcommands above.

`lore gate plan-promote --plan <id-or-slug>` / `lore gate task-claim --task <id-or-slug>` are the two "commit-time cross-tier gates" joining the same `gate` command group: each resolves its target's ancestor spec via `corpusService.getPlanBundle` (the SAME plan→parent-spec traversal `TaskWorkflowService.ready()` uses for the `upstream_unapproved` advisory — see `../../../service/checkpoint-registry.js`'s third module invariant) and dispatches through `checkpointRegistry["plan-promote"|"task-claim"]`. No spec-tier ancestor (prd-parented or unparented plan) ⇒ vacuous pass, never a failure. `plan-promote` requires the ancestor spec `approved` AND ≥1 declared acceptance criterion; `task-claim` requires only `approved`. Exit 0 = pass (incl. vacuous, incl. `LORE_GATE_BYPASS=1`); 3 = target doesn't resolve; 4 = wrong doc type, or a spec-tier ancestor exists but fails its predicates.

`feed` (IoC vertical-slice tech-spec §4.1/§11 P4; extended by SPEC-041 §3 D5) — `lore feed <checkpoint> [--parent <id-or-slug>] [--json]`: feed-before-produce PULL, the advisory counterpart to `gate` (PULL the governing rule ahead of writing instead of discovering it via a rejected write). Thin pipe over `../../../flows/feed-flow.js::buildFeed` — this slice only wires `spec-create` → `"spec"` via `CHECKPOINT_PRODUCED_TYPE`; an unknown checkpoint degrades to a one-line advisory note, never a failure. Exit code is ALWAYS 0 for this branch. `lore feed session-resume [--plan <id-or-slug>] [--handoff <id-or-slug>] [--by <name>] [--json]` is a SEPARATE dispatch (SPEC-041 §3 D5, `buildResumeFeed`/`SessionService.resume`), consulted BEFORE the `CHECKPOINT_PRODUCED_TYPE` lookup — deliberately NOT a `CHECKPOINT_PRODUCED_TYPE` entry (that map's absent-key branch yields the generic "unknown checkpoint" note, wrong for a real, wired capability). Prints the resolved handoff's full rendered content (the one deliberate pointers-only exception), an age line, a `⚠ handoff older than the configured TTL` warning past `workflow.handoff_ttl_minutes`, a live readiness pointer block, and a multi-actor header (`"N actors have handoffs"`) when `--by` is omitted and the corpus/plan has handoffs from more than one actor. Unlike the gate-checkpoint branch, THIS branch CAN fail — an unresolvable `--plan`/`--handoff` maps through the normal `exitCode()`/`formatError()` pipeline (VALIDATION_ERROR → 4); "no handoff recorded yet" is a fact (exit 0), not an error.

`bootstrap` (SPEC-041 §3 D1, D2) — `lore bootstrap [--by <name>] [--json]`: the S1 volatile session pointer-set a fresh session (agent or human) queries in ONE deterministic, read-only call. Thin pipe over `SessionService.bootstrap` — zero store mutations. Reports the root PRD pointer, active plans + task readiness counts, the pending-review queue (bounded slug sample), the caller's own claims (`--by` filters this field only — every other field is corpus-wide), armed gate checkpoints + their discoverable feeding-skill source, the newest handoff per plan, and a corpus-wide resume hint. Deliberately excludes the STATIC layer (architecture, conventions — that's CLAUDE.md/AGENTS.md's job, "Division of labor"). `--json` prints the raw `BootstrapReport`; the default text mode (`formatBootstrapReport`, same file) is a compact pointer-only block. An empty corpus is legal output (`root: null`, every array `[]`), not an error.

`handoff` (SPEC-041 §3 D3, D6) — `lore handoff [--json-file <path> | (--file... --decision... --next... [--failing-command --failing-tail-file])] [--plan] [--by] [--json]`: the SOLE CLI write path for a lossless session-continuity handoff document (`knowledge`/`sub_type: "handoff"`). PRIMARY path `--json-file <path>` — the file IS the `extra.handoff` SSOT (Zod-validated, field-precise errors, exit 2). Human convenience path: repeatable `--file` (→ `modified_files`), `--decision "<judgment>[@<confidence 0-100>]"` (→ `key_decisions`, trailing `@NN` split off by `parseDecisionFlag`), `--next` (→ `next_steps`, required — an empty `next_steps` is a `handoffExtraSchema` violation, exit 2: "a handoff naming no next step is a status report, not a handoff"), `--failing-command` + `--failing-tail-file` (mutually required, exit 2 if only one is passed). `--plan`/`--by` work with BOTH paths — explicit values override the json-file's own `plan_ref`/`by`; omitted, the json-file's values are left untouched. `--json-file` is mutually exclusive with any field flag (exit 2, naming the conflict). The pure candidate-assembly functions (`parseDecisionFlag`, `assembleHandoffInput`, `parseHandoffJsonFile`) live in the sibling `../handoff-input.js` module (NOT `commands/handoff.ts` itself), mirroring `assess-render.ts`'s split — `commands/handoff.ts` transitively imports `loader.ts` (`bun:sqlite`), which vitest cannot resolve, but `handoff-input.ts` imports only `@lore/core`, so `session-roundtrip.test.ts` (SPEC-041 §4 AC-SL-7) can exercise both authoring paths without spawning a subprocess. There is deliberately no `--content`/`--content-file` flag — `content` is always the deterministic `renderHandoffContent(extra.handoff)` projection, never hand-authored. Direct `lore create knowledge --sub-type handoff` is rejected by `CorpusService._createImpl`'s writer-identity guard (VALIDATION_ERROR naming `lore handoff` as the sole legitimate writer) — see `create.ts`'s `KNOWLEDGE_SUB_TYPES` SSOT-import note below.

**Hook integration (SPEC-041 §3 D7 — honest framing: Lore does not install or manage hooks; this is a documented pattern, not a shipped script).** `bootstrap` is SessionStart-hook-authorable — it is a deterministic, read-only, zero-argument-from-the-agent call, so a shell hook can invoke it directly. `handoff` is NOT hook-authorable the same way — `key_decisions`/`next_steps` exist only in the agent's own context, a shell hook has no access to them. The honest integration model:

```bash
# SessionStart hook — script-authorable (bootstrap is deterministic + read-only)
lore bootstrap --by "$LORE_ACTOR" --json
# Optionally follow the printed resume_hint straight into a resume read:
# lore feed session-resume --plan <resume_hint.plan_slug> --handoff <resume_hint.handoff_slug>

# Stop / PreCompact hook — REMINDS the agent, does not author the handoff itself.
# Two legitimate shapes for this hook, per D7:
#   (a) a blocking prompt telling the agent to run `lore handoff` before exiting
#       (preferred — the agent supplies real key_decisions/next_steps); or
#   (b) a degraded, git-only capture when the agent cannot be prompted in time —
#       modified_files ONLY, no decisions, explicitly marked `degraded: true`:
lore handoff --by "stop-hook" \
  --next "review uncommitted changes" \
  --json-file <(git status --porcelain | awk '{print $2}' | \
    jq -R -s '{by: "stop-hook", modified_files: (split("\n") | map(select(length > 0))), next_steps: ["review uncommitted changes"], degraded: true}')
```

Shape (b) is a LAST RESORT, not the default path — a degraded handoff's `key_decisions` is always `[]`; `renderHandoffContent` prints a visible `⚠ degraded (git-only capture — no key decisions recorded, next_steps may be incomplete)` marker so a resuming session never mistakes it for a fully-authored one. Lore itself installs and manages neither hook — this block documents the pattern an operator's own `.claude/settings.json` (or equivalent) wires up, mirroring how `hooks/g1-spec-create.sh` etc. are operator-installed shims around `lore gate`, not part of the `lore` binary.

`ac` (SPEC-038 §4, §6) — `lore ac add <spec> <id> --statement <s> --mode <script|ai|human> [--oracle --command | --rubric | --note]` / `lore ac list <spec> [--json]` (renders `✔/✘/·` coverage badges when the spec has a child plan, plus a dangling-ids note) / `lore ac rm <spec> <id> [--force]` (exit 4 if any task evidence still references the id, unless `--force`). Thin pipe over `AcService`; candidate criterion objects are assembled untyped from CLI flags and validated entirely by `specAcceptanceCriteriaSchema` (single source of truth for mode-specific required fields).

`verify` (SPEC-039 §2, §3, §4 AC-VRF-10) — `lore verify <plan> [--ac <id> repeatable] [--task <t>] [--by] [--json]`: trusted runner, thin pipe over `VerifyRunnerService.verifyPlan`. Actually EXECUTES every declared script-mode AC on the plan's parent spec (or the `--ac`-filtered subset — the flag may repeat, citty collapses repeated occurrences into a string array) against the resolved target task (`--task` override, else the plan's sole fresh claim via core's `resolveTargetTask`; 0 or >1 candidates → exit 4 listing every candidate slug), recording each outcome as runner-attested evidence (`result` derived from the command's exit code, never a caller assertion — contrast `lore evidence`, which is self-reported and whose `EvidenceInput` type structurally excludes `attestation`; the only production caller of the attestation-carrying `TaskWorkflowService.recordVerifiedEvidence` is this runner). Renders a per-AC pass/fail/timed-out line with `duration_ms`, a skipped-ai/human-mode list, and any advisory warnings (e.g. parent spec not `approved`/`active` — never a hard gate). Exit codes: `0` all executed ACs passed (or none matched the selection — a clear notice prints, never silent); `1` at least one executed AC's command exited non-zero or timed out (a business outcome, NOT a `LoreError` — see `verify.ts`'s header for why it shares `STORE_ERROR`'s exit-1 bucket) OR a command failed to LAUNCH (`STORE_ERROR`, the run aborts, message lists every AC already recorded); `3` `DOC_NOT_FOUND`; `4` `VALIDATION_ERROR` (no parent spec / no structured ACs / unknown `--ac` id / ambiguous target task); `5` `STALE_VERSION`.

`review` (SPEC-034 §4, §6) — `lore review <doc> [--by] [--ai|--no-ai] [--json]` / `lore review --pending [...]`: structured AI review judgment. Loads `lore.tree.yaml` if present (absence degrades the `tree_position` check to `"skipped"`, never fatal; a present-but-invalid blueprint IS fatal, mirrors `lore status --check-tree`), calls `corpusService.getReviewBundle` → `runDeterministicChecks` (pure fn, `@lore/core`) → any check `outcome: "fail"` records a judgment WITHOUT invoking the AI provider (`decision: "reject"`, `confidence: 1.0`, `judge.provider: "deterministic-checks"`) → otherwise `aiProviderService.judgeDoc` → `judgmentService.record`. Same AI-intent semantics as `lore assess` (SPEC-026 §3 D5, reused via `isAssessAiBraked`): `--no-ai` always exits 2; the surface's built-in AI-off default does NOT brake it, only an explicit `ai.default_per_surface.<surface> = false` config override does — and this brake check runs unconditionally BEFORE the deterministic checks, even for docs that would short-circuit before any AI call. Exit 0 on any recorded judgment (approve/reject/escalate all count as success); exit 6 on AI provider failure (no judgment row written); standard `LoreError` codes otherwise. `--pending` batches the same pipe over `reviewService.pending()`: per-doc failures are collected (not fatal), a summary table renders at the end, and the batch only exits 6 if EVERY doc failed. `lore pending` gained an "AI Judgment" badge column (`[AI: approve 0.93]` / `[AI: escalate ✋NQ]` / `[unreviewed]`, `(stale)` suffix when the judgment's `doc_version` trails the doc's current version) and a `--escalated` flag (fresh, non-stale escalations only, printing each doc's `blocking_questions` as indented bullets).

`audit` (SPEC-035) — `lore audit [<doc>] [--actor] [--action] [--since] [--limit] [--json]` queries the audit table (filters map 1:1 to `AuditFilters`); `lore audit --verify [--since] [--json]` runs the versions⋈audit completeness oracle (exit 0 clean, exit 4 with itemized misses). AI-judge actors (`ai:{provider}:{model}:{prompt_version}`, SPEC-034 §2) are decoded via `parseAuditActor` for human-readable output.

`calibration` (SPEC-035 §4) — `lore calibration --stats [--doc-type <type>] [--prompt-version <v>] [--json]`: read-only table of `{n, agreement_rate, wilson_lower_bound, window_limit}` per (doc_type × prompt_version), thin pipe over `JudgmentService.computeCalibrationStats`. `--stats` is required (only mode currently); omitting it exits 2.

`sync-docs` (SPEC-018) scans a directory of `*.md` spec files, creates corpus rows for missing specs matched by title, and reports body drift without auto-applying. Flags: `--from <path>` (scan dir), `--dry-run` (no writes), `--json` (machine-readable SyncReport).

`claim` / `release` / `evidence` / `ready` (SPEC-025) — task execution workflow: `lore claim <task> [--by] [--branch] [--steal]` acquires an advisory lease; `lore release <task> [--by] [--reason] [--force]` clears it; `lore evidence <task> --oracle <kind> --command <cmd> --result <pass|fail> [--output-tail | --output-tail-file] [--by]` appends an oracle verification record; `lore ready <plan>` prints the computed readiness report (never stored). `lore tree` / `lore list --type task` render a claim/evidence badge on task rows.

`assess` (SPEC-026) — `lore assess <plan> [--diff <git-range> | --diff-file <path>] [--json] [--ai|--no-ai]`: AI plan-outcome assessment (LLM-as-judge). `--diff` shells `git diff <range>` (via `node:child_process.spawnSync`, mirrors `editor.ts`'s subprocess pattern); `--diff-file` reads pre-generated diff text (mirrors `set.ts`'s `--content-file` hermetic-test-seam idiom); passing both → exit 2. Zero child tasks on the plan → exit 4 (`VALIDATION_ERROR`) BEFORE any AI call. Unlike every other AI mutation command, assess has no non-AI mode — `--no-ai` always exits 2, and the surface's built-in AI-off default (agent/mcp/http_token) does NOT brake it; only an explicit `ai.default_per_surface.<surface> = false` config override does (`isAssessAiBraked`, `../../ai/resolve-ai.js`). On success, persists a `knowledge` doc (`sub_type="assessment"`) linked to the plan via `informs` and prints a verdict + AC score table (or `--json` envelope).

`serve` mounts the HTTP adapter; `agent` manages API keys for AI agents — create/list/revoke (SPEC-010 §3.2), NOT an MCP launcher (MCP is entered via the top-level `--mcp-server` flag only); `eval` runs evaluation scenarios; `dashboard` (SPEC-016) starts the HTTP server in-process, spawns the `@lore/dashboard` Vite dev server, ensures `.lore/local-key` exists, and injects a one-time bootstrap token so the SPA can exchange it for an HttpOnly session cookie.
