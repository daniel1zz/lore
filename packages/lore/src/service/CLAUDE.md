# Module: service

## Purpose

Business logic layer. Ten stateless services orchestrate `StoreInterface` calls and apply domain rules (lifecycle, parent-type, MDX placeholders, version snapshots, drift checks, AI generation, file-to-corpus sync, task execution workflow, structured acceptance criteria). All public methods return `Promise<Result<T, LoreError>>` — no thrown exceptions cross this boundary. `GateEnforcer` (`gate-enforcer.ts`) is an eleventh, cross-cutting module — not a `StoreInterface`-holding service itself, but an optional dependency `CorpusService`/`ReviewService`/`TaskWorkflowService` consult before a gated write (see below).

## Key Invariants

- **Stateless** — every service holds only a `StoreInterface` (and optionally a `Telemetry` for `CorpusService`). All persistent state lives in the store.
- **`Promise<Result<T, LoreError>>` everywhere** — public methods never throw. Internal helpers may throw, but every public surface catches and maps to `Result`.
- **`resolveDoc` / `resolveDocId`** in `resolve.ts` is the single helper for ID-or-slug lookup. Detects ULID via `^[0-9A-HJKMNP-TV-Z]{26}$/i` and dispatches to `store.find` vs `store.findBySlug`.
- **Approval edits content reset → `draft`** — `CorpusService.update` automatically reverts an `approved` doc to `draft` when title or content changes (lifecycle invariant from SPEC-002 §3).
- **Migration is idempotent** — `MigrationService` distinguishes `imported` from `already_existed`; re-running the same import does not duplicate docs.
- **Version log is append-only** — `VersionService.restore(id, version)` does not delete newer entries; it inserts a new version with `action: "restore"` containing the historical content snapshot.
- **OutlineService is regex-based** — no `remark` / `unified` / `mdx` dependency. Self-closing tags only; props limited to `key="string"` and `key={literal}` (`COMPONENT_REGEX` + `PROP_REGEX`). Unknown components are stripped with a warning, not an error.
- **`OutlineService.renderResolvedToMarkdown` is the SSOT for text-projection** (SPEC-032 §3.3) — `resolve()` alone only emits structured data, it never touches `content`; this pure function (no store, no IO) splices a `resolve()` result's `resolvedComponents` back into the markdown body, walking positions DESCENDING (offsets stay stable since `resolve()`'s regex matches are non-overlapping). Two consumers: CLI `get` (prints the spliced body unless `--raw`) and `ExportDocsService` (writes the spliced body to disk). HTTP/MCP still return raw `resolvedComponents` data alongside untouched `doc.content` (dashboard splice rendering is SPEC-033, not this).
- **`CorpusService.get()`'s `GetOpts.resolve_mdx` / `DocWithNavigation.resolved_components` are intentionally dead** — MDX resolution needs `OutlineService.resolve()`, and CorpusService must not import OutlineService (see "no cross-service calls" below). The real seam is adapter-level: CLI `get.ts`, HTTP `routes.ts`, and MCP `tools.ts` each call `app.outlineService.resolve(doc)` themselves after `corpusService.get()`. Do not "fix" `GetOpts.resolve_mdx` by making CorpusService call OutlineService — see its JSDoc.
- **`ExportDocsService` index allocation is collision-safe against duplicate corpus titles** — `CorpusService` dedupes `slug` only (`slugifyWithCollision`), never `title`; two docs may legitimately share the same title. `buildOrExtendIndex`'s title-match reconcile path (used to rebuild the index from files on disk when `.lore/export-index.json` is missing/partial) MUST NOT hand a `file_path` already claimed by a *different* doc id in the same reconcile pass to a same-titled doc — tracked via a `usedFilePaths` set built from `index.mappings`. Sequential fallback allocation dedupes its computed `file_path` the same way (`-2`/`-3`/... suffix, mirroring `slugifyWithCollision`), failing loud (`VALIDATION_ERROR`) after 999 attempts rather than aliasing another doc's file. A prior version lacked this guard: a same-titled doc silently inherited an unrelated doc's `human_id` + `file_path`, producing a permanent false drift report (SPEC-021 export-collision incident).
- **`ExportDocsService` new-allocation human_ids honor a title-declared number before the sequential counter** (SPEC-021 Amendment A1) — for an unmapped doc with no title-match on disk, `buildOrExtendIndex` first checks whether `doc.title` self-declares a number for `doc.type`'s prefix (`^{PREFIX}-(\d+)\b`, e.g. a spec titled "SPEC-040 — X"); if that normalized `{PREFIX}-{NNN}` id isn't already held by an existing mapping or an earlier allocation this pass (`usedHumanIds`, mirroring `usedFilePaths`), it's adopted directly and the sequential counter is fast-forwarded past it, otherwise allocation falls back to the sequential counter which itself skips any number `usedHumanIds` already holds. This closes the incident where a doc titled "SPEC-035 — …" was allocated `SPEC-033` by a pure max+1 counter that ignored the number already in the title. Title-match reconcile and existing index mappings are untouched by this amendment.
- **`ExportDocsService` self-heals a corrupted index** — if `.lore/export-index.json` already has two doc ids mapped to the same `file_path` (e.g. written by the bug above, or a hand-edit), `repairCollisions` keeps exactly one canonical owner (content match against the on-disk file if unambiguous, else earliest `created_at`), strips the losing mapping(s) so the normal allocation loop reallocates them, and reports every repair via `ExportReport.repaired` — never a silent skip.
- **`ExportDocsService` splices MDX placeholders via an injected `ResolveDocBody` callback, not a direct OutlineService import** (SPEC-032 §3.3 AC-4) — `app.ts` wires `(doc) => outlineService.resolve(doc).then(renderResolvedToMarkdown)`. The SAME resolved body is used for both the drift comparison and the on-write content; comparing raw `doc.content` on one side against a spliced on-disk file on the other would make any placeholder-bearing doc report permanent false drift on every run.

## Patterns

- **Service per concern, no cross-service calls** — services do not import each other. Composition lives in `packages/lore/src/app.ts`. If a workflow spans two services (e.g. `approve` produces a `versions` entry), the calling layer (CLI / MCP / HTTP) sequences them.
- **`CorpusService` is the only service wired to telemetry** — constructor takes `Telemetry`; other services don't record events. Exception: `TaskWorkflowService` also takes its own `Telemetry` DI (SPEC-025 D8) — it never routes writes through `CorpusService` (cross-service calls are forbidden), so telemetry parity requires its own wiring rather than piggybacking on CorpusService's.
- **`TaskWorkflowService` writes only `extra.claim` / `extra.verification_evidence` directly via the store** — never `content`/`title`/`status`, and never through `CorpusService.update`. This is a documented, bounded bypass of the "services don't touch the store for doc mutation outside CorpusService" norm (SPEC-025 §3 D8); it exists because CorpusService's approved→draft demotion invariant is unreachable from these fields by construction, and cross-service calls are forbidden.
- **Stable public types live next to the service that owns them** — `PendingDoc`, `ApproveOpts` in `review-service.ts`; `Diff`, `FieldChange` in `version-service.ts`; `MigrationReport`, `SecretWarning` in `migration-service.ts`; `TreeDrift`, `FixReport`, `ReconcileReport` in `tree-check-service.ts`. Don't move them to `core/types.ts`.
- **TreeCheckService is the only service that may modify the link table directly** — it reconciles the `parent_id` column on `docs` against the parent links in the link table. Other services treat them as synchronised.
- **`CorpusService.getPlanBundle` is the only cross-doc read-orchestration entry point for assessment** (SPEC-026 §3 D1) — it assembles `{plan, spec?, tasks[]}` for `AIProviderService.assessPlan`, the same way `tree()` assembles multi-doc reads for other callers. `AIProviderService` stays store-free (its four pre-existing methods take already-fetched `DocRecord`s); bundle assembly does NOT move into the adapters (CLI/MCP contract: thin pipes only). **`knowledge_links` (SPEC-040 §T2)** is ALWAYS populated (possibly `[]`, never omitted) — a pointer list `{slug, sub_type, title}` (never content) of `knowledge` docs linked to the plan via `informs`/`relates-to`, feeding `computeAssessmentFacts`'s knowledge-capture fact (`source: "bundle"` vs the `"unavailable"` degrade for a pre-T2 bundle that never populated this field).
- **`CorpusService` cross-entity-validates a plan's `extra.ac_scope` in BOTH `_createImpl` and `set`** (SPEC-040 §T2 D5) — mirrors the pre-existing task `extra.phase`-vs-parent-plan pattern: every declared id must be a member of the parent spec's `extra.acceptance_criteria`; a plan with no spec parent (or a spec parent with no declared criteria) declaring any `ac_scope` at all is `VALIDATION_ERROR`. Shape validation (non-empty array of non-empty strings, `planAcScopeSchema`/`@lore/core`) is automatic on `create` (routed through `createDocInputSchema`'s superRefine) but must be explicitly re-checked on `set` (`docPatchSchema.extra` is untyped `z.record(z.unknown())`). The shared parent-walk lives in a new private `_resolveDeclaredAcIdsForParent(parentId)`, which `resolveDeclaredAcIds` (below) now delegates to after resolving its own plan argument. Post-edit staleness (the SPEC dropping an id a plan's `ac_scope` still references) is deliberately NOT re-validated at write time — `computeAssessmentFacts`'s `scope.dangling[]` (assess-time) is the intended detection point, not a reverse validation hook on the spec's own writes.
- **`CorpusService.resolveDeclaredAcIds(planIdOrSlug)` is the single cross-entity traversal locus for SPEC-038 `ac_ref` validation** — same family as `getPlanBundle` (plan → parent spec), returning `Set<string> | null` (id set when the parent spec has structured AC, `null` when there's no plan-parent-spec chain or no structured AC declared — a fact, not an error). `TaskWorkflowService.addEvidence` never calls it directly; it's injected as a narrow constructor port (`resolveDeclaredAcIds: (planId) => Promise<Result<Set<string> | null, LoreError>>`, defaulting to a stub that always resolves `null` so every pre-SPEC-038 caller keeps compiling) and bound in `app.ts` as `corpusService.resolveDeclaredAcIds.bind(corpusService)` — SPEC-038 §7 D4.
- **`CorpusService.findFeedingSkill(appliesTo)` generalizes `lore gate`'s "active feeding" rule-doc lookup from a hardcoded title to declared-scope discovery** (IoC vertical-slice tech-spec §4.1/§11, P1 slice-2) — finds the most-recently-updated APPROVED `knowledge` doc with `sub_type: "skill"` and `extra.skill.applies_to === appliesTo` (validated via `knowledgeExtraSchema.safeParse`, not a hand-rolled cast), returning `ok(null)` (a fact, never an error) when none match. Supersedes `gate.ts`'s former `findApprovedRuleDoc` (which matched on the exact literal `"Write-spec rules (gate feeding source)"` title) — any future gate can be fed by any approved skill doc that declares a matching `applies_to`, with no new per-gate title constant required. `gate.ts`'s `runSpecCreateGate` is its only production caller so far (`findFeedingSkill(app, SPEC_CREATE_PRODUCED_TYPE)`, scope `"spec"` — derived from `flows/feed-flow.ts::CHECKPOINT_PRODUCED_TYPE`, the SSOT map, rather than a second hardcoded literal).
- **`CorpusService.getReviewBundle` mirrors `getPlanBundle` for the SPEC-034 review-judgment pipeline** — assembles `{doc, parent?, links, brokenLinkTargets?, blueprint?}` for `runDeterministicChecks` (pure fn, `@lore/core`) and `AIProviderService.judgeDoc`. `blueprint` is PARAM-INJECTED (`getReviewBundle(idOrSlug, blueprint?)`), never read from disk here — CorpusService has no filesystem access; the CLI adapter (task C) loads `lore.tree.yaml` the same way `lore status --check-tree` does and passes the parsed `TreeBlueprint` in. Omitting it makes the `tree_position` check degrade to `"skipped"`, never a silent pass.
- **`AuditService.verify`'s join key is `(doc_id, version)` PLUS an action-family check, never a literal `audit.action === versions.action` string match AND never bare version-equality either** (SPEC-035 §2, §5 D9, action-family follow-up) — every audit writer now stamps `details.version` (the version its action produced); `verify` walks `StoreInterface.listAllVersions(since)` filtered to `action ∈ {create,update,approve,reject,restore}` and demands, for each, some audit entry sharing its `(doc_id, version)` pair AND whose `action` is a member of that versions-action's family (`VERSION_ACTION_AUDIT_FAMILY` in `audit-service.ts`: `create→create`, `update→{update,claim,release,evidence}`, `approve→approve`, `reject→reject`, `restore→restore`). `TaskWorkflowService`'s shared `writeTaskExtra` helper inserts every claim/release/evidence versions row under the generic action `"update"` but writes its audit entry under the more specific action `"claim"`/`"release"`/`"evidence"` — the `update` family membership (not bare version-equality) is what lets these satisfy the oracle despite the label divergence. Critically, `"judge"` (SPEC-034's AI-judgment audit action, which stamps the doc's CURRENT version but never produces a versions row) is NOT in any family — an audit entry with action `"judge"` can never incidentally satisfy a missing create/update/approve/reject/restore entry merely by sharing the same `(doc_id, version)`. `delete` is deliberately excluded from the anchor set even though `CorpusService.delete` also stamps `details.version` (its versions row is a `version: 0` sentinel, not part of the reconcile walk).
- **`CorpusService` has exactly one `DocRecord → DocSummary` projection site — the private `toSummary(doc)` method** (SPEC-036 §2 D3) — `get`/`list`/`buildTreeNode` all call it; it wraps `deriveTypeMeta(doc, {claimTtlMinutes})` (`@lore/core`) to populate `DocSummary.meta`, using an optional 3rd constructor param `claimTtlMinutes?: number` (same DI shape as `TaskWorkflowService`'s, wired from `resolveClaimTtlMinutes(config)` in `app.ts` — one resolution path, not a second config read). `OutlineService.toSummary` and `@lore/core`'s `task-workflow.ts::toDocSummary` are separate, narrower projections (MDX placeholder rendering and `ReadyRecord.task` respectively) that deliberately omit `meta` — out of scope for this convergence, noted inline at each site.
- **`TaskWorkflowService.recordVerifiedEvidence` is the SOLE injection point for `EvidenceEntry.attestation`** (SPEC-039 §2 D2, anti-spoofing) — the public `addEvidence` (CLI `lore evidence` / MCP `lore_evidence_add`) accepts an `EvidenceInput` type that structurally EXCLUDES `attestation`, AND runs an explicit runtime `hasOwnProperty` check on the raw input object, failing loud with `VALIDATION_ERROR` rather than silently stripping the key if a caller forces it past the type system (e.g. an `as EvidenceInput` cast on an untyped candidate). `recordVerifiedEvidence` is never registered on any CLI/MCP surface — its only production caller is `VerifyRunnerService.verifyPlan`, bound in `app.ts` the same way `resolveDeclaredAcIds` is bound. Both methods share one private append implementation (`appendEvidenceEntry`) — cap check, schema validation, and `ac_ref` cross-entity validation are never duplicated between them.
- **`verify-spawn.ts` (pure) / `verify-executor.ts` (bun-only) is the SPEC-039 §2 D5 spawn split, mirroring `../ai/hermetic-spawn.ts` / `../ai/claude-cli-provider.ts`** — `buildVerifySpawnSpec` + `deriveVerifyResult` + the `VerifySpawnSpec`/`VerifyExecutionResult` shapes live in the pure module so `VerifyRunnerService` and its vitest suite never import anything (not even a type) from the bun-only executor; `executeVerifySpawnSpec` (the only `Bun.spawn` callsite) imports its result type FROM `verify-spawn.ts`, never the reverse. `VerifyRunnerService` never imports either module's executor directly — `executor` is a constructor-injected port (SPEC-039 §2 D3), same shape as `getPlanBundle`/`recordVerifiedEvidence`.
- **`verify-executor.ts` uses a detached process group + SIGTERM→(5s grace)→SIGKILL escalation on timeout — a NEW behavior, no existing precedent** (SPEC-039 §2 D6) — `../ai/claude-cli-provider.ts`'s watchdog sends a single `SIGTERM` to the direct child only (adequate for the non-forking `claude` binary); a `verify.script.command` is an arbitrary shell one-liner that may fork descendants, so `Bun.spawn(..., {detached: true})` (POSIX `setsid()`) plus `process.kill(-pid, signal)` (negative pid = process group) is required to reach the whole tree. Do not copy this escalation pattern back onto `claude-cli-provider.ts` without re-deriving whether it needs it — they solve different threat models.
- **`DocWithNavigation.navigation.ancestors`** (SPEC-036 §2 D1) — the `parent_id` chain from root to direct parent, root-first, excluding the current doc; assembled by one iterative `store.find` walk inside `CorpusService`'s private `_getImpl` (search `ANCESTOR_DEPTH_CAP`). Guards: a seen-set stops on a repeated `parent_id` (manufactured cycle) and returns the pre-cycle chain; depth is capped at 20 (backstop only — the tree contract caps real depth at ≤5); a broken parent ref (`store.find` → null or a store error) terminates the walk with whatever was already collected — the doc stays viewable, tree-integrity reporting is `TreeCheckService`'s job. `parent` (`navigation.parent`) is derived from the SAME walk (`chain[0]`), not a second `store.find` call.
- **`GateEnforcer` closes the service-layer gate bypass** (retro follow-up item 8, "[arch] defense-in-depth", IoC vertical-slice tech-spec §4.1/§5.1/§11) — before this, the four gate checkpoints (`spec-create` / `spec-promote` / `plan-promote` / `task-claim`) existed ONLY behind `lore gate <checkpoint>`, a separate CLI command an agent/CI hook shells out to BEFORE the real write (`lore create` / `lore_create`, etc.). A caller going straight at `CorpusService.create` / `ReviewService.approve` / `TaskWorkflowService.claim` — an MCP tool, an HTTP dashboard route, a script — never invoked `lore gate` and bypassed every checkpoint. `GateEnforcer.enforce(checkpoint, ctx)` (`gate-enforcer.ts`) reuses `checkpointRegistry`/`resolveGateEnabled` (`checkpoint-registry.ts`, `@lore/core`) UNCHANGED — it adds zero new predicate logic, only translates a blocked verdict into `err(VALIDATION_ERROR)` (`field: "gate:<checkpoint>"`, `value` the failing reasons array; CLI `utils.ts::exitCode` maps this to exit 4, same as `lore gate`'s own blocked exit code).
  - **OPTIONAL constructor dependency, absent-in-bare-tests** — `CorpusService(store, telemetry?, claimTtlMinutes?, gateEnforcer?)`, `ReviewService(store, claimTtlMinutes?, gate?)`, `TaskWorkflowService(store, telemetry?, config, resolveDeclaredAcIds?, gate?)`. Every pre-existing bare `new XService(store)` construction (the ~3700 unit tests across this codebase) omits it and stays ungated — byte-identical to pre-`GateEnforcer` behavior. Only `app.ts`'s production composition root wires a real `GateEnforcer` — mirrors the identical optional-DI shape `Telemetry` and `claimTtlMinutes?` already use on these same three services.
  - **`ReviewService`/`TaskWorkflowService` take a `GateDependencies` BUNDLE (`{enforcer, getPlanBundle}`), never two separate optional params** — `plan-promote` (a plan's approve) and `task-claim` (a task's claim) both need an ancestor spec's data, not just the doc already in hand. Bundling as one dependency eliminates the illegal state of holding an `enforcer` with no way to resolve upstream-spec context (or vice versa) — both are always wired together in `app.ts`, or neither is. `getPlanBundle` is `corpusService.getPlanBundle.bind(corpusService)` (the SAME port `VerifyRunnerService` is already injected with) — never a direct `CorpusService` import (services don't cross-import).
  - **Gated call sites**: `CorpusService._createImpl` (spec-create, for `type === "spec"` only) and `CorpusService.set` (spec-promote, ONLY on an ACTUAL draft→approved TRANSITION — `existing.status !== "approved" && newStatus === "approved"` — never a no-op re-approve); `ReviewService.approve` (spec-promote for a `spec` doc, plan-promote for a `plan` doc); `TaskWorkflowService.claim` (task-claim). **Both `CorpusService.set` and `ReviewService.approve` gate spec-promote** — they are two INDEPENDENT write paths to `status: "approved"` (`set` never delegates to `approve`, and `approve` never delegates to `set`), and `set` performed ZERO transition validation before this change (`docPatchSchema` accepts any `DocStatus`, `isValidTransition` was never consulted) — `lore set --status approved` was a real bypass around `ReviewService.approve`'s own `INVALID_TRANSITION` check, so it needed its own spec-promote gate to close the SAME hole a second way.
  - **`buildUpstreamSpecContext(spec: DocRecord | undefined): GateContext`** (`checkpoint-registry.ts`) is the SSOT ctx-builder for `plan-promote`/`task-claim`'s `hasSpecParent`/`parentSpec`/`parentSpecPointer` trio — relocated here from a former CLI-adapter-local copy in `gate.ts` so both the CLI (`lore gate plan-promote`/`task-claim`) and the three gated services build the identical shape from the identical resolved-spec input; `gate.ts` now imports it rather than duplicating it.
  - **`MigrationService`'s direct `store.insert` bypass is intentionally UN-gated** — it writes docs straight to the store (not through `CorpusService.create`), a pre-existing, out-of-scope bypass (one-shot v1→v2 import, not a steady-state creation path); `GateEnforcer` was not retrofitted onto it.
- **`ValidityService`'s SPEC-044 D12 `stalenessCalibration` port is wired in `app.ts`** — `ValidityService(store, telemetry, {latestStalenessJudgment, recordCalibration})`, both bound to the SAME `JudgmentService` instance the composition root also exposes as `App.judgmentService` and injects into `StalenessProbeService`. Bare `new ValidityService(store)` unit-test constructions (every pre-SPEC-044 test) stay unwired and write no calibration records — the port is purely additive DI, same optional-third-arg shape `GateEnforcer` uses on `CorpusService`/`ReviewService`/`TaskWorkflowService`.

| `MigrationService` | One-shot v1→v2 import; reads YAML-frontmatter MD files, maps types, inserts via store |
| `TreeCheckService` | Drift detection (`missing \| extra \| misplaced \| cycle \| orphan`), auto-fix, parent_id ↔ link-table reconciliation |
| `AIProviderService` | AI provider dispatch + template render + ai.generation telemetry (SPEC-017 §3.6); assessPlan — LLM-as-judge plan assessment with one corrective retry (SPEC-026; v6 prompt + deterministic facts persistence + `computeGroundingWarnings` D4 cross-check, SPEC-040 §T2); judgeDoc — LLM-as-judge document review (SPEC-034; doc-truncation notice, SPEC-040 D8) |

| `TaskWorkflowService` | addEvidence / claim / release / ready — evidence log, advisory claim lease, computed readiness over `blocks` links (SPEC-025, own telemetry wiring) |
| `ExportDocsService` | One-way corpus→file exporter; maintains `.lore/export-index.json` (collision-safe human_id/file_path allocation, self-heals corrupted mappings) (SPEC-021); splices MDX placeholders into the written body via injected `ResolveDocBody` (SPEC-032 §3.3) |
| `JudgmentService` | record / latestFor / listFor for AI review judgments (`review_judgments`); recordCalibration (version-pinned human confirm/override) / computeCalibrationStats (Wilson-bound aggregation) for `calibration_records` — owns both tables as one judgment-derived family (SPEC-034, own telemetry wiring) |
| `StalenessProbeService` | `probeBatch` / `probeOne` — batch/single-doc orchestration for `lore review --staleness` (SPEC-044 §Design Decisions D4): assembles candidates via the pure selection layer (`selectProbeCandidates`, `@lore/core`) with ONE `countLinksByToIds` + ONE `latestJudgmentsByDocIds` call per batch (never a per-candidate N+1), probes each via the injected `probeStaleness` port (`AIProviderService.probeStaleness`), and persists via the injected `recordJudgment` port (`JudgmentService.record`, audit action `staleness_probe`, actor = the commissioning `by` — never the synthetic AI judge string). Store + two injected ports — never imports `AIProviderService`/`JudgmentService` directly. Probes NEVER mutate the probed doc (D13 — no version bump, no `extra` change); partial-batch failures collect-and-continue (per-candidate result captured, never aborts the batch) |
| `AuditService` | query (thin `store.queryAudit` delegation) / verify (versions⋈audit completeness oracle over the LIVE `audit` table) — store-only, no telemetry, constructor-resolved `verifySince` watermark (SPEC-035, mirrors TaskWorkflowService's `claimTtlMinutes` DI shape) |
| `AcService` | addCriterion / listCriteria / removeCriterion on `spec.extra.acceptance_criteria` (SPEC-038 §4, §6) — mirrors PhaseService's shape but CAS-writes with a version bump + audit entry (AC declarations are judge-consumed data); `listCriteria` aggregates per-AC evidence coverage across the spec's child plans' tasks (`computeAcCoverage`, `@lore/core`) and surfaces dangling `ac_ref` ids left behind by a forced removal |
| `VerifyRunnerService` | `verifyPlan` — trusted-runner orchestration for `lore verify` (SPEC-039 §2): filters a spec's declared script-mode ACs (respecting an optional `acIds` filter, reporting ai/human-mode ACs as skipped), resolves the target task via core's `resolveTargetTask`, runs each AC's command through an injected `executor` port, and records the outcome via `TaskWorkflowService.recordVerifiedEvidence` (the sole `attestation` injection point). Three constructor-injected ports (`getPlanBundle`, `recordVerifiedEvidence`, `executor`) — never imports CorpusService/TaskWorkflowService/the bun-only executor module directly. A launch-failure from `executor` aborts the whole run (fail-loud, no partial evidence ambiguity); a non-approved/active parent spec runs anyway with an advisory warning (never a hard gate) |
| `GateEnforcer` | `enforce(checkpoint, ctx)` — service-layer runner for the four `lore gate` checkpoints (spec-create/spec-promote/plan-promote/task-claim), reusing `checkpointRegistry`/`resolveGateEnabled` unchanged. | `DriftCheckService` | `checkDrift(probe)` — doc-code drift oracle orchestration (SPEC-045 §Design Decisions D4): loads every non-deleted spec's declared `extra.code_anchors`, probes each DISTINCT path exactly once via the caller-injected `FsProbe` port (built in the CLI/MCP adapter, `adapters/real-fs-probe.ts`), delegates classification to `computeDrift` (`@lore/core`); a THROWN probe error becomes a `probe_error` drift row for that anchor, never a batch-abort. Read-only (D9 — no store writes, no doc version bump, no audit row).
