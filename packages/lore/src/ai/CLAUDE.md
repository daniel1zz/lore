# Module: ai

## Purpose

Runtime AI provider implementations, registry builder, template engine, assess judge prompt builder, AI-default resolution, and in-memory test double. Wires the `AIProvider` interface (defined type-only in `@lore/core`) to concrete spawn-based execution. Six files cover: CLI spawner, registry, template rendering, AI-default resolution, assess prompt builder, and test double.

## Key Invariants

- **Type-only interface in `@lore/core`, concrete classes here** — `AIProvider` is declared in `packages/core/src/ai.ts` and imported by `ClaudeCliProvider` and `InMemoryAIProvider` via `@lore/core`. No reverse dependency: `@lore/core` never imports from `packages/lore/src/ai/`.
- **All providers use ClaudeCliProvider in v1** — `buildProviderRegistry` constructs a `ClaudeCliProvider` for every entry in the merged config map. A future SPEC (not this one) will add a `kind` discriminator and an `HttpProvider` class.
- **User provider entries REPLACE whole built-in entries** — no deep-merge. The user owns the full `{ command, args, timeout_ms }` block or none.
- **InMemoryAIProvider ships in src/ not tests/** — so any test in any package (including `@lore/core` tests) can import it without path hacks.
- **Never throw** — all public async methods return `Promise<Result<T, LoreError>>`. `ClaudeCliProvider.generate` wraps `Bun.spawn` in try/catch to map ENOENT to `AI_PROVIDER_ERROR`.
- **assess judge prompt lives here, NOT in `@lore/core`** (SPEC-026 §3 D8) — `assess-template.ts` owns the prompt text and `ASSESS_PROMPT_VERSION`; `@lore/core`'s `assessment.ts` stays limited to schemas + pure data helpers (truncation, JSON extraction, content rendering), matching the `task-workflow.ts` precedent of "core = schemas + pure helpers, no prompt strings."
- **Diff-omission truncation manifest (bugfix F3, `ASSESS_PROMPT_VERSION` 2→3)** — when `truncateDiffByFile` drops any diff files entirely, `buildAssessPrompt` (`assess-template.ts`) appends a "Truncation Manifest" section (grouped production/test/other via `classifyDiffFilePriority`) listing every dropped path plus a hard instruction not to score it as missing. Built from the SAME `diffResult.omittedFiles` array that feeds `truncated[]` — no second bookkeeping. Fixes an observed judge failure mode (`knowledge-assess-diff-truncation-systematically-hides-tests-from`): with no manifest, the judge couldn't tell "file absent" from "file cut for budget" and systematically under-scored test-coverage ACs whose test files sorted into the dropped set. Spec/plan/task section truncation is unaffected — still bare `truncated[]` entries, no manifest (those sections aren't split per-file).
- **Structured AC table (SPEC-038 §5, `ASSESS_PROMPT_VERSION` 3→4)** — when the plan's linked spec declares `extra.acceptance_criteria` (`extractDeclaredAcceptanceCriteria`, `assess-template.ts`), `buildAssessPrompt` replaces the "Spec Acceptance Criteria (verbatim)" prose section with a deterministic `id | statement | verify | coverage` table (`renderStructuredAcTable`, coverage from `@lore/core`'s `computeAcCoverage` — this module renders, core computes facts, per SPEC-038 §7 D6) and tightens the output instruction to `ac_id MUST be one of: <declared list>` plus a script-mode evidence-priority note. A spec with NO declared criteria renders byte-identical to v3 (verbatim fallback). `BuildAssessPromptResult.declaredAcIds` carries the same extracted id list out to `AIProviderService.assessPlan`, which uses it to build the `Set` for `validateAcIdContainment` (SPEC-038 §5 D5, in `../service/ai-provider-service.ts`) — one extraction site, no drift between what the prompt showed the judge and what the containment check enforces.
- **Attested coverage annotation (SPEC-039 §2 D8, `ASSESS_PROMPT_VERSION` 4→5)** — the structured AC table's coverage cell (`renderCoverageCell`, `assess-template.ts`) annotates `computeAcCoverage`'s `attested_pass`/`attested_fail` counts alongside pass/fail, e.g. `2 pass (1 attested), 0 fail` — present only when the corresponding attested count is `> 0`. Rendering only; the attested/self-reported split is derived exactly once in `@lore/core`'s `computeAcCoverage`, never re-derived here. A spec with no structured ACs still falls through to the untouched verbatim prose section.
- **review judge prompt (SPEC-034) lives here too, same split** — `review-template.ts` owns `REVIEW_PROMPT_VERSION` (string, e.g. `"v2"` — unlike assess's numeric `ASSESS_PROMPT_VERSION`, this one is a string because `judgeIdentitySchema.prompt_version` is `z.string()`) and a version-keyed `REVIEW_TEMPLATES: Record<string, ReviewTemplateFn>` registry (`v1` frozen + `v2` active; a future prompt spec adds a key rather than mutating an existing one). `@lore/core`'s `review-checks.ts` stays limited to the pure `runDeterministicChecks` fn — no prompt strings there either.
- **review v2 AC-vagueness advisory (SPEC-053, `REVIEW_PROMPT_VERSION` v1→v2)** — `review-template.ts` refactored v1's monolithic builder into a shared `assembleReviewPrompt(bundle, checks, budgets, nowIso, advisory)` taking an `{section, jsonField, rule}` advisory bundle; `buildReviewPromptV1` passes the `NO_ADVISORY` all-`""` bundle and stays **byte-identical** to its pre-SPEC-053 output (locked by the `packages/lore/tests/fixtures/review-prompt-v1.txt` fixture + AC-053-6). `buildReviewPromptV2` renders a `# AC Quantifiability (advisory)` material section (via `renderAcAdvisorySection` — AC list + `lintAcQuantifiability` verdict COUNT, so the judge never re-derives the lexical result) + an `advisory[]` JSON field + the exported `ADVISORY_ONLY_CLAUSE` output rule, ONLY when `extractSpecAcceptanceCriteria(bundle)` is non-empty (a spec with ≥1 declared AC) — otherwise it too returns the `NO_ADVISORY` assembly, byte-identical to v1 (non-spec / 0-AC). `judgeDoc` needs NO template-selection change (it already reads `REVIEW_TEMPLATES[REVIEW_PROMPT_VERSION]`), only a one-line `_finalizeJudgment` passthrough of `parsed.advisory` (verbatim, never re-derived, never allowed to alter the decision — the prompt forbids it). The advisory `kind` enum SSOT + `reviewAdvisorySchema` live in `@lore/core/review-judgment.ts`; CLI rendering is `renderAdvisoryBlock` (`adapters/cli/review-render.ts`, pure `""`-no-op when absent).
- **`InMemoryAIProvider`'s `sequence` mode mutates its own `responses` array via `shift()`** (SPEC-026 D9) — FIFO, one scripted response consumed per `generate()` call. Exhausting the script (more calls than responses) returns `AI_PROVIDER_ERROR` rather than silently reusing the last response — a test that under-scripts its sequence is a test bug, and this fails loud instead of masking it.
- **assess prompt registry (SPEC-040 §T2 D6, `ASSESS_PROMPT_VERSION` 5→6)** — `assess-template.ts` now exposes a version-keyed `ASSESS_TEMPLATES: Record<number, AssessTemplateFn>` (mirrors `REVIEW_TEMPLATES`): `5` is the frozen `buildAssessPrompt` (v5, provenance-only, no byte-identical guarantee going forward), `6` is the active `buildAssessPromptV6`. `getAssessTemplate(version)` is the Result-returning lookup (`err(AI_PROVIDER_ERROR)` naming an unregistered version, never a throw) — `AIProviderService.assessPlan` calls this instead of `buildAssessPrompt` directly. v6 adds a "# Deterministic Facts" section (`computeAssessmentFacts`, `@lore/core`, computed ONCE by the service from the full untruncated bundle and passed in as v6's 4th `facts?` param — persisted verbatim, never re-derived from truncated prompt text), a three-dimension rubric (`outcome`/`evidence_integrity`/`scope_fidelity`), and D5 scope-fit: when the plan declares `extra.ac_scope`, `renderStructuredAcTable`'s new optional 3rd param (`scopedIds`) annotates out-of-scope rows and `BuildAssessPromptResult.declaredAcIds` narrows to the scoped subset (so `validateAcIdContainment` enforces the PLAN's scope, not just the spec's full declared set).
- **`buildAssessDiffMeta(diffText)` / `listDiffFiles(diffText)` (SPEC-040 §T2)** — `diff-truncation.ts` exports `listDiffFiles`, the SAME `diff --git` header parse `truncateDiffByFile` uses internally, standalone; `assess-template.ts`'s `buildAssessDiffMeta` classifies its output via `classifyDiffFilePriority` into the `DiffMeta` shape (`@lore/core`) consumed by `computeAssessmentFacts`'s regression signals. Single derivation site — neither function re-implements diff-header parsing.
- **review truncation notice (SPEC-040 §T2 D8)** — `BuildReviewPromptResult` gained a structural `docTruncated: boolean` field (NOT derived by string-matching `truncated.includes("doc")` at call sites). When the document BODY (not parent context) is truncated for budget, `buildReviewPromptV1` inserts a "# Truncation Notice" prompt section instructing the judge to treat unseen content as present-but-unseen, and `AIProviderService.judgeDoc` stamps `NewReviewJudgment.truncated = true` (additive-only — key omitted, never `false`, when not truncated; `review-judgment.ts`'s `truncated` field stays OPTIONAL on both the raw LLM output schema and the persisted schema, unlike `checks` which becomes required once persisted).
- **golden-fixture harness aggregation (SPEC-040 §T3 D7)** — `assess-golden-aggregation.ts` is a pure module (no IO, no `getAssessTemplate`/provider import) consumed by `scripts/assess-golden.ts` (repo root, NOT under `packages/lore/src/`): `deriveGoldenDirectionLabel(overallScore)` maps a raw score onto a coarse `met`(>=80)/`partial`/`not_met`(<40) taxonomy; `computeMajorityLabel(labels)` collapses N scripted-or-live judge runs to one label per fixture per prompt version, with a documented conservative tie-break (`not_met` > `partial` > `met`) for a genuine N-way tie; `aggregateGoldenRun(runs)` computes both prompt versions' agreement-with-expected rates and a `promotable` verdict — non-inferiority (`candidateAgreement >= incumbentAgreement`), ties pass. The script's `--dry-run` mode (lists fixtures, zero provider calls, AC-ADF-7) and scored mode (`--candidate <v> --incumbent <v>`, live provider calls) both live in `scripts/assess-golden.ts`; this module is the arithmetic ONLY, unit-tested with scripted labels (AC-ADF-12) — it never invokes a live provider itself.

## Patterns

- **No module-level IO** — `ClaudeCliProvider` only spawns inside `generate()`, never in the constructor. Registry construction is purely synchronous object creation.
- **Timeout watchdog** — `setTimeout` + `proc.kill("SIGTERM")` + `clearTimeout` on normal completion. The killer timer is always cleared to prevent stale-timer surprises on reuse.
- **Hermetic judge spawn (SPEC-030 AC-HJ-1)** — `ClaudeCliProvider.generate` never builds `Bun.spawn`'s `cwd`/`env`/`args` inline. It calls `buildHermeticSpawnSpec(cfg, {sourceEnv: process.env, tmpDir: tmpdir()})` (`hermetic-spawn.ts`), a pure function so the sanitization logic is vitest-testable even though the callsite is bun-only. The spec: neutral cwd (OS tmpdir, not the host project dir), a sanitized env (denylist strips `CLAUDECODE` + `CLAUDE_*`, everything else — including auth vars — passes through), and, ONLY when the configured command's basename is `claude`, the official `--setting-sources ""` isolation flag appended to args (probed via `claude --help`; `--bare` was rejected because it restricts auth to `ANTHROPIC_API_KEY`/`apiKeyHelper` only). A custom judge command (any other basename) gets no injected flag.
- **Template rendering is two-pass** — conditionals (`{{#key}}…{{/key}}`) before substitutions (`{{key}}`), to prevent partial expansion of vars inside a collapsed block.
- **assess has no non-AI mode** (SPEC-026 §3 D5) — `resolve-ai.ts::isAssessAiBraked(resolveAiDefault(undefined, surface, configDefaults))` is the only correct way to gate it: the built-in per-surface AI-off default (agent/mcp/http_token) must NOT brake assess, only an EXPLICIT `ai.default_per_surface.<surface> = false` config override should. Checking `resolveAiDefault(...).ai === false` directly (without the source-tier check) is a bug — it braked assess on every agent/mcp call, defeating D5's entire point.
